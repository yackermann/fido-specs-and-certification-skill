# FIDO AppID and Facet Specification

Version 2.1 · Proposed Standard · 2022-05-23 · [source](https://fidoalliance.org/specs/common-specs/fido-appid-and-facets-v2.1-ps-20220523.html)

## Summary

Defines the AppID and FacetID model that scopes UAF and U2F credentials to an application. An AppID is the identifier a credential is bound to. A FacetID identifies one concrete caller: a web origin, an Android app (`android:apk-key-hash:` / `android:apk-key-hash-sha256:` hash of the APK signing certificate) or an iOS app (`ios:bundle-id:`). When the AppID is an HTTPS URL, the FIDO client fetches a JSON Trusted Facet List from it. The client picks the entry whose `version` is the highest one not above the protocol version in use, and allows the caller only if its FacetID is listed. The document sets the processing rules: HTTPS fetch and redirect handling, origins reduced to scheme/host/port, all web origins required to share the AppID's eTLD+1, and no wildcards. Remote attestation of app identity is explicitly a non-goal.

The document applies to the UAF and U2F protocol families. WebAuthn replaced the AppID with the RP ID, but its `appid` and `appidExclude` extensions use the AppID rules here so that legacy U2F credentials keep working.

**Who needs it:** platform & client developers, relying parties & server developers (UAF/U2F, or WebAuthn sites migrating U2F credentials)

**Changes from previous version:** Adds the SHA-256 Android FacetID form `android:apk-key-hash-sha256:`, with keytool/openssl commands for computing both hashes and a note to list both forms for older clients. Splits the JSON definition into a TrustedFacetList dictionary holding an array of TrustedFacets entries, and marks `version` and `ids` as required. Defines version matching as the highest listed version not above the protocol version in use. Words the origin check explicitly as the most specific public suffix plus one label (eTLD+1) and adds Android sample code for the SHA-256 FacetID. The rest is editorial and reference updates.

## Reading guide

**Start here:** read §2.4 Non-Goals `#h3_non-goals` first, to see what facets do not protect against. Then read §3 `#h2_the-appid-and-facetid-assertions`, which defines the default scope as the same origin as the AppID. Then read §3.1.2 `#h4_determining-if-a-caller-s-facetid-is-authorized-for-an-appid`, the only real algorithm in the document. Suite: 2.1 belongs with the 2022 common specs and is the version cited by UAF 1.2. The text says it covers both U2F and UAF. It does not mention WebAuthn or CTAP.

**Section by section:**
- §2 Overview `#h2_overview` and §2.1–§2.3 (`#h3_motivation`, `#h3_avoiding-app-phishing`, `#h3_comparison-to-oauth-and-oauth2`): informative. They explain why one logical application with web, Android and iOS facets should share credentials without needing an embedded "app secret".
- §2.4 Non-Goals `#h3_non-goals`: the mechanism does not identify an app to the server remotely, and it does nothing against a hostile TCB (root malware). On desktop OSes without app isolation, only web-origin scoping can be enforced.
- §3 `#h2_the-appid-and-facetid-assertions`: the AppID is a URL sent by the server. If it is an https URL, the client may fetch a TrustedFacetList from it to widen the scope. All registrations under one AppID share the same audience.
- §3.1.1 `#h4_determining-the-facetid-of-a-calling-application`: FacetID formats (MUST). Web: the origin, with no path and default ports dropped. Android: `android:apk-key-hash-sha256:` or `android:apk-key-hash:` (SHA-1), which is base64 of the APK signing-cert hash with padding removed. iOS: `ios:bundle-id:`. List both Android forms if older clients must work.
- §3.1.2 `#h4_determining-if-a-caller-s-facetid-is-authorized-for-an-appid`: the decision procedure:
  - A null or empty AppID becomes the caller's FacetID (MUST).
  - A non-https AppID equal to the FacetID, or an https FacetID on the same host as the AppID, passes with no fetch.
  - Otherwise the client does an anonymous GET: no cookies, auth, Origin/Referer or client certificates.
  - The response MUST have Content-Type `application/fido.trusted-apps+json`, and the server MUST serve the same body to everyone.
  - A redirect is followed only if the response carries `FIDO-AppID-Redirect-Authorized: true`.
  - The client picks the trustedFacets entry with the highest version that is ≤ the protocol version.
  - https ids are reduced to scheme, host and port. Ids outside the AppID's eTLD+1 (public suffix list) are discarded.
  - If fetching or parsing fails, the client MUST abort.
- §3.1.3 `#h4_trustedfacet-list-and-structure` (with `#h5_dictionary-trustedfacetlist-members` and `#h5_dictionary-trustedfacets-members`): `{ "trustedFacets": [ { "version": {major, minor}, "ids": [...] } ] }`. Both members are required.
- §3.1.4–§3.1.5 (`#h4_appid-example-1`, `#h4_appid-example-2`): worked examples. http entries and other registrable domains are discarded and the port does not matter. A private public suffix (hosting.example.com) stops sharing between tenants.
- §3.1.6 `#h4_obtaining-facetid-of-android-native-app`: informative Java for computing both Android FacetIDs.
- §3.1.7 `#h4_additional-security-considerations` and §3.1.7.1 `#h5_wildcards-in-trustedfacet-identifiers`: trusting an origin implicitly trusts its subdomains. Callers SHOULD be identified through platform IPC. A compromised listed facet can act as a confused deputy. Wildcards are not supported (informative rationale).

**What matters most:**
- The eTLD+1 check is computed from the *original* AppID host, before any redirect, and the comparison is case-insensitive (§3.1.2 `#h4_determining-if-a-caller-s-facetid-is-authorized-for-an-appid`).
- The fetch must be anonymous and the response uniform. A server that varies the response by cookie or IP breaks the rule (§3.1.2).
- The client must refuse to follow a redirect that lacks the authorization header, and must abort, not fall back, when the list is invalid (§3.1.2).
- Android facets come from the signing certificate, not the package name. Changing the signing key changes the FacetID (§3.1.1 `#h4_determining-the-facetid-of-a-calling-application`).
- Versions are selected per protocol message version, using the "highest ≤" rule (§3.1.2).

**Watch out for:**
- §3.1.2 says that after a redirect the client restarts "from step 4", but the steps are not numbered in the published text. Step 4 corresponds to the fetch step.
- §3.1.2 gives `apk:` as an example application scheme, while §3.1.1 defines `android:` FacetIDs.
- In §3.1.1, the sentence before Example 1 says it computes the SHA-1 hash, but Example 1 computes SHA-256.
- The Glossary 2.1 entry for Application Facet ID lists only the SHA-1 Android form.

**Related documents:** `fido-uaf-protocol` (the Version structure, where the AppID is carried); `fido-u2f-javascript-api` and `fido-u2f-overview` (U2F use of AppIDs); `webauthn` (the RP ID that replaces the AppID, and its `appid` extension for legacy credentials); `fido-glossary` (definitions of facet and AppID); `fido-security-ref` (SM-14 AppID/RP ID separation).
