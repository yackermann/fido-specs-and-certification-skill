# FIDO Registry of Predefined Values

Version 1.2 · Proposed Standard · 2017-04-11 · [source](https://fidoalliance.org/specs/fido-u2f-v1.2-ps-20170411/fido-registry-v1.2-ps-20170411.html)

## Summary

Copy of the FIDO Registry of Predefined Values shipped with the U2F 1.2 suite. It holds the UAF-era constants: user verification methods, key and matcher protection, attachment hints, transaction-confirmation display types, nine signature algorithms (P-256, secp256k1, RSA-PSS, SM2, RSA PKCS#1 v1.5) and four public key formats. It has no attestation-type section and no string forms; both came in 2.1, which also added the FIDO2-era algorithms.

**Who needs it:** UAF authenticator vendors and server developers working against the 2017 suites

**Look here for:**
- User verification methods → §3.1 `#h3_user-verification-methods`
- Signature algorithms → §3.6.1 `#h4_authentication-algorithms`

**Changes from previous version:** Editorial only. The constants and text match 1.1; only the status header and reference links changed.

## Reading guide

**Use this version when:** you work with the U2F 1.2 / UAF 1.2-era suite published in April 2017, or with UAF deployments whose metadata uses numeric constants only. Suite: UAF 1.2 / U2F 1.2.

**Differences from 1.1:** none in substance. The text and every constant are identical. Only the status header, the previous-version link (it points to the UAF 1.0 registry) and the reference URLs changed.

**Differences from 2.x:**
- No string forms: constants are numbers only.
- §3.1 `#h3_user-verification-methods` uses the unsuffixed names (`USER_VERIFY_PRESENCE`, `USER_VERIFY_FINGERPRINT`, …) and has no `_EXTERNAL` methods. Its single rule is that all verification is local to the authenticator.
- §3.4 `#h3_authenticator-attachment-hints` does not yet require `EXTERNAL` to be combined with another hint.
- §3.6.1 `#h4_authentication-algorithms` has only 0x0001–0x0009: P-256 and secp256k1 ECDSA RAW/DER, RSASSA-PSS SHA-256 RAW/DER, SM2 and RSA EMSA-PKCS1 SHA-256 RAW/DER.
- §3.6.2 `#h4_public-key-representation-formats` has four formats and no COSE.
- There is no attestation-type section at all (2.1 added §3.7).

**Section by section:** §3.1–§3.6 have the same structure and the same values as 2.3. The key-protection and matcher "effective security" notes are already present in §3.2 `#h3_key-protection-types` and §3.3 `#h3_matcher-protection-types`. For the semantics of each family, see the 2.3 page's reading guide.
