# FIDO Registry of Predefined Values

Version 2.1 · Proposed Standard · 2019-12-17 · [source](https://fidoalliance.org/specs/common-specs/fido-registry-v2.1-ps-20191217.html)

## Summary

Earliest catalogued common-specs (FIDO2-era) version of the FIDO Registry, published in December 2019. It extends the UAF-era constants for use with FIDO2 metadata, each constant gaining a case-sensitive string representation for metadata. It was the current Registry from December 2019 until the May 2022 release. 2.2 later added Ed448, corrected the P-521 name and added AnonCA and None attestation types.

**Who needs it:** authenticator vendors, FIDO server developers, certification applicants using 2019–2022 metadata

**Look here for:**
- `_INTERNAL` / `_EXTERNAL` user verification flags → §3.1 `#h3_user-verification-methods`
- Signature algorithms → §3.6.1 `#h4_authentication-algorithms`
- Attestation types → §3.7 `#h3_authenticator-attestation-types`

**Changes from previous version:** Substantive. Adds a string form for every constant. Renames user verification flags with an `_INTERNAL` suffix (same meaning, made explicit) and adds `USER_VERIFY_PASSCODE_EXTERNAL` and `USER_VERIFY_PATTERN_EXTERNAL`. Adds signature algorithms 0x000A–0x0012 (RSASSA-PSS SHA-384/512, RSASSA-PKCS1-v1_5 SHA-1/256/384/512, P-384 and "P-512" ECDSA, Ed25519) and `ALG_KEY_COSE`. Adds a new §3.7 with attestation types (basic full, basic surrogate, ECDAA, AttCA).

## Reading guide

**Use this version when:** you read metadata or servers built between December 2019 and May 2022 (early FIDO2/CTAP 2.0–2.1 and MDS 3.0 drafts), or you trace where a string form came from. Suite: FIDO2 / common specs 2.x. It was the first Registry that was not tied to the UAF/U2F suites.

**Differences from 1.2:** big changes.
- Every constant gets a case-sensitive string form for metadata.
- §3.1 `#h3_user-verification-methods` renames the UV flags with an `_INTERNAL` suffix (same values and meaning) and adds `USER_VERIFY_PASSCODE_EXTERNAL` (0x800) and `USER_VERIFY_PATTERN_EXTERNAL` (0x1000). It also replaces 1.2's general rule that all verification is local with an internal/external definition tied to the authenticator boundary.
- §3.4 `#h3_authenticator-attachment-hints` now says `EXTERNAL` MUST be combined with another hint.
- §3.6.1 `#h4_authentication-algorithms` adds 0x000A–0x0012 (RSA-PSS SHA-384/512, PKCS#1 v1.5 SHA-256/384/512/SHA-1, P-384, "P-512", Ed25519) and COSE key mappings.
- §3.6.2 `#h4_public-key-representation-formats` adds `ALG_KEY_COSE`.
- The new §3.7 `#h3_authenticator-attestation-types` defines `BASIC_FULL`, `BASIC_SURROGATE`, `ECDAA` and `ATTCA`. There is no `NONE` or `ANONCA` yet.

**Differences from 2.2:** see the 2.2 page. 2.2 corrected the errors listed below and added Ed448, ANONCA and NONE.

**Watch out for (errors in this version's §3.6.1 `#h4_authentication-algorithms`):**
- secp256k1 is mapped to COSE alg 7 instead of -47.
- 0x000B (PSS SHA-512) has the string "rsassa_pss_sha256_raw", the same string as 0x0003.
- 0x0011 is called `SECP512R1` with the string "secp512r1_ecdsa_sha256_raw". The curve is P-521 and the hash is SHA-512.

Code that parses metadata strings from this period should expect these values.

**Section by section:** structure as in 2.3 (minus the later additions); see that page's reading guide.
