# FIDO Registry of Predefined Values

Version 2.3 · Proposed Standard · 2026-01-05 · [source](https://fidoalliance.org/specs/common-specs/fido-registry-v2.3-ps-20260105.html)

## Summary

The FIDO Registry of Predefined Values: the numeric and string constants for authenticator characteristics shared by UAF, FIDO2 and the Metadata Service. It defines user verification method flags (`USER_VERIFY_*`, with `_INTERNAL` / `_EXTERNAL` variants), key protection types (`KEY_PROTECTION_*`), matcher protection types, attachment hints (`ATTACHMENT_HINT_*`), transaction-confirmation display types, authentication algorithms (`ALG_SIGN_*`, from P-256 ECDSA through RSA-PSS/PKCS#1, SM2, Ed25519 and Ed448) with their allowed public key formats (`ALG_KEY_*`, including COSE), and attestation types (`ATTESTATION_BASIC_FULL`, `_BASIC_SURROGATE`, `_ECDAA`, `_ATTCA`, `_ANONCA`, `_NONE`). Each constant has a case-sensitive string form used in metadata.

Metadata Statements and MDS entries describe authenticators with these values: the key protection, matcher protection, user verification methods, attachment hints, algorithms and attestation types an applicant declares are all Registry constants. The Registry is expected to grow as new algorithms and authenticator characteristics are defined.

**Who needs it:** authenticator vendors (writing Metadata Statements), FIDO server and relying-party developers (policy and metadata processing), certification applicants, labs

**Look here for:**
- User verification method flags and the internal/external distinction → §3.1 `#h3_user-verification-methods`
- Key protection values, including multi-device (synced) keys → §3.2 `#h3_key-protection-types`
- Attachment hints (wired, wireless, NFC, smart card …) → §3.4 `#h3_authenticator-attachment-hints`
- Signature algorithm identifiers and encodings → §3.6.1 `#h4_authentication-algorithms`
- Public key representation formats → §3.6.2 `#h4_public-key-representation-formats`
- Attestation type constants → §3.7 `#h3_authenticator-attestation-types`

**Changes from previous version:** Adds `KEY_PROTECTION_SYNC_FABRIC` (0x0020, "sync_fabric") for keys designed to exist on several devices (multi-device credentials). When it is set, the authenticator has to set the WebAuthn backup-state flags and declare multi-device support in its Metadata Statement; the flag can be combined with SE/TEE/software protection for imported keys. Also adds `ATTACHMENT_HINT_SMART_CARD` (0x0200, "smart-card") for external authenticators that speak ISO 7816. The rest is reference status updates.

## Reading guide

**Start here:** this is a lookup table, not a protocol. Read §1 Notation `#h2_notation` once: it says the "(optional)" markers are defined by the specs that cite the Registry. Then go straight to the section for the field you are filling in. Most readers need §3.1 `#h3_user-verification-methods`, §3.2 `#h3_key-protection-types` and §3.6.1 `#h4_authentication-algorithms`, because those values go into every Metadata Statement. Suite: 2.3 is the current Registry for FIDO2/CTAP and MDS 3.1.1. The UAF 1.2 documents also use it.

**Section by section:**
- §3 Authenticator Characteristics `#h2_authenticator-characteristics`: normative. Every family has a numeric value (a bit flag or a 16-bit integer) and a case-sensitive string form. Metadata uses the string form. UAF Discovery and UAF policy use the number.
- §3.1 User Verification Methods `#h3_user-verification-methods`: 32-bit `USER_VERIFY_*` flags. An `_INTERNAL` method gathers, processes and matches the data entirely inside the authenticator boundary. An `_EXTERNAL` method (only `PASSCODE_EXTERNAL` 0x800 and `PATTERN_EXTERNAL` 0x1000 exist) may collect input outside but must match inside. `PRESENCE_INTERNAL` MUST be set for any presence check. Setting it alone only means a human was involved, not that the user was verified. `NONE` is for silent authenticators. `ALL` (MAY) means every flagged method is enforced (AND). Without it, any one method is enough (OR).
- §3.2 Key Protection Types `#h3_key-protection-types`: 16-bit `KEY_PROTECTION_*`. In metadata some flags exclude others: `SOFTWARE` excludes `HARDWARE`/`TEE`/`SECURE_ELEMENT`, and `TEE` and `SECURE_ELEMENT` exclude each other and should be paired with `HARDWARE`. In server policy any bits may be ORed. `REMOTE_HANDLE` MUST be combined with another flag. New in 2.3: `SYNC_FABRIC` (0x0020). When it is set, the authenticator SHALL set the WebAuthn backup-state flags and SHALL declare multi-device support in the Metadata Statement. It may be combined with SE/TEE/SOFTWARE to describe an imported synced key.
- §3.3 Matcher Protection Types `#h3_matcher-protection-types`: `SOFTWARE`, `TEE` and `ON_CHIP`. In metadata the three exclude each other.
- §3.4 Authenticator Attachment Hints `#h3_authenticator-attachment-hints`: hints, not mandatory metadata. `INTERNAL` cannot be combined with other hints. `EXTERNAL` MUST be combined with at least one other hint. `NFC`, `BLUETOOTH` and `WIFI_DIRECT` SHOULD also set `WIRELESS`. The new `SMART_CARD` (0x0200, ISO 7816) SHOULD also set `WIRED`. For a phone usable locally and remotely, the client MUST report only the bit that applies.
- §3.5 Transaction Confirmation Display Types `#h3_transaction-confirmation-display-types`: `ANY` MUST be set whenever any display exists, and the value MUST be 0 when there is none. `PRIVILEGED_SOFTWARE`, `TEE` and `HARDWARE` exclude each other. `REMOTE` combines with any of them.
- §3.6.1 Authentication Algorithms `#h4_authentication-algorithms`: `ALG_SIGN_*` 0x0001–0x0013. Each entry gives the exact byte encoding and the key formats it works with (including the COSE kty/alg/crv triple). Values 0x0001–0x0009 are the UAF-era RAW/DER pairs. 0x000A–0x0013 are the RSA-PSS/PKCS#1 v1.5 variants, P-384, P-521, Ed25519 and Ed448, all RAW and COSE-only. SM2 (0x0007) is marked optional.
- §3.6.2 Public Key Representation Formats `#h4_public-key-representation-formats`: `ALG_KEY_ECC_X962_RAW`/`_DER`, `RSA_2048_RAW`/`_DER` and `COSE` (0x0104). For X962_DER, authenticators MUST emit `namedCurve` and UAF servers MUST accept it.
- §3.7 Authenticator Attestation Types `#h3_authenticator-attestation-types`: `BASIC_FULL` 0x3E07, `BASIC_SURROGATE` 0x3E08 (self-signed, so it proves nothing about the hardware), `ECDAA` 0x3E09, `ATTCA` 0x3E0A, `NONE` 0x3E0B and `ANONCA` 0x3E0C. `ANONCA` maps to the WebAuthn formats `android-safetynet`, `android-key`, `apple` and `apple-appattest`.

**What matters most:**
- Set key and matcher protection by *effective* security. A secure-element key that host software can export counts as `KEY_PROTECTION_SOFTWARE`. A passcode matcher that is on-chip but receives the passcode unauthenticated counts as `MATCHER_PROTECTION_SOFTWARE` (notes in §3.2 `#h3_key-protection-types` and §3.3 `#h3_matcher-protection-types`).
- Exclusivity applies to metadata, not to policy. A Metadata Statement may carry at most one value from each mutually exclusive group (§3.2 `#h3_key-protection-types`).
- Synced passkeys: `KEY_PROTECTION_SYNC_FABRIC` comes with the backup-flag and Metadata Statement obligations above (§3.2 `#h3_key-protection-types`).
- Encodings are exact. RAW ECDSA is R‖S big-endian. The DER RSA variants are an OCTET STRING, not a BIT STRING. PSS default parameters are MGF1 with the same hash and a salt as long as the hash (§3.6.1 `#h4_authentication-algorithms`).
- Use the string forms exactly as written. They are case-sensitive, and the attachment hint uses a hyphen ("smart-card") while other strings use underscores (§3.4 `#h3_authenticator-attachment-hints`).

**Watch out for:**
- The §3.1 note about the `_INTERNAL` suffix being "made explicit" is left over from the 2.1 rename. The numeric values are the same as in UAF 1.x.
- `ATTESTATION_ANONCA` (0x3E0C) is listed after `ATTESTATION_NONE` (0x3E0B), so don't infer values from the listing order (§3.7 `#h3_authenticator-attestation-types`).
- The ECDAA and ATTCA entries say support is optional "at this time" but might be required by certification. Check the current certification policy.
- The [FIDOEcdaaAlgorithm] reference names the 2022 Proposed Standard but its link points to the 2018 v2.0 draft.

**Related documents:** `fido-metadata-statement` (where these strings are used); `fido-metadata-service`; `fido-authenticator-security-requirements` (the authenticator boundary used by `_INTERNAL`); `fido-security-ref` (the threat model the "effective security" notes rely on); `fido-ecdaa-algorithm` (`ATTESTATION_ECDAA`); `fido-uaf-protocol` and `fido-uaf-authnr-cmds` (policy matching, KRD encodings); `webauthn` (backup flags, attestation formats).
