# FIDO Security Reference

Version 2.1 · Proposed Standard · 2022-05-23 · [source](https://fidoalliance.org/specs/common-specs/fido-security-ref-v2.1-ps-20220523.html)

## Summary

Security analysis of the FIDO protocols: UAF, U2F, and FIDO2 (CTAP and WebAuthn). It classifies attacks by whether they are automatable and whether they need the user's device each time, then states numbered security goals `[SG-n]`, the measures that achieve them `[SM-n]` with a measures-to-goals mapping, and the assumptions the analysis relies on `[SA-n]`. The largest part is a threat catalogue (`T-x.y.z`). Each threat names the attack class, the goals it violates, its consequences and its mitigations, grouped by target: client side (user deception, the user device and apps, the client-to-authenticator channel), the authenticator, the relying party (server data, challenge handling), the TLS channel, the supply chain (authenticator manufacturers, server vendors, metadata service operators), and threats specific to second-factor use.

The FIDO Authenticator Security Requirements used in certification cite this version and define their security measures by reference to it, so it is background reading for authenticator security certification.

**Who needs it:** certification applicants, labs, authenticator vendors, relying parties & server developers doing threat modelling

**Look here for:**
- Attack classes (AC1…) used to rate threats → §3 `#h2_attack-classification`, `#attack-classes`
- FIDO security goals and protected assets → §4 `#h2_fido-security-goals`, §4.1 `#h3_assets-to-be-protected`
- Which measures satisfy which goals → §5.1 `#h3_relation-between-measures-and-goals`
- Security assumptions → §6 `#h2_fido-security-assumptions`
- Threats to the authenticator → §7.2 `#h3_threats-to-fido-authenticator`
- Threats from reused or weak server challenges → §7.3.2 `#h4_threats-due-to-server-challenge-characteristics`

**Changes from previous version:** Substantive. Scope widens from UAF/U2F to UAF, U2F and FIDO2/WebAuthn: the UAF security goals and assumptions become FIDO-wide, with notes on how U2F and WebAuthn differ. A separate attack-classes list is added. Security measures grow from SM-1–15 to SM-1–29 and goals from 15 to 16. Threats are reorganized: the authenticator gets its own subsection, new subsections cover the client-to-authenticator channel and server challenge characteristics (for example nonce reuse), the second-factor section is extended to WebAuthn, and "Creating a Fake Client" no longer has its own subsection.

## Reading guide

**Start here:** read §3 Attack Classification `#h2_attack-classification` and the unnumbered Attack Classes list `#attack-classes` (AC1–AC6). Then §4 Security Goals `#h2_fido-security-goals` (SG-1…SG-16), §5 Security Measures `#h2_fido-security-measures` (SM-1…SM-29) and §6 Assumptions `#h2_fido-security-assumptions` (SA-1…SA-6). Every threat row in §7 points back to these IDs. Suite: 2.1 covers UAF, U2F and FIDO2 (CTAP2 + WebAuthn). It is the version the Authenticator Security Requirements build on.

**Section by section:**
- §2 Introduction `#h2_introduction` / §2.1 `#h3_intended-audience`: the reference architecture. In WebAuthn the browser takes the FIDO Client role and the platform takes the ASM role.
- §3 `#h2_attack-classification` and `#attack-classes`: AC1–AC4 are scalable, meaning the marginal cost per extra victim is near zero. AC5–AC6 are non-scalable, one-off physical or targeted attacks. The class number is not a difficulty ranking. Attacks by someone who had physical access before the legitimate user uses the device again are explicitly out of scope.
- §4 `#h2_fido-security-goals`: SG-1 strong authentication through SG-15 respect for OS security boundaries, plus the new SG-16, which requires the authenticator to be assessable by a lab. U2F does not have SG-14 (transaction non-repudiation). WebAuthn reaches it only through extensions. §4.1 `#h3_assets-to-be-protected` lists the assets: authentication private keys, the RP's key reference, attestation keys, CA keys and certificates, trust stores, linkable identifiers, and TLS keys.
- §5 `#h2_fido-security-measures`: each SM is tagged with the protocols it applies to (U2F/UAF/WebAuthn).
  - SM-1–15 are the protocol measures: key protection, unique keys, attestation, status checking via MDS, consent, a verifier database of public keys only, TLS, nonces, certification, transaction confirmation (UAF + WebAuthn only), round-trip integrity, channel binding, KHAccessToken / clientPIN, AppID/RP ID separation, and the signature counter.
  - SM-16–29 are authenticator-implementation measures: allowed cryptography, side-channel and fault resistance, birthday bound, ≥100 000-unit attestation batches, protection of stored data, full vendor description, key handles bound to the authenticator and RP, a trusted path, input validation, protection of UV reference data, and remote-timing resistance.
- §5.1 `#h3_relation-between-measures-and-goals`: the table mapping each goal to its supporting measures.
- §6 `#h2_fido-security-assumptions` / §6.1 `#h3_discussion`: sound crypto (SA-1), OS isolation (SA-2), TLS (SA-3), a user device that acts as the user's trustworthy agent (SA-4), keys losing assurance over time (SA-5), and a trustworthy RP back end (SA-6). §6.1 sets the limits: root malware and kiosks defeat these assumptions, and transaction confirmation is the mitigation offered.
- §7 Threat Analysis `#h2_threat-analysis`: each row gives a T-ID, an attack class, a description, consequences, mitigations (SM references), and the goals or assumptions violated.
  - §7.1 client side (`#h3_threats-to-client-side`): homograph mis-registration/authentication (`#h4_exploiting-user-s-pattern-matching-weaknesses`), corrupted or malicious clients and apps and phishing (`#h4_threats-to-the-user-device-fido-client-and-relying-party-client-applications`), and the client–authenticator link (malicious apps or devices talking to the authenticator directly, sniffing) (`#h4_threat-to-the-communication-between-client-and-fido-authenticator`).
  - §7.2 authenticator `#h3_threats-to-fido-authenticator`: T-1.4.1–T-1.4.32. Topics include key compromise, UV bypass, fake authenticators, TC display overlay, RNG/PRNG compromise, bad key generation, side channels, fault injection, counter non-monotonicity, UV caching, debug interfaces, malformed input and remote timing.
  - §7.3 relying party (`#h3_threats-to-relying-party`): DB read/modify, web-app malware, linking via the RP database (`#h4_threats-to-fido-server-data`), and reused or predictable challenges (`#h4_threats-due-to-server-challenge-characteristics`).
  - §7.4 TLS channel (`#h3_threats-to-the-secure-channel-between-client-and-relying-party`, `#h4_exploiting-weaknesses-in-the-secure-transport-of-fido-messages`): TLS proxy, fraudulent certificates, real-time MITM.
  - §7.5 infrastructure (`#h3_threats-to-the-infrastructure`): attestation key compromise and malicious hardware at manufacturers (`#h4_threats-to-fido-authenticator-manufacturers`), trust-anchor injection at server vendors (`#h4_threats-to-fido-server-vendors`), and MDS signing-key compromise and data injection (`#h4_threats-to-fido-metadata-service-operators`).
  - §7.6 second-factor (`#h3_threats-specific-to-second-factor-authenticators-u2f-uaf-webauthn`): error-status probing for tracking, an RP attacking wrapped key handles (no mitigation; relies on SA-1), and physical attacks on presence-only devices.

**What matters most:**
- Certification works from the SM and T IDs. The Security Requirements derive their requirements from these measures and threats, so cite exact IDs (§5 `#h2_fido-security-measures`, §7.2 `#h3_threats-to-fido-authenticator`).
- Server challenges must never repeat, or repeat only with negligible probability (the text gives about 2^-112 as an example) (T-2.3.1 in §7.3.2 `#h4_threats-due-to-server-challenge-characteristics`).
- Attestation privacy depends on large batches (SM-20) or ECDAA. Extracting the attestation key enables fake authenticators (T-1.4.6), and the remedy is MDS status checking (SM-4) (§4.1 `#h3_assets-to-be-protected`, §7.2).
- For UV caching (T-1.4.28), conforming authenticators add a signed extension, and servers accept it only if they requested caching (§7.2 `#h3_threats-to-fido-authenticator`).
- The mitigation for non-resident key-handle wrapping is only an assumption (T-5.1.2 in §7.6 `#h3_threats-specific-to-second-factor-authenticators-u2f-uaf-webauthn`).

**Watch out for:**
- The document is informative analysis: its RFC 2119 keywords are boilerplate, and the binding requirements are in `fido-authenticator-security-requirements`.
- The §5.1 table has no row for SG-16 and does not list SM-18, 19, 22, 24, 26, 27 or 28. It calls SM-20 "No Identifying Information", which differs from SM-20's own wording.
- T-IDs do not follow section numbers: T-1.4.x is in §7.2, T-2.x in §7.3, T-3.x in §7.4, T-4.x in §7.5 and T-5.x in §7.6. T-1.4.5 does not exist.
- In some rows the Consequences text and the Violates column disagree (for example T-1.4.28). The UV caching threat refers to the UAF Registry for caching.

**Related documents:** `fido-authenticator-security-requirements` (normative requirements mapped to these SM/T IDs); `fido-authenticator-allowed-cryptography-list` (SM-16); `fido-metadata-service` (SM-4, SM-9, T-4.3.x); `fido-glossary` (terms); `fido-registry` (the effective-security notes refer to this document); `fido-uaf-protocol`, `fido-client-to-authenticator-protocol` and `webauthn` (the protocols analyzed).
