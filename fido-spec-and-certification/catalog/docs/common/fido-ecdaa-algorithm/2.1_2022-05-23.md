# FIDO ECDAA Algorithm

Version 2.1 · Proposed Standard · 2022-05-23 · [source](https://fidoalliance.org/specs/common-specs/fido-ecdaa-algorithm-v2.1-ps-20220523.html)

## Summary

Specifies FIDO ECDAA, an attestation scheme based on elliptic-curve Direct Anonymous Attestation with bilinear pairings over Barreto-Naehrig curves. It lets an authenticator prove its model without a shared or per-device certificate linking its registrations. An ECDAA Issuer, standing for the authenticator vendor and dedicated to one model, runs ECDAA-Join once with each authenticator to give it a credential (A, B, C, D). At registration the authenticator runs ECDAA-Sign over the key registration data and AppID, and the FIDO Server runs ECDAA-Verify with the issuer public key taken from metadata. The document defines byte encodings for big numbers and curve points, the global and issuer parameters, Join and Sign split between an authenticator and ASM or between a TPM and ASM, the verify procedure, the curves and algorithm names (ED256, ED256-2, ED512, ED638), the `ecdaaSignature` format, and notes on key sizes, revocation and performance.

ECDAA is relevant to UAF: UAF 1.2 defines an ECDAA attestation path, and the Registry keeps `ATTESTATION_ECDAA` (0x3E09). FIDO2/WebAuthn no longer use it: WebAuthn Levels 2 and 3 have no ECDAA attestation type.

**Who needs it:** authenticator vendors implementing UAF ECDAA attestation, FIDO server developers verifying it, labs

**Look here for:**
- Roles and the Join/Sign/Verify flow → §2.2 `#h3_architecture-overview`
- Issuer parameters and how one issuer key maps to one authenticator model → §3.3 `#h3_issuer-specific-ecdaa-parameters`
- Join and Sign steps split for a TPM → §3.4.3 `#h4_ecdaa-join-split-between-tpm-and-asm`, §3.5.3 `#h4_ecdaa-sign-split-between-tpm-and-asm`

**Changes from previous version:** Substantive. The scheme is now based on newer DAA work (CamDriLeh16 and CCDLNU2017) instead of the patched CheLi2013 construction. The Join flow changes: the issuer nonce step also returns issuer values (B, sc, yc), and the authenticator's second Join step takes only (A, C), since B and D are already known. The ECDAA Issuer's role as the vendor's per-model attester is spelled out, and the issuer public key identifier `c` is introduced. Other edits are terminology ("ECDAA Issuer") and typo fixes. This version follows the FIDO 2.0 ID of 2018, which is not catalogued.

## Reading guide

**Start here:** read §2.2 Architecture Overview `#h3_architecture-overview` for the roles and the four Join calls, §3.3 `#h3_issuer-specific-ecdaa-parameters` for the issuer key and its proof, and then §3.6 ECDAA-Verify `#h3_ecdaa-verify-operation`, which is what a FIDO server must implement. Suite: 2.1 is the common-specs version cited by the Registry 2.x (`ATTESTATION_ECDAA`). In practice ECDAA is a UAF attestation path. The text itself is protocol-neutral and works on the KRD and the AppID.

**Section by section:**
- §2 Overview `#h2_overview` (informative): ECDAA signs the registration's KRD. No basename is used, so registrations stay unlinkable per AppID. The ASM is assumed to run in the normal OS.
- §2.2 `#h3_architecture-overview`: Join happens once with an ECDAA Issuer (the vendor) before the first registration. After that the authenticator runs Sign and the server runs Verify. Join is normative only as far as interoperability needs. Sign, Verify and the signature encoding are fully normative.
- §3.1 Object Encodings `#h3_object-encodings`: `BigNumberToB` is I2OSP, right-aligned and zero-padded (`#h4_encoding-bignumber-values-as-byte-strings-bignumbertob`). `ECPointToB` is 0x04‖x‖y (`#h4_encoding-ecpoint-values-as-byte-strings-ecpointtob`). `ECPoint2ToB` is 0x04‖cx.a‖cx.b‖cy.a‖cy.b, with zero encoded as all zeros (`#h4_encoding-ecpoint2-values-as-byte-strings-ecpoint2tob`). Every hash input MUST use these encodings.
- §3.2 `#h3_global-ecdaa-system-parameters`: G1, G2, GT, generators P1 and P2, an ate pairing, and H mapping to Zp.
- §3.3 `#h3_issuer-specific-ecdaa-parameters`: the issuer secret isk=(x,y) and public key ipk=(X,Y,c,sx,sy) with a proof of correctness. Every party must verify the proof before first use. ipk MUST be dedicated to one authenticator model, and c is used as the issuer public key identifier.
- §3.4 ECDAA-Join `#h3_ecdaa-join` and §3.4.1 `#h4_ecdaa-join-algorithm` (normative):
  - The issuer derives B=(H(m), yc) from a nonce m.
  - The authenticator checks that B is on the curve, picks sk, sets Q=B^sk and proves possession (c1, s1, n).
  - The issuer checks Q ∈ G1 and the proof, and issues A=B^(1/y), C=(A·Q)^x, D=Q.
  - The authenticator checks A, C ∈ G1, A≠1, and both pairing equations.
  - In-factory and remote Join are both allowed. A remote Join must authenticate Q and refuse a second Join.
- §3.4.2 `#h4_ecdaa-join-split-between-authenticator-and-asm` and §3.4.3 `#h4_ecdaa-join-split-between-tpm-and-asm` (informative): the ASM does the pairing checks. The TPM variant uses EK certificates, TPM2_Commit/TPM2_Sign and TPM2_ActivateCredential, with required objectAttributes (fixedTPM=1, restricted=1, sign=1, …).
- §3.5.1 ECDAA-Sign `#h4_ecdaa-sign-algorithm` (normative): randomize the credential to R, S, T, W with l, compute U=S^r, c2=H(U|S|W|AppID|H(KRD)), c=H(n|c2), s=r+c·sk. The signature is (c, s, R, S, T, W, n).
- §3.5.2 `#h4_ecdaa-sign-split-between-authenticator-and-asm` and §3.5.3 `#h4_ecdaa-sign-split-between-tpm-and-asm` (informative): the ASM randomizes and the authenticator or TPM signs. Anonymity needs both sides to be honest. Unforgeability needs only the authenticator.
- §3.6 `#h3_ecdaa-verify-operation`:
  - Look up X, Y for the claimed AAID/AAGUID.
  - Check R, S, T, W ∈ G1 and R, S ≠ 1.
  - Check the hash equation and the pairing equations e(R,Y)=e(S,P2) and e(T,P2)=e(R·W,X).
  - Reject if W=S^sk' for any sk' on the RogueList.
  - For a TPM, also check TPMS_ATTEST for TPM_GENERATED and fixedTPM=1.
- §4.1 Supported Curves `#h3_supported-curves-for-ecdaa`: the BN curves TPM_ECC_BN_P256, TPM_ECC_BN_P638, ECC_BN_DSD_P256 and ECC_BN_ISOP512 with their parameters. H is SHA-256 or SHA-512 reduced mod p.
- §4.2 `#h3_ecdaa-algorithm-names`: ED256, ED256-2, ED512, ED638.
- §4.3 ecdaaSignature object `#h3_ecdaasignature-object`: the byte layout is c, s, n (N bytes each) followed by R, S, T, W (2N+1 bytes each), 356 bytes for 256-bit curves. Note that the wire order differs from the tuple order.
- §5 Considerations `#h2_considerations` (informative): one issuer key per model (`#h3_indicating-the-authenticator-model`), revocation by RogueList at verifiers and by the issuer's own means (`#h3_revocation`), pairing choice is local (`#h3_pairing-algorithm`), work split for performance (`#h3_performance`), plain concatenation is safe because AppID is followed by a fixed-length value (`#h3_binary-concatentation`), and the IANA JWS registration (`#h3_iana-considerations`).

**What matters most:**
- Verifiers must do the group-membership and non-identity checks before the pairings (§3.6 `#h3_ecdaa-verify-operation`).
- The issuer key is bound to one model. That binding is the only way the RP learns the model when the KRD cannot carry an AAGUID, as with TPMs (§3.3 `#h3_issuer-specific-ecdaa-parameters`, §5.2 `#h3_indicating-the-authenticator-model`).
- The randomizer l must be unguessable and unique. The text suggests hashing it with the AppID and a counter if the RNG is doubtful (§3.5.2 `#h4_ecdaa-sign-split-between-authenticator-and-asm`).
- Byte-exact encodings and field order decide interoperability (§3.1 `#h3_object-encodings`, §4.3 `#h3_ecdaasignature-object`).
- Join values should survive a factory reset (note in §3.4.2 `#h4_ecdaa-join-split-between-authenticator-and-asm`).

**Watch out for:**
- §4.1 says TPM_ECC_BN_P256 (that is, ED256) gives only about 96-bit security and should NOT be used any longer, yet ED256 is still defined and registered.
- §4.3 describes c2 as H(U|S|W|KRD|AppID), while §3.5.1 and §3.6 use H(U|S|W|AppID|H(KRD)). Follow the algorithm sections.
- §5.7 registers ED256, ED512 and ED638 with IANA, but not ED256-2.
- WebAuthn Levels 2 and 3 removed ECDAA, so this document only matters for UAF.

**Related documents:** `fido-registry` (`ATTESTATION_ECDAA` 0x3E09); `fido-uaf-protocol` and `fido-uaf-authnr-cmds` (KRD, `TAG_UAFV1_KRD`, ECDAA attestation handling); `fido-uaf-asm-api` (ASM split); `fido-metadata-statement` (where the ECDAA trust anchor for each model is published); `fido-security-ref` (SM-3 attestation, SM-20 privacy).
