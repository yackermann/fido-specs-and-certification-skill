# FIDO ECDAA Algorithm

Version 1.2 · Proposed Standard · 2017-04-11 · [source](https://fidoalliance.org/specs/fido-u2f-v1.2-ps-20170411/fido-ecdaa-algorithm-v1.2-ps-20170411.html)

## Summary

Copy of the FIDO ECDAA Algorithm shipped with the U2F 1.2 suite. ECDAA is a pairing-based Direct Anonymous Attestation scheme used for UAF attestation (U2F itself does not use it). This version describes the improved scheme based on CheLi2013 with security fixes for splitting signing between authenticator and ASM, and the Join, Sign and Verify algorithms, including TPM splits. Version 2.1 later rebased the scheme on newer DAA work and changed the Join flow. FIDO2/WebAuthn no longer use ECDAA.

**Who needs it:** UAF authenticator vendors and FIDO server developers working against the 2017 suites

**Look here for:**
- Join/Sign/Verify overview → §2.2 `#h3_architecture-overview`
- Join algorithm → §3.4.1 `#h4_ecdaa-join-algorithm`
- Verify operation → §3.6 `#h3_ecdaa-verify-operation`

**Changes from previous version:** Editorial only. A word-level comparison with 1.1 found no normative change; the extracted text differs only in how formulas are typeset, the header and reference links.

## Reading guide

**Use this version when:** you need to interoperate with ECDAA implementations built against the April 2017 suite (UAF 1.2 / U2F 1.2 bundle; U2F itself does not use ECDAA). It is not wire-compatible with 2.1. Suite: UAF 1.2 / U2F 1.2.

**Differences from 2.1 (latest):** substantive. These are different algorithms, not editorial changes.
- §3.4.1 Join `#h4_ecdaa-join-algorithm`:
  - The issuer sends only a nonce n.
  - The authenticator's key is Q=P1^sk, with proof c1=H(U1|P1|Q|n).
  - The issuer picks a random l_J and issues A=P1^l_J, B=A^y, C=A^x·Q^(x·y·l_J), D=Q^(l_J·y).
  - The issuer adds its own proof (c2, s2), which the authenticator verifies.
  - In 2.1, B is derived from H(m), Q=B^sk, D=Q, and there is no issuer proof.
- §3.5.1 Sign `#h4_ecdaa-sign-algorithm`: c=H(U|S|W|AppID|H(KRD)) directly, with no extra nonce. The signature is (c, s, R, S, T, W).
- §3.6 Verify `#h3_ecdaa-verify-operation`: checks c without n.
- §4.3 `#h3_ecdaasignature-object`: there is no `ECDAA_Signature_n` field, so the object is 324 bytes for 256-bit curves instead of 356.
- §3.3 `#h3_issuer-specific-ecdaa-parameters`: does not yet name c as the issuer public key identifier.
- §4.1 `#h3_supported-curves-for-ecdaa`: does not carry 2.1's warning that BN_P256 offers only about 96-bit security.
- The abstract bases the scheme on CheLi2013 with security fixes. 2.1 bases it on CamDriLeh16/CCDLNU2017.

**Differences from 1.1:** none in substance. Apart from formula typesetting and reference links, the text is identical.

**Section by section:** the same section structure and anchors as 2.1. Encodings (§3.1 `#h3_object-encodings`), curves and algorithm names (§4.2 `#h3_ecdaa-algorithm-names`: ED256, ED256-2, ED512, ED638), the RogueList revocation and the TPM checks match 2.1. See the 2.1 page's reading guide for those.
