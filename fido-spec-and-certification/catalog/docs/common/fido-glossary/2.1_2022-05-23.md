# FIDO Technical Glossary

Version 2.1 · Proposed Standard · 2022-05-23 · [source](https://fidoalliance.org/specs/common-specs/fido-glossary-v2.1-ps-20220523.html)

## Summary

The FIDO Alliance glossary of normative technical terms, shared by UAF, U2F, FIDO2 (CTAP/WebAuthn) and the certification documents. It is one alphabetical definitions chapter and does not try to cover every term: well-known terms are left to the referenced external glossaries. Entries cover protocol actors (FIDO Client, FIDO Server, ASM, Relying Party, RP ID), authenticator properties (AAGUID/AAID, attestation key, attestation types including ECDAA, user verification, user presence, key protection, matcher), execution environments used in security certification (Restricted, Allowed Restricted and Rich Operating Environments, TEE, Secure Element, trusted path, side-channel attack, Authenticator Security Parameter, security strength), and metadata (Metadata Statement, Metadata Service).

Use it when another FIDO specification or the Authenticator Security Requirements use a capitalized term without defining it. The other common specifications and the UAF, U2F and FIDO2 documents reference it normatively.

**Who needs it:** everyone reading FIDO specifications; certification applicants and labs in particular (security certification terms such as AROE and ASP)

**Look here for:**
- Definition of a FIDO term (AAGUID, ASM, attestation, user verification, …) → §3 `#h2_definitions`
- Security-certification terms (ROE/AROE, TEE, SE, ASP, security strength) → §3 `#h2_definitions`
- Enterprise attestation modes (vendor-facilitated vs platform-managed) → §3 `#h2_definitions`
- Scope of the glossary and where other terms come from → §2 `#h2_introduction`, A `#h2_references`

**Changes from previous version:** Substantive growth (about 30% longer). New entries include AAGUID, Relying Party Identifier / RP ID, Credential, ECDAA, Enterprise Attestation (EA mode 1 and 2), Metadata Statement and Metadata Service, Authenticator Model, Authenticator Security Parameter, Security Strength, Restricted / Allowed Restricted / Rich Operating Environment, Trusted Execution Environment, Secure Element, Trusted Path, Side Channel Attack, Revision Control System and Test of User Presence. "UAF Protocol Version" becomes "Unified Protocol Version", and several existing entries were reworded.

## Reading guide

**Start here:** §2 Introduction `#h2_introduction` says the glossary is deliberately incomplete and leaves well-known terms to the referenced sources. After that, everything is in §3 Definitions `#h2_definitions`, a single alphabetical list, so search it for the term you need. Suite: 2.1 belongs with the 2022 common specs and serves FIDO2/CTAP, WebAuthn-related and certification documents, as well as UAF 1.2. Most entries still use UAF wording.

**Section by section:**
- §1 Notation `#h2_notation` and §1.1 Key Words `#h3_key-words`: boilerplate. The glossary defines vocabulary and imposes no requirements of its own.
- §3 Definitions `#h2_definitions`. Useful clusters:
  - *Identity and model:* AAID (UAF) vs AAGUID (FIDO2), Authenticator Model (same AAID/AAGUID, or a shared `attestationCertificateKeyIdentifier`), Attestation, Attestation Root Certificate, Enterprise Attestation (EA mode 1 is vendor-facilitated with a fixed RP ID list; EA mode 2 is platform-managed through local policy).
  - *Actors:* FIDO Client, FIDO Server (worded as a UAF server), ASM, Relying Party, RP ID (taken from WebAuthn), User Agent, FIDO User Device.
  - *Authenticator types:* first-factor (needs an internal matcher; presence-only devices do not qualify), second-factor (always needs a key handle), bound vs roaming, silent.
  - *Presence vs verification:* User Presence Check needs an explicit, conscious gesture, and passive biometrics do not count. User Verification identifies a particular user by PIN, password or biometric.
  - *Security-certification terms:* ROE, AROE (approved by FIDO via the AROE list), REE, TEE, Secure Element, tamper-resistant secure hardware (tied to PP0084), Trusted Path, ASP (Authenticator Security Parameter), Security Strength (bits; for an RNG, the number of random bits drawn), side-channel attack.
  - *UAF data objects:* KRD, SignedData, KeyHandle, KeyID, KHAccessToken, UAuth.pub/priv, Sign Counter, PersonaID, TLV, UINT8/16/32.
  - *Scoping:* AppID, Application Facet, Facet ID, TrustedFacets.
- A References `#h2_references`: where the externally defined terms come from (RFC 4949, ISO biometrics, GlobalPlatform, WebAuthn).

**What matters most:**
- Keep user presence separate from user verification. Certification and the Registry's `USER_VERIFY_PRESENCE_INTERNAL` both depend on this distinction (§3 `#h2_definitions`).
- AROE, ROE, ASP, Trusted Path and Security Strength are the terms the Authenticator Security Requirements build on. Use these definitions when you answer a vendor questionnaire (§3 `#h2_definitions`).
- "Authenticator Model" and "first-factor authenticator" carry real constraints: the AAID/AAGUID scope, and the rule that a presence-only device is never first-factor (§3 `#h2_definitions`).

**Watch out for:**
- The Abstract is wrong: it describes the Registry of constants ("strings and constants reserved by UAF protocols"), not a glossary.
- The Application Facet ID entry lists only the SHA-1 `android:apk-key-hash:` form. AppID & Facets 2.1 also defines `android:apk-key-hash-sha256:`.
- Many entries (FIDO Server, Metadata Statement, Server Challenge, Step-up Authentication) still describe UAF/U2F only. Passkey or sync terms are not here.
- "Unified Protocol Version" replaces 1.x's "UAF Protocol Version" for UPV.

**Related documents:** `fido-registry` (the constants behind several terms); `fido-security-ref` (threats and measures that use these terms); `fido-authenticator-security-requirements` and `fido-authenticator-allowed-restricted-operating-environments-list` (AROE, ASP); `fido-appid-and-facets` (AppID and facets); `webauthn` (RP ID and the authoritative WebAuthn terminology).
