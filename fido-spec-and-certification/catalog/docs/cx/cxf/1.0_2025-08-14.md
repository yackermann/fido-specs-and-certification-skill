# Credential Exchange Format

Version 1.0 · Proposed Standard · 2025-08-14 · [source](https://fidoalliance.org/specs/cx/cxf-v1.0-ps-20250814.html)

## Summary

Credential Exchange Format 1.0 (August 2025) is the first Proposed Standard of the JSON/CDDL data model for exporting and importing credentials between providers. It covers accounts, collections and items holding passkeys, passwords, TOTP, keys, payment cards, identity documents and more. It does not specify transport; the Credential Exchange Protocol (CXP) does that. A 2026-03-09 errata edition supersedes it. That edition changes only the Appendix A example payload and one reference. CXF has no FIDO certification program.

**Who needs it:** credential provider and platform developers implementing credential import/export

**Look here for:**
- Credential data types → §3.3 `#sctn-credential-data-types`
- Passkey dictionary → §3.3.12 `#dict-passkey`
- Validating received files → §5.2 `#sctn-validation-of-files`
- Example payload (corrected in the errata edition) → Appendix A `#appendix-a`

## Reading guide

**Use this version when:** you need to cite the original August 2025 Proposed Standard, for example in a product statement written before March 2026. For implementation use the 1.0-errata edition: both declare format version 1.0 (§3.1.1 `#dict-version`), so payloads are the same format, and the normative text is identical.

**Differences from 1.0-errata (2026-03-09):** a full-text comparison shows changes only in Appendix A `#appendix-a` and in one reference entry (the WebAuthn Level 3 editor name). Several sample values in this edition contradict the normative sections, which is why it should not be used as a test vector:
- The passkey sample uses `hmacSecret` with `HS256` and a single `secret`, where §3.3.12.2 `#dict-fido2-extensions` and §3.3.12.3 `#dict-fido2-hmac-credentials` define `hmacCredentials` with `credWithUV`, `credWithoutUV` and the algorithm `hmac-sha256` (§3.3.12.4 `#enum-fido2-hmac-credential-algorithm`). The errata sample also adds `credBlob`, `largeBlob` and `payments`.
- The Wi-Fi sample uses `WPA2`, not a value of `WIFINetworkSecurityType` (§3.3.17.1 `#dict-wifi-network-security-type`, `wpa2-personal`).
- Territory samples use `CA`, not an ISO 3166-2 subdivision code as `subdivision-code` requires (§3.4.3 `#enum-field-type`); the errata uses `US-CA`.
- An `expiryDate` EditableField carries `"extensions": []`, which breaks the rule that empty optional arrays are omitted (§2.1.2 `#sctn-array-encoding`) and the non-empty `[ + Extension ]` type in §3.4.2 `#dict-editable-field`.
- The File sample's `integrityHash` is placeholder text rather than a SHA-256 of a stated file (§3.3.7 `#dict-file`, §5.2 `#sctn-validation-of-files`); the errata gives the file content and its real hash.
- Smaller value changes (TOTP issuer, passport type, a timestamp) have no normative effect.

**Section by section:** structure and normative content as in cxf 1.0-errata; see that page's reading guide.
