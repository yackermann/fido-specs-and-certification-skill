# Credential Exchange Format

Version 1.0 · Proposed Standard (errata edition) · 2026-03-09 · [source](https://fidoalliance.org/specs/cx/cxf-v1.0-ps-errata-20260309.html)

## Summary

The Credential Exchange Format (CXF) 1.0 defines a JSON data model for moving a user's credentials between credential providers, such as password managers and passkey providers. Each export is a header plus accounts, which contain collections and items. Each item carries typed credentials: passkeys, basic auth (username/password), TOTP, API keys, SSH keys, credit cards, identity documents, passports, driver's licenses, Wi-Fi passphrases, notes, files, custom fields and more. Types are given in CDDL. Binary values are base64url. Unknown enumeration values must be tolerated so the format can be extended, and IANA registries cover credential types and extensions. CXF does not define the transport. The companion Credential Exchange Protocol (CXP) does that. CXF also sets rules for an orchestrating party that relays data without implementing CXP. The CX specifications have no FIDO certification program.

This errata edition has no change log. A text comparison with the 2025-08-14 edition shows that the normative sections are unchanged. The corrections are in the Appendix A example payload: the passkey example now uses `hmacCredentials`, `credBlob`, `largeBlob` and `payments` in place of `hmacSecret`, and enumeration values were fixed (`wpa2-personal`, `US-CA`). The File example was also corrected, and one reference was updated.

**Who needs it:** credential provider (password manager / passkey provider) developers, platform vendors implementing import/export

**Look here for:**
- Account / Collection / Item structure → §3.2 `#sctn-entity-data-types`
- Passkey export fields → §3.3.12 `#dict-passkey`
- Handling unknown enum values and JSON encoding → §2.1 `#sctn-encoding-considerations`
- Rules for orchestrating parties without CXP → §5.1 `#sctn-orchestrating-party-requirements`
- A complete example export → Appendix A `#appendix-a`

**Changes from previous version:** Editorial and example-only. The Appendix A sample payload was corrected (passkey extension fields, enumeration values, File item), and a WebAuthn reference was updated. No normative changes were found when the texts were compared.

## Reading guide

**Start here:** §1.3 `#sctn-terminology` (exporting / importing provider, orchestrating party, identifier rules), §2.1 `#sctn-encoding-considerations` with §2.1.1 `#sctn-enumerations-as-recommended` and §2.1.2 `#sctn-array-encoding` (the parsing rules that govern everything else), then the Header → Account → Collection / Item tree in §3.1 `#dict-header` and §3.2 `#sctn-entity-data-types`. Passkey implementers go straight on to §3.3.12 `#dict-passkey`.

**Section by section:**
- §1 `#sctn-intro` (§1.1 `#sctn-motivation`, §1.2 `#sctn-scope`): CXF is only the data model; it assumes no transport. CXP is the preferred transfer protocol (SHOULD), and any transfer protocol MUST keep the data confidential between providers. Identifiers are at most 64 bytes, unique per exchanged Account, SHOULD carry no personal data (they travel in clear in CXP), and SHOULD stay stable across exports.
- §2.1 `#sctn-encoding-considerations`: types in CDDL, MUST be encodable as JSON; `b64url` is RFC 4648 URL-safe base64 in a JSON string, and byte lengths refer to the decoded bytes.
- §2.1.1 `#sctn-enumerations-as-recommended`: enums are open strings. An unknown value in an optional member SHOULD make the importer ignore that member; in a required member, the enclosing structure, cascading upward to the nearest optional parent, and abort if nothing usable is left.
- §2.1.2 `#sctn-array-encoding`: required arrays MUST appear even when empty; optional arrays MUST be omitted when empty.
- §3.1 `#dict-header`, §3.1.1 `#dict-version`: `version` {major 1, minor 0}, `exporterRpId`, `exporterDisplayName`, `timestamp`, `accounts`. Participants MUST ignore unknown fields and enum values; new optional fields and enum values are not breaking changes.
- §3.2.1 `#entity-account`: `id`, `username` (empty string if none), `email`, `collections`, `items`; collections and items shared to this account by others MUST NOT be listed.
- §3.2.2 `#entity-collection`, §3.2.2.1 `#dict-linked-item`: nested collections that reference items by `LinkedItem` (item id plus optional owning account id); the referenced item may not be in the export.
- §3.2.3 `#entity-item`, §3.2.4 `#dict-credential-scope`, §3.2.4.1 `#dict-android-app-id`: an Item groups related credentials with optional `scope` (URLs and Android apps with certificate fingerprint), `tags`, `favorite`, timestamps (importer SHOULD substitute the current time when missing).
- §3.3 `#sctn-credential-data-types`: every credential has a `type`; importers MAY split credential combinations they cannot store into separate items and MAY store unknown types as best effort. Types: §3.3.1 `#dict-address`, §3.3.2 `#dict-api-key`, §3.3.3 `#dict-basic-auth` (SHOULD come with a scope), §3.3.4 `#dict-credit-card`, §3.3.5 `#dict-custom-fields`, §3.3.6 `#dict-drivers-license`, §3.3.7 `#dict-file` (metadata plus SHA-256 `integrityHash`; the bytes come through the transfer protocol), §3.3.8 `#dict-generated-password`, §3.3.9 `#dict-identity-document`, §3.3.10 `#dict-item-reference`, §3.3.11 `#dict-note`, §3.3.13 `#dict-passport`, §3.3.14 `#dict-person-name` (exporters SHOULD NOT split names themselves), §3.3.15 `#dict-ssh-key` (PKCS#8 DER private key, IANA SSH algorithm name), §3.3.16 `#dict-totp` (Base32 secret, period, digits, algorithm; §3.3.16.1 `#enum-otp-hash-algorithm`), §3.3.17 `#dict-wifi` with §3.3.17.1 `#dict-wifi-network-security-type`.
- §3.3.12 `#dict-passkey`: `credentialId`, `rpId`, `username`, `userDisplayName`, `userHandle` and `key` (PKCS#8 DER, MUST yield the originally registered public key), all MUST match the registration values except the two user-editable names (§3.3.12.1 `#sctn-editability-of-passkey-fields`). The item's CredentialScope MUST NOT apply to passkeys; only the `rpId` does.
- §3.3.12.2–§3.3.12.5 `#dict-fido2-extensions`, `#dict-fido2-hmac-credentials`, `#enum-fido2-hmac-credential-algorithm`, `#dict-fido2-large-blob`: `hmacCredentials` (one seed pair serves both `prf` and `hmac-secret`: `credWithUV`, `credWithoutUV`, `hmac-sha256`), `credBlob`, `largeBlob` (DEFLATE data plus `uncompressedSize`), `payments`.
- §3.4 `#sctn-supporting-data-structures`: `CredentialType` (§3.4.1 `#enum-credential-type`), `EditableField<F>` (§3.4.2 `#dict-editable-field`: `fieldType`, string `value`, optional `id`, `label`, `extensions`) and `FieldType` (§3.4.3 `#enum-field-type`: date formats, ISO 3166 country and subdivision codes, `"true"`/`"false"` booleans).
- §3.5 `#sctn-defined-extensions`: extensions are named; custom ones MUST be `EXPORTER_RP_ID/NAME`. §3.5.1 `#sctn-sharing-an-entity` defines `shared` for Collections and Items only, with accessors (§3.5.1.1 `#dict-sharing-accessor`), `user` / `group` types (§3.5.1.2 `#enum-sharing-accessor-type`) and permissions (§3.5.1.3 `#enum-sharing-accessor-permission`); importers MUST drop accessors with unknown type or an empty permission list.
- §4 `#sctn-iana-considerations` (§4.1 `#sctn-iana-credential-types-registry`, §4.2 `#sctn-iana-extension-registry`): requested registries for credential types and extensions, seeded from this document.
- §5 `#sctn-security-considerations`: an orchestrating party MAY use CXF without CXP but MUST then publish documentation (§5.1 `#sctn-orchestrating-party-requirements`, §5.1.1 `#sctn-documentation-requirements`) stating it only relays, does not persist or reuse, and does not alter the data. Importers MUST reject a file whose hash does not match (§5.2 `#sctn-validation-of-files`).
- Appendix A `#appendix-a`: a full export with every credential type; informative.

**What matters most:**
- Passkey counters: passkeys with a non-zero signature counter MUST be left out of the export (the exporter SHOULD tell the user), and importers MUST set the counter to zero and never increment it (§3.3.12 `#dict-passkey`). This decides which credentials are exportable at all.
- Exact preservation of WebAuthn values (`credentialId` equal to the original rawId, `userHandle`, `rpId`, key material) (§3.3.12 `#dict-passkey`), and HMAC seeds stored and used as-is with no extra derivation, identical across every importer; an exporter supporting only one of prf / hmac-secret MUST generate the missing seed once and keep it stable (§3.3.12.3 `#dict-fido2-hmac-credentials`). The document stresses this because these extensions are mainly used for encryption.
- Tolerant import: unknown enum values, field types, TOTP algorithms, HMAC algorithms and sharing entries are dropped rather than failing the whole import (§2.1.1 `#sctn-enumerations-as-recommended`, §3.4.2 `#dict-editable-field`, §3.3.16 `#dict-totp`).
- Array presence rules (§2.1.2 `#sctn-array-encoding`) and ownership rules for shared data (§3.2.1 `#entity-account`, §3.5.1 `#sctn-sharing-an-entity`) are easy to get wrong when serializing.
- Confidentiality is delegated: CXF has no encryption of its own, so the transfer protocol or a documented orchestrator carries that obligation (§1.3 `#sctn-terminology`, §5.1 `#sctn-orchestrating-party-requirements`).

**Watch out for:**
- The passkey counter rule sits in a Note, and the Conformance `#conformance` section declares notes informative, yet it uses MUST. Treat it as binding.
- Requirement words are not always upper case (Conformance `#conformance`), so lower-case "must" can still be normative.
- The `Extension` CDDL in §3.5 `#sctn-defined-extensions` still contains an open editorial question as a comment, and `WIFINetworkSecurityType` (§3.3.17.1 `#dict-wifi-network-security-type`) is written with map braces instead of a plain choice; validate against the prose, not only the CDDL.
- TOTP `secret` is a Base32 string, not `b64url` like other binary values (§3.3.16 `#dict-totp`).
- The IANA registries in §4 `#sctn-iana-considerations` are described as requested, not established.
- This errata edition fixes only Appendix A `#appendix-a` (and one reference); the normative sections match the August 2025 text. No FIDO certification program covers CXF.

**Related documents:** cxf 1.0 (earlier edition, same normative text but an example that contradicts it), webauthn (passkey fields, `prf`, `largeBlob`, signature counter semantics), fido-client-to-authenticator-protocol (`hmac-secret`, `credBlob`), fido-metadata-statement 3.1.1 (`cxConfigURL`, credential exchange configuration of a passkey provider). The Credential Exchange Protocol (CXP), which carries this format, is not in this catalog.
