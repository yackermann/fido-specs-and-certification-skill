# Web Authentication: An API for accessing Public Key Credentials - Level 3

Version 3 · W3C Recommendation · 2026-08-25 · **current W3C Recommendation** · [source](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/)

## Summary

Web Authentication Level 3 is the current W3C Recommendation (2026-08-25) for the browser API that lets web applications create and use scoped public key credentials (passkeys) to authenticate users. It defines the PublicKeyCredential interface and the create/get algorithms, and it covers JSON serialization helpers, client capabilities, signal methods, conditional mediation, cross-origin iframes and related origins. It also specifies the authenticator model (authenticator data, backup-eligible and backup-state flags, attestation), the relying-party procedures for verifying registrations and assertions, the attestation statement formats, the client and authenticator extensions, WebDriver automation, and test vectors. CTAP 2.x is the companion protocol that carries these operations to external authenticators. FIDO server certification checks relying-party behaviour against the verification procedures in §7.

**Who needs it:** relying parties & server developers, platform & client (browser) developers, authenticator vendors (authenticator data, attestation formats), labs using the test vectors

**Look here for:**
- How an RP verifies a new credential → §7.1 `#sctn-registering-a-new-credential`
- How an RP verifies an authentication assertion → §7.2 `#sctn-verifying-assertion`
- Meaning of the BE/BS backup flags → §6.1.3 `#sctn-credential-backup`
- Attestation statement formats, including compound → §8 `#sctn-defined-attestation-formats`
- Sample attestation objects for testing → §16 `#sctn-test-vectors`
- Full list of changes since Level 2 → §18.1 `#changes-since-l2`

**Changes from previous version:** New: JSON methods (toJSON, parseCreationOptionsFromJSON, parseRequestOptionsFromJSON), getClientCapabilities, signal methods, and conditional mediation for both create and get. Credential creation is now allowed in cross-origin iframes, and related origins (via a well-known URI) are supported. Also new: the `topOrigin` client data field, the `hybrid` transport value, user-agent hints, the BE/BS authenticator data flags, the compound attestation format, the prf extension, the attestationFormats registration parameter, and test vectors. Removed: the uvm extension. Deprecated: Android SafetyNet attestation and `rp.name` (still a required member; RPs may set it to the RP ID); in-field language metadata is no longer recommended. tokenBinding is now reserved. aaguid is no longer zeroed when attestation is `none`.

## Reading guide

**Start here:** §2 Conformance `#sctn-conformance` for the three conformance classes (user agents follow §5, authenticators §6, RPs §7) and the rule that all CBOR uses the CTAP2 canonical form. Then §7.1 `#sctn-registering-a-new-credential` and §7.2 `#sctn-verifying-assertion`, the RP procedures that server work and FIDO server testing revolve around. Then §6.1 `#sctn-authenticator-data` for the byte layout every verifier parses. Keep §4 Terminology `#sctn-terminology` open for defined terms such as credential record, RP ID and discoverable credential.

**Section by section:**
- §1 Introduction `#sctn-intro`: use cases (consumer multi-device, workforce single-device) and sample JavaScript in §1.3 `#sctn-sample-scenarios`. Informative.
- §5.1 PublicKeyCredential `#iface-pkcredential`: `id`/`rawId`, `authenticatorAttachment`, `getClientExtensionResults()`, `isConditionalMediationAvailable()` (covers get only) and `toJSON()`. toJSON base64url-encodes every ArrayBuffer and MUST fill `transports`, `publicKey` and `publicKeyAlgorithm` from the getters.
- §5.1.3 `#sctn-createCredential` (create): the client algorithm. `user.id` must be 1–64 bytes or the call fails with TypeError. If `rp.id` is not the effective domain or a registrable suffix of it, the client falls back to the related-origins check, and fails with SecurityError if that is unsupported or fails. Empty `pubKeyCredParams` defaults to ES256 and RS256. Cross-origin iframes need transient activation and cannot use conditional create. With conditional mediation the client sets both UP and UV requirements to false unless it can actually collect them. A required UV that cannot be collected gives ConstraintError. With `attestation` = `none`, fmt/attStmt become `none` (self attestation is kept), but the AAGUID now passes through. InvalidStateError for an excluded credential is returned only after the user consents. §5.1.3.1 `#sctn-create-request-exceptions` is an informative table of errors.
- §5.1.4 `#sctn-getAssertion`, §5.1.4.1 `#sctn-discover-from-external-source`, §5.1.4.2 `#sctn-issuing-cred-request-to-authenticator` (get): with conditional mediation, `allowCredentials` becomes a filter only and is emptied (so only discoverable credentials can be used), and the timer is infinite. Credentials surface through an input field carrying the `webauthn` autocomplete token, with optional silentCredentialDiscovery (§6.3.5 `#sctn-op-silent-discovery`). A response that has neither a filter match nor a user handle is dropped. The effective UV requirement is worked out per authenticator. Errors: §5.1.4.3 `#sctn-get-request-exceptions` (informative).
- §5.1.6–§5.1.9 (`#sctn-isUserVerifyingPlatformAuthenticatorAvailable`, `#sctn-getClientCapabilities`, `#sctn-parseCreationOptionsFromJSON`, `#sctn-parseRequestOptionsFromJSON`): getClientCapabilities returns a sorted record of the §5.8.7 `#enum-clientCapability` values plus `extension:<id>` keys. A missing key means unknown, not false. The parse methods turn the JSON option forms back into binary and MUST throw EncodingError on bad input.
- §5.1.10 Signal methods `#sctn-signal-methods`: signalUnknownCredential, signalAllAcceptedCredentials and signalCurrentUserDetails. The promise only reports that the input was well formed, never whether anything changed. Authenticators may hide or delete credentials and may deviate from the recommended actions. RP IDs are validated asynchronously (§5.1.10.1 `#sctn-signal-methods-async-rp-id-validation`).
- §5.4 Creation options `#dictionary-makecredentialoptions` with §5.4.1–§5.4.7: `rp.name` is deprecated but still required. The user handle MUST NOT be empty or contain PII. `pubKeyCredParams` SHOULD include -8, -7 and -257, and the fully-specified -9/-51/-52/-19 are NOT RECOMMENDED there. `excludeCredentials`, `hints`, `attestation` (default none) and the advisory `attestationFormats` are defined here. residentKey `preferred` takes precedence over the UV setting. `enterprise` attestation is given only when the UA or authenticator configuration permits it for that RP ID.
- §5.5 Request options `#dictionary-assertion-options`: rpId, the ordered `allowCredentials` (an empty list means discoverable-only), `userVerification` (default preferred) and `hints`.
- §5.8 Supporting data `#sctn-supporting-data-structures`: CollectedClientData (§5.8.1 `#dictionary-client-data`) with `topOrigin`, and `tokenBinding` now [RESERVED]. The fixed serialization and the limited verification algorithm are in §5.8.1.1 `#clientdatajson-serialization` and §5.8.1.2 `#clientdatajson-verification`. Transports (§5.8.4 `#enum-transport`) add `hybrid` and `smart-card`. COSE key constraints (§5.8.5 `#sctn-alg-identifier`): ES256 MUST use P-256 and EC keys MUST NOT use compressed points. Hints (§5.8.8 `#enum-hints`) are listed in order of preference and override transports and authenticatorAttachment.
- §5.9–§5.11 (`#sctn-permissions-policy`, `#sctn-iframe-guidance`, `#sctn-related-origins`): the `publickey-credentials-create`/`-get` policies (default 'self') and the iframe `allow` attribute. Related origins use a JSON `origins` list served over HTTPS at `/.well-known/webauthn` for the RP ID. Clients MUST support at least five registrable origin labels. The validation procedure is in §5.11.1 `#sctn-validating-relation-origin`.
- §6.1 Authenticator data `#sctn-authenticator-data`: rpIdHash(32) | flags(1) | signCount(4) | attested credential data | extensions. The flag bits are UP=0, UV=2, BE=3, BS=4, AT=6 and ED=7. BE is set if and only if the credential is multi-device and MUST NOT change afterwards. BS SHOULD be clear when the backup state is uncertain. AT MUST NOT appear in assertions. Counters (§6.1.1 `#sctn-sign-counter`) SHOULD be per credential. U2F signature compatibility is in §6.1.2 `#sctn-fido-u2f-sig-format-compat`. The valid BE/BS combinations (0/1 is invalid) and RP uses for them are in §6.1.3 `#sctn-credential-backup`.
- §6.2 Taxonomy `#sctn-authenticator-taxonomy`: attachment, storage modality and factor capability, including the passkey platform and passkey roaming authenticator types.
- §6.3 Operations `#sctn-authenticator-ops`: the abstract authenticatorMakeCredential (§6.3.2 `#sctn-op-make-cred`) and authenticatorGetAssertion (§6.3.3 `#sctn-op-get-assertion`) map onto CTAP. They cover exclude-list handling with a UP gesture, ConstraintError cases, choosing the first supported entry of attestationFormats, counter increments, and returning the credential ID only when the allow list was empty or had at least two entries.
- §6.4 Strings `#sctn-strings`: truncation rules for clients (MUST respect code points, §6.4.1.1 `#sctn-strings-truncation-client`) and the looser rules for authenticators. In-field language and direction encoding is NOT RECOMMENDED (§6.4.2 `#sctn-strings-langdir`).
- §6.5 Attestation `#sctn-attestation`: attested credential data (§6.5.1 `#sctn-attested-credential-data`) is AAGUID(16) | length(2, value ≤1023) | credentialId | COSE key (which MUST contain `alg` and no other optional parameters). Attestation types Basic, Self, AttCA, AnonCA and None are in §6.5.3 `#sctn-attestation-types`. The attObj CBOR map is in §6.5.4 `#sctn-generating-an-attestation-object`. Signature encodings (ECDSA uses DER, RS256/PS256 use raw bytes) are in §6.5.5 `#sctn-signature-attestation-types`.
- §7.1 Registration `#sctn-registering-a-new-credential`, in step order: check type `webauthn.create`, then the challenge, then the origin, then crossOrigin/topOrigin when present. Hash clientDataJSON and decode the attestationObject. Check rpIdHash. Require UP unless mediation was conditional, and UV if your policy needs it. Reject BS without BE, then apply your BE/BS policy. Check that `alg` is one of those you offered. Run the fmt verification procedure (step 22), get trust anchors (for example from MDS via AAGUID, step 23), and assess trust (step 24). Reject credential IDs over 1023 bytes and IDs already registered to any user. Build the credential record, then process the extensions.
- §7.2 Authentication `#sctn-verifying-assertion`: check that the ID is in allowCredentials, then resolve the credential record by rawId and userHandle (userHandle is required if the user was not identified beforehand). Check type `webauthn.get`, then the challenge, origin, crossOrigin and topOrigin, then rpIdHash (the appid hash is allowed when the appid extension applies). UP is always required. UV is enforced only if required and otherwise ignored. Check BE/BS consistency with the stored record, then verify the signature over authData‖SHA-256(clientDataJSON). Evaluate the counter (RP decides), then update signCount, backupState and uvInitialized (changing uvInitialized SHOULD need an extra factor).
- §8 Attestation formats `#sctn-defined-attestation-formats`: format IDs are case-sensitive, at most 32 octets (§8.1 `#sctn-attstn-fmt-ids`). Packed (§8.2 `#sctn-packed-attestation`, Basic/Self/AttCA) has certificate rules in §8.2.1 `#sctn-packed-attestation-cert-requirements`: OU must be "Authenticator Attestation", the aaguid extension 1.3.6.1.4.1.45724.1.1.4 is required when a root serves several models, and CA must be false. Enterprise serial-number rules are in §8.2.2 `#sctn-enterprise-packed-attestation-cert-requirements`. TPM (§8.3 `#sctn-tpm-attestation`, AttCA) checks pubArea and certInfo. Android Key (§8.4 `#sctn-android-key-attestation`) checks attestationChallenge and the authorization lists. SafetyNet (§8.5 `#sctn-android-safetynet-attestation`) is deprecated. FIDO U2F (§8.6 `#sctn-fido-u2f-attestation`) requires a P-256 key and rebuilds the U2F signed data. None is §8.7 `#sctn-none-attestation`. Apple (§8.8 `#sctn-apple-anonymous-attestation`) is AnonCA and checks a nonce in OID 1.2.840.113635.100.8.2. Compound (§8.9 `#sctn-compound-attestation`) holds an array of at least two non-compound statements, and RP policy decides how many must verify.
- §9 Extension framework `#sctn-extensions`: client vs authenticator extensions and identifier rules (§9.1 `#sctn-extension-id`). All extensions are OPTIONAL, and RPs MUST cope with ignored or unsolicited ones.
- §10 Defined extensions `#sctn-defined-extensions`: appid (§10.1.1 `#sctn-appid-extension`) and appidExclude (§10.1.2 `#sctn-appid-exclude-extension`) for U2F migration. credProps (§10.1.3 `#sctn-authenticator-credential-properties-extension`): a missing `rk` most likely means non-discoverable. prf (§10.1.4 `#prf-extension`) runs on hmac-secret using the UV PRF and context-hashed salts, with `evalByCredential` only allowed when allowCredentials is non-empty. largeBlob is §10.1.5 `#sctn-large-blob-extension`. §10.2 `#sctn-defined-authenticator-extensions` is empty.
- §11 WebDriver automation `#sctn-automation`: virtual authenticators for testing. Set Credential Properties (§11.10 `#sctn-automation-set-credential-properties`) can flip BE/BS.
- §12 IANA `#sctn-IANA`: registry updates for formats and extensions, and the `webauthn` well-known URI (§12.5 `#sctn-well-known-uri-reg`).
- §13 Security `#sctn-security-considerations` and §14 Privacy `#sctn-privacy-considerations`: covered below. §15.1 `#sctn-timeout-recommended-range` recommends timeouts of 5–10 minutes, with 5 minutes as the default.
- §16 Test vectors `#sctn-test-vectors` (informative): deterministic registration and authentication pairs for none, self, packed (ES256/384/512, RS256, Ed25519, Ed448), TPM, Android Key, Apple and U2F, plus crossOrigin, topOrigin, long-credential-ID and prf/hmac-secret cases. They use RP ID example.org.
- §18.1 Changes since L2 `#changes-since-l2`: the authoritative change list.

**What matters most:**
- Origin and topOrigin validation are MUSTs. Exact matching is the safe default, and a subdomain origin SHOULD NOT be allowed by default (§13.4.9 `#sctn-validating-origin`, §13.4.8 `#sctn-code-injection`).
- Challenges MUST be random and generated server-side, SHOULD be at least 16 bytes, and SHOULD be stored rather than trusted from the client (§13.4.3 `#sctn-cryptographic-challenges`).
- The UP rule differs by ceremony. Registration skips it only for conditional create, while assertions always require it. UV is enforced only when the RP asked for it (§7.1, §7.2).
- Attestation trust is RP policy. Under `none` the AAGUID now arrives, but no attestation statement backs it. Keep intermediate CA certificates so you can un-register credentials after a CA revocation (§13.4.5 `#sctn-revoked-attestation-certificates`).
- Duplicate credential IDs: L3 says SHOULD fail when the ID is registered to any user (the rationale is the victim-takeover attack described in §7.1).
- User handle: no PII, not even unsalted hashes. 64 random bytes are RECOMMENDED (§14.6.1 `#sctn-user-handle-privacy`).
- Sending allowCredentials to unauthenticated callers leaks information (§14.6.3 `#sctn-credential-id-privacy-leak`, §13.4.7 `#sctn-unprotected-account-detection`). Use signalUnknownCredential, not signalAllAcceptedCredentials, in that situation.

**Watch out for:**
- Only `rp.name` is marked deprecated in the text (§5.4.1 `#dictionary-pkcredentialentity`). `user.name` and `user.displayName` are still REQUIRED; what is no longer recommended for them is the in-field language and direction metadata. The Summary's deprecation list reads more broadly than that.
- Informative sections that look normative: the error tables (§5.1.3.1, §5.1.4.3), §13.4.4 `#sctn-attestation-limitations`, §13.4.7 and §16.
- signalAllAcceptedCredentials may remove credentials irreversibly when a valid ID is left out of the list.
- prf `results` are included in toJSON output. Strip them if PRF outputs are meant to stay on the client.
- getPublicKey() is guaranteed only for -7, -257 and -8 (Ed25519) (§5.2.1.1 `#sctn-public-key-easy`). For other algorithms, parse the COSE key from authData.
- §12 contains no registration entries for `compound` or `prf`. Check the IANA registry itself.
- Android SafetyNet is deprecated here but is still a MUST in fido-server-requirements 2.3.

**Related documents:** fido-client-to-authenticator-protocol (2.2/2.3) for how §6.3 operations, hmac-secret, largeBlob, credential management and hybrid are carried. fido-server-requirements 2.3, which makes §7 and §8 normative for FIDO2 server certification; its WebAuthn links point to Level 2 numbering. fido-metadata-service and fido-metadata-statement for trust anchors via AAGUID (§7.1 step 23). fido-appid-and-facets for the appid algorithms. fido-u2f-raw-message-formats for U2F signature and attestation compatibility. fido-registry for key formats cited in §8.6. fido-security-ref for the threat model. fido-functional-certification-policy for how server certification is run.
