# Web Authentication: An API for accessing Public Key Credentials - Level 2

Version 2 · W3C Recommendation · 2021-04-08 · **superseded by Level 3** · [source](https://www.w3.org/TR/2021/REC-webauthn-2-20210408/)

## Summary

WebAuthn Level 2 is the 2021 W3C Recommendation for the Web Authentication API, now superseded by Level 3. It defines `navigator.credentials.create()`/`get()` for public key credentials, the authenticator model (authenticator data, attestation), the relying-party registration and assertion verification procedures, attestation formats (packed, TPM, Android Key, Android SafetyNet, FIDO U2F, none, Apple anonymous), extensions including appid, appidExclude, credProps, largeBlob and uvm, and WebDriver automation for virtual authenticators. The active FIDO2 Server Requirements (2.3) target Level 3, so use this level mainly for legacy deployments.

**Who needs it:** relying parties & server developers, platform & client (browser) developers, authenticator vendors (authenticator model and attestation)

**Look here for:**
- Steps to verify a registration → §7.1 `#sctn-registering-a-new-credential`
- Steps to verify an assertion → §7.2 `#sctn-verifying-assertion`
- Authenticator data layout and flags → §6.1 `#sctn-authenticator-data`
- Packed attestation rules → §8.2 `#sctn-packed-attestation`
- Defined extensions (appid, largeBlob, uvm, ...) → §10 `#sctn-defined-extensions`

## Reading guide

**Use this version when:** you maintain an RP, client or test suite written against the 2021 text, or you need the uvm extension (§10.3 `#sctn-uvm-extension`), which Level 3 dropped. FIDO2 server certification (fido-server-requirements 2.3) targets Level 3, but its WebAuthn section links still resolve to Level 2 numbering, so keep this page handy to decode those references. getPublicKey() and getAuthenticatorData() (§5.2.1.1 `#sctn-public-key-easy`) first appeared in this level.

**Differences from Level 3:**
- Client data: §5.8.1 `#dictionary-client-data` has a live `tokenBinding` member and no `topOrigin`. §7.1 `#sctn-registering-a-new-credential` and §7.2 `#sctn-verifying-assertion` require checking `tokenBinding.status`, and they check `origin` only against the RP's own origin, with no crossOrigin/topOrigin steps.
- Flags: §6.1 `#sctn-authenticator-data` treats bits 3–5 as RFU. There are no BE/BS flags, no backup-state section and no BE/BS checks in §7.
- §7.1: no 1023-byte credential ID check. For a credential ID already registered to a different user, the RP SHOULD fail or MAY accept the registration while deleting the older one (L3 just says SHOULD fail). There is no credential record concept: the RP stores the ID, public key, counter and, RECOMMENDED, the transports. UP is always required.
- §7.2: UV is checked if required, with no rule to ignore it otherwise and no uvInitialized/backupState updates. The counter case is described only as possible cloning.
- §5.1.3 `#sctn-createCredential`: create from a cross-origin iframe always returns NotAllowedError (§5.10 `#sctn-iframe-guidance` allows only get). With attestation `none`, the client zeroes the AAGUID. There is no conditional mediation, no hints, no attestationFormats and no related origins.
- API surface: there is no toJSON/parse*FromJSON, getClientCapabilities, signal methods or isConditionalMediationAvailable. §5.1.6 `#sctn-preventSilentAccessCredential` is present here.
- Transports (§5.8.4 `#enum-transport`): only usb, nfc, ble and internal (no hybrid or smart-card).
- Strings: §6.4.2 `#sctn-strings-langdir` defines the in-string language/direction encoding that L3 marks NOT RECOMMENDED. §6.4.1 `#sctn-strings-truncation` is not split into client and authenticator rules.
- Attestation: no compound format, no enterprise-packed certificate section, and SafetyNet is not deprecated (§8.5 `#sctn-android-safetynet-attestation`).
- Extensions (§10 `#sctn-defined-extensions`): appid, appidExclude, uvm, credProps and largeBlob, with no prf.
- No test vectors, no §15.1 timeout range, no §13.4.8/§13.4.9 (code injection, origin validation) and no §14.5.4/§14.5.5.

**Section by section:** structure as in Level 3 for §1–§14, except that §10 is flat (10.1–10.5 rather than 10.1.x) and there are no §16 test vectors or §18 revision history; see that page's reading guide. The step references inside §7.1 also differ: attestation verification is step 19, trust anchors step 20, and trust assessment step 21.
