# FIDO Device Onboard Specification

Version 2.0 · Proposed Standard · 2026-04-02 · [source](https://fidoalliance.org/specs/FDO/FIDO-Device-Onboard-PS-v2.0-20260402/FIDO-Device-Onboard-PS-v2.0-20260402.html)

## Summary

FIDO Device Onboard (FDO) 2.0 is the current version of FIDO's automatic onboarding protocol. A device ships without knowing its final owner. At first power-up it uses a Rendezvous Server to find the owner's platform, then proves its identity and receives the owner's credentials and configuration. This is called "late binding". The spec defines the protocol entities, the Ownership Voucher chain that transfers ownership through the supply chain, and the protocols DI, TO0, TO1 and TO2. It also covers CBOR/COSE encoding, ServiceInfo modules and the base cryptographic profile. FDO is not a user-authentication protocol. It has its own FIDO certification program, separate from the authenticator, server and biometric programs. In 2.0 the TO2 exchange differs from 1.1 in essentially every message. Each message was reordered and renamed with a `20` suffix (for example `TO2.ProveDevice20`). Capability flags handle version negotiation. pv4fdo is an optional companion protocol for path verification.

**Who needs it:** IoT/edge device vendors, owner and onboarding service developers, Rendezvous Server operators, FDO certification applicants

**Look here for:**
- How DI, TO0, TO1 and TO2 fit together → §2.5 `#FIDOIOTProtocols`
- Ownership Voucher structure and extension → §2.7 `#OVIntro`
- Delegate certificates and Name-Owner Match permissions → §3.5 `#Delegation`
- Capability flags for version negotiation → §3.3.2 `#CAPVENDOR`
- Mandatory crypto profile and algorithms → §1.7 `#BASEPROFILE`, Appendix B `#AP-C-CRYPTO`
- Full list of 1.1 → 2.0 changes → Appendix F `#FDOV11-20`

**Changes from previous version:** Adds Delegation: an Owner-signed delegate certificate lets other sites onboard devices for the Owner, with X.509 permissions and Name-Owner Match (NOM) constraints. Adds CapabilityFlags/VendorCapFlags for version negotiation and per-device or per-Owner control of Delegation. In TO2, device attestation now comes before the Ownership Voucher proof, so every TO2 message changed and was renamed (`…20`). The final voucher validation rules now have their own section (§5.6). EPID group signatures were removed. Every COSE_Sign1 signature now carries an operation-specific `external_aad` tag (domain separation). The document adds a key-words lexicon and drops the term "Delegation Problem". Post-quantum suites are not included yet; they are planned for a later update.

## Reading guide

**Start here:** §1.3 Protocol Introduction `#intro` for late binding and the untrusted-installer model. §2.5 Protocols `#FIDOIOTProtocols` (with §2.5.1–2.5.4) gives the start and end state of DI, TO0, TO1 and TO2. §2.7 The Ownership Voucher `#OVIntro` explains the trust chain. §1.7 Base Profile `#BASEPROFILE` is the normative minimum every implementation must meet. Then go to §5.5 `#TO2` for the message-level detail, and keep §5.6 `#VoucherValidation` open, because that is where the security decision is made.

**Section by section:**
- §1.3.1 `#DELEGATEDOWNERS`, §1.3.2 `#CAPABINTRO`, §1.4 `#FIDOIOTVersion`: what is new in 2.0, plus versioning. Owners and Rendezvous Servers MAY support several protocol versions; a Device MAY support only one.
- §1.5 Correlation Attack Concerns `#CorrAtkConcern`: TO2 replaces every FDO key and identifier except the device attestation key, so repeated FDO use stays linkable through that key. Single use or closed networks avoid it.
- §1.7 Base Profile `#BASEPROFILE` (normative): §1.7.1 `#BPVERSIONING` makes CapabilityFlags and version negotiation mandatory. §1.7.2 `#profileProtocols`: Rendezvous Server and Owner SHALL serve HTTP and HTTPS; the Device needs either. §1.7.3 `#DEVICEATTN`: device attestation is ECDSA P-256/P-384 (X5CHAIN or X.509); PQ-safe crypto is recommended but not defined. §1.7.4 `#PROFILEDELEGATION`: capability flags for Delegation are MUST, Delegation itself SHOULD. §1.7.5 `#OV`: Owner and Rendezvous Server verify every voucher crypto combination; the Device needs only one, and the manufacturer seeds one option that all later extensions must keep. §1.7.6 `#TO2CRYPTO`: key exchange and cipher sets. §1.7.7 `#local-rendezvous-discovery-path`: every Device MUST carry `rvserver.local` in its RendezvousInfo.
- §2.1–2.4 (`#messageProtocol`, `#CBORdoc`, `#protocolEnt`, `#protentity`): message layer, CDDL conventions, and the entities (Device ROE, Manufacturer, Owner Onboarding Service, Rendezvous Server, Management Agent and Service).
- §2.5.1 DI `#DIINTRO`: explicitly non-normative, an example of factory provisioning with a TOFU trust model. What a device must hold after any initialization method is normative in §5.2.5 `#FDOINITREQUIREMENTS`. §2.5.2 TO0 `#TO0INTRO` and §2.5.3 TO1 `#TO1INTRO`: the Owner registers a time-limited GUID→address "blob", and the Device fetches it. The Rendezvous Server is trusted only to remember that mapping; it neither authorizes nor learns the result. §2.5.4 TO2 `#TO2INTRO`: mutual proof, encrypted channel, ServiceInfo, credential replacement.
- §2.6 Routing Requirements `#ROUTINGREQ`: closed networks work if the Rendezvous Server and Owner are reachable inside them. §2.7 `#OVIntro` and §2.7.1: the voucher is a chain of signed public keys from the manufacturer key (hashed in the device) to the Owner key. Signing and key encoding must stay consistent across all entries. It is unrelated to RFC 8366 vouchers.
- §3.1–3.3 Encoding `#PROTENC`: CBOR types. §3.3.3 `#CAPABILITYFLAGS` defines bits for FDO 1.0/1.1/2.0 and Delegation. §3.3.3.1 `#VERNEGOTIATION`: Owner and Rendezvous Server MUST negotiate, 2.0 devices SHOULD, and a 1.x-only device can send the 2.0 probe and then `SWITCH_VERSION`. §3.3.3.2 `#VENDORFLAG`: vendor flags use reverse-DNS strings. §3.3.8 `#COSEDomainSep`: every COSE_Sign1 (TO0.OwnerSign, TO1.ProveToRV, TO2.ProveDevice20, TO2.ProveOVHdr20, TO2.SetupDevice20, OVEntry) MUST carry its `FDODomainTag` in `external_aad`, and verifiers MUST check it. §3.3.16–3.3.17 cover RendezvousInfo and the `RVTO2Addr` blob.
- §3.4 Device Credential & Ownership Voucher `#DCOV`: §3.4.1 `#DeviceCredential` is non-normative storage; §3.4.2 `#OwnershipVoucher` is the normative persisted format. §3.4.3 `#OVEXT` covers extension and §3.4.4 `#OVRESTORE` recovery. §3.4.5 `#DEVCERTVALID` and §3.4.6 `#OVVERIFY` (subsections for internal checks, Owner key, delegate certificate, device chain, receiver and Rendezvous Server) give the verification rules per role.
- §3.5 Delegation `#Delegation`: §3.5.1 `#DELEGATETOPS` describes the enterprise model (central ordering key, local onboarding sites). §3.5.2 `#DLGMECHANISM`: a Delegate Certificate (X5CHAIN rooted in an Owner signature) replaces the Owner key in the TO0/TO1 blob and in TO2.ProveOVHdr20. It stops working if the voucher is extended to a new Owner key. All certificates must be verified before the first ServiceInfo is processed. §3.5.2.1 `#CAOwnerKey`: the Owner key may be a CA key, and then only delegates can onboard and the voucher cannot be extended. §3.5.3–3.5.4 (`#DelegatedRendezvous`, `#RVWeights`): several Owner/delegate records with preference weights. §3.5.5 `#x509keytypes`: EKU permissions `fdo-ekt-permit-redirect` (needed for TO0) and the onboard permissions `...-new-cred`, `...-reuse-cred` and `...-fdo-disable` (one needed for TO2); a missing one means `DELEGATE_NOT_PERMITTED`. §3.5.6 `#NOM`: Name-Owner Match identity and constraints, which can only narrow down the chain.
- §3.6 `#DevAttnProt` and §3.7 `#kex`: EAT-based attestation with ECDSA (EPID is gone). Key exchange is DH (id14/id15), RSA-OAEP asymmetric or ECDH, with the KDF and the mapping to cipher suites in §3.7.4–3.7.5.
- §3.8 RendezvousInfo `#RVInfo`: directives and instructions, §3.8.1 `#RVBYPASS` to skip the Rendezvous Server, examples, and §3.8.3 `#recommendedRVInfo` with the normative local-rendezvous rule (§3.8.3.1 `#requiredLocalRV`) and HTTPS-only vs. fallback patterns.
- §3.9 ServiceInfo `#ServiceInfo`: the module key-value framework. `devmod` (§3.9.2 `#RVDEVMOD`) MUST come first from the device. The Owner MUST send `modname:active` before using a module, the Device answers for modules it lacks, and any module error fails the session (§3.9.3 `#RVMODSEL`). File transfer and code execution examples are hypothetical.
- §4 Data Transmission `#datatrans`: message format, stream framing and HTTP mapping (§4.3 `#HTTPLike`: the server issues a token in `Authorization` for each protocol run), and §4.4 `#encmsgbody` for the encrypted message body (AEAD or encrypt-then-MAC).
- §5.1 `#errormsg` and §5.1.1.1 `#ECValues`: Error message 255 and codes, including the new `SWITCH_VERSION`, `CHANGE_CAP_ERROR`, `CRED_REUSE_ERROR` and `DELEGATE_NOT_PERMITTED`. §5.2 DI messages 10–13 (`#DI-Details`).
- §5.3 TO0 `#TO0` (20–23) and §5.4 TO1 `#TO1` (30–33, plus `#rvmore`): `TO0.OwnerSign` carries the signed blob (to1d) and a wait time. `TO1.ProveToRV` is the device's EAT proof, and `TO1.RVRedirect` returns the blob that the device must verify later in TO2.
- §5.5 TO2 `#TO2` (80–91): `TO2.HelloDeviceProbe` (capabilities, GUID, hash types, `sugar`) → `HelloDeviceAck20` (suites, nonce, `hashPrev`) → `ProveDevice20` (EAT signed by the device, chosen suites, key exchange share A, `hashPrev2`) → `ProveOVHdr20` (voucher header, HMAC, key exchange share B, `OwnerPubKey`, optional `DelegateChain`) → `GetOVNextEntry20`/`OVNextEntry20` loop → encrypted phase: `DeviceServiceInfoRdy20` → `SetupDevice20` (disposition `DispResale`/`DispCredReuse`/`DispDisable` plus replacement credentials under a new Owner2 key) → `DeviceSvcInfo20`/`OwnerSvcInfo20` loop → `Done20`/`DoneAck20`. ServiceInfo messages default to 1300 bytes (1500 MTU), with a 1,000,000 round-trip cap (§5.5.2 `#TO2RT`). §5.5.4.1 `#PROBEVERSIONS` describes version probing.
- §5.6 Final Voucher Validation `#VoucherValidation`: the early `OwnerPubKey` verifies the TO1 blob and ProveOVHdr20, directly or through delegate certificates (which need the redirect and onboard permissions). The voucher walk then proves that `OwnerPubKey` equals the last entry's key, rooted in the hash stored in the device. §5.7 `#TO2-AFTER`: hand-off to the management agent.
- §6 Resale `#resale` and §6.1 `#TO2-NORESALE`: FDO goes dormant after TO2. The new HMAC and Owner2 key let the Owner build a replacement voucher; `DispDisable` forbids re-enabling. §7 Credential Reuse `#credreuse`: keeps the same credentials for demos or supplier recovery. A device MAY refuse it (`CRED_REUSE_ERROR`), and delegates need the reuse permission.
- Appendix A `#AP-B-ECDSA`, Appendix B `#AP-C-CRYPTO` (non-normative crypto table), Appendix E `#localIANA`, Appendix F `#FDOV11-20` (change list).

**What matters most:**
- The device-side checks in §5.5.7 `#to2ProveOVHdr20`, §5.5.9 `#MSGT2-63` and §5.6 `#VoucherValidation`: verify the header HMAC against the device secret, check the stored manufacturer key hash, walk each entry (signature, `HashPrevEntry`, `HashHdrInfo`), match the last key to `OwnerPubKey`, and verify the stored TO1.RVRedirect signature with the same key, failing TO2 on mismatch. Skipping any of these breaks the ownership model.
- Domain separation (§3.3.8 `#COSEDomainSep`): a signer or verifier that omits `external_aad` or uses the wrong tag will not interoperate with 2.0 peers.
- Delegate chain rules (§3.5.2 `#DLGMECHANISM`, §3.5.5 `#x509keytypes`): leaf not a CA, non-leaf certificates with IsCA, root signed by the final Owner, and permissions present in the chain. A failure counts as an Owner signature failure.
- `hashPrev`/`hashPrev2` (§5.5.5 `#HelloDeviceAck20`, §5.5.6 `#MSGT2-64`) protect the two unsigned opening messages. The Owner MUST drop the connection on mismatch.
- Version negotiation is unsigned (§3.3.3.1 `#VERNEGOTIATION`), so an Owner MUST NOT select a version it knows to be vulnerable.
- `rvserver.local` in every device's RendezvousInfo (§1.7.7 `#local-rendezvous-discovery-path`, §5.2.5 `#FDOINITREQUIREMENTS`) is a MUST that is easy to miss in manufacturing tools.
- Left to implementers: how DI is secured, Owner-side storage of delegate-issued credentials, how FDO is re-enabled for resale, token format, ServiceInfo module semantics, and the choice of suites within the profile.

**Watch out for:**
- Order of proof. Appendix F `#FDOV11-20` and the message order (ProveDevice20 = 82 before ProveOVHdr20 = 83) put device attestation first, but §5.5.1 `#to2v20` says Owner verification comes before device verification. Follow the message definitions.
- Where `ReplacementHMac` goes is inconsistent. It appears in `DeviceServiceInfoRdy20` (with a comment saying it moved to "TO2.Done12"), in the first `DeviceSvcInfo20`, and in the prose of `Done20`, whose CDDL does not contain it. §7 `#credreuse` asks for a null HMAC in message 86, although the disposition only arrives in message 87.
- Leftover 1.1 and draft names: HTTP paths `/101`, `/62`, `/66`, `/68`, `/70` do not match type numbers 81, 84, 86, 88, 90. Text also refers to `TO2.HelloDevice`, `TO2.ProveDevice` as the next state after the last voucher entry, `SetupDevice12`, `OwnerServiceInfoReady` and `fdo-ekt-permit-new-cred`. `TO1.RVMore` has no type number.
- §3.5.2 `#DLGMECHANISM` says permissions narrow toward the leaf, while §3.5.5 says a permission counts only if every certificate in the chain carries it. Issue permissions on every certificate to be safe.
- Normative status varies: DI (§2.5.1) and the Device Credential layout (§3.4.1) are non-normative, as is Appendix B, but the voucher format (§3.4.2) and §5.2.5 are normative.
- 2.0 signatures now include domain tags, also on OVEntry. How vouchers extended by 1.x tools are treated in a 2.0 flow is not spelled out; check before mixing toolchains.
- No PQ suites yet (§1.7.3.1 `#PROFILEPQSAFECRYPTO`); an update is announced.

**Related documents:** `pv4fdo` (optional path verification of TO1/TO2 connections at a network choke point). `fido-device-onboard` 1.1 and 1.0 for devices that only speak those versions; negotiation per §3.3.3.1 lets a 2.0 Owner serve them. `fido-glossary` for the base terms extended in §1.2.1.
