# Path Verification for FDO (PV4FDO)

Version 1.0 · Proposed Standard · 2026-01-22 · [source](https://fidoalliance.org/specs/FDO/pv4fdo-v1.0-ps-20260122/pv4fdo-v1.0-ps-20260122.html)

## Summary

Path Verification for FDO (PV4FDO) 1.0 is an optional companion to FIDO Device Onboard. It gives the onboarding side evidence that a device's FDO connection actually passed through a chosen point in the network. This helps with the "proof of possession" problem: an attested device can still be plugged in at the wrong place, or be part of a doorstep-style attack. The network owner places a PV4FDO node at a network choke point, either as a router or by reading a mirror (SPAN) port. The node hashes the upstream client-to-server bytes of each FDO TO1/TO2 connection and derives a connection ID (`PVGuid`). For FDO over TLS, the `PVGuid` comes from the ClientHello record. The node never decrypts the traffic. It posts the result as `Proxy.SendHash` (CBOR or JSON, bearer-token authenticated) to the TO1/TO2 service. The service compares that hash with what it received. TO0 is not covered, and redundant routing paths are not handled. The document is short and does not change FDO messages themselves. FDO has its own FIDO certification program, separate from user-authentication certification. Whether PV4FDO is part of that program was not checked.

**Who needs it:** FDO owner/onboarding service operators, network and infrastructure vendors deploying FDO in controlled sites

**Look here for:**
- What problem path verification addresses → §1 `#pvIntro`

## Reading guide

**Start here:** §5 Overall Approach `#pvOverall` is the actual protocol: what a node is configured with, what it hashes and what the FDO target does with the result. Then read §6 `#pvTechDescr` for the one HTTP message and §7 `#message-meaning` for retry rules and examples. §1 `#pvIntro` and §4 `#pvThreatMitg` give the motivation in two pages.

**Section by section:**
- §1 Introduction `#pvIntro`: frames PV4FDO as a partial answer to FDO's "proof of possession" gap. The FDO server side learns whether a TCP connection crossed one chosen waypoint. Redundant IP paths are explicitly not handled, so the waypoint should be a choke point.
- §2 Other Internet Path Verification Mechanisms `#pvPathVerif` (informative): positions this as single-waypoint proof-of-transit, unlike BGP or source routing.
- §3 Vocabulary `#pvVocabulary`: Monitoring Point, Monitoring Extent (how many bytes per connection are examined), PVGuid, SPAN/mirror port. TCP port 61 is suggested as a site-specific PV4FDO port.
- §4 Threat Mitigation `#pvThreatMitg`: two scenarios, a device cabled into the wrong network segment and the "doorstep attack" where devices are swapped so FDO provisions the victim's device inside the attacker's network.
- §5 Overall Approach `#pvOverall`: the node is a router or reads a SPAN port, and is configured with a port, an access-token mechanism, its Monitoring Point and a Monitoring Extent. It hashes only client-to-server (upbound) bytes and never decrypts. For FDO over TLS, the PVGuid is the hash of the first TLS record (the ClientHello), and TLS data MUST be hashed on record boundaries. Without TLS, hashing MUST continue through `TO1.ProveToRV` (TO1) or `TO2.HelloDevice` (TO2). TO0 is out of scope. A second hash covers bytes up to the Monitoring Extent and is posted to the FDO target, which compares it with its own. Hash choices: SHA256 (-16) and SHA384 (-43).
- §6 Protocol Technical Description `#pvTechDescr`: HTTP POST to `/fdo/communication/client` with body `Proxy.SendHash = [pvguid, hash, hashedBytes]` in CBOR or JSON. `Authorization: Bearer` is mandatory; how tokens are issued is site-specific and out of scope.
- §7 Message Meaning `#message-meaning`: the proxy posts each time the FDO agent sends new data and retries until it gets 200 (retry count and delay are implementation-specific). The service answers 200 or 400 (bad token, too many requests) with an empty body. Two worked examples follow.

**What matters most:**
- Target behaviour in §5 `#pvOverall`: on a hash mismatch the target SHOULD drop the FDO connection. If traffic comes from a network known to be covered by PV4FDO and no PV4FDO message arrives, the target MUST log an error and SHOULD reject the requested action. This is where the security benefit comes from.
- Hashing on TLS record boundaries and over upbound data only (§5 `#pvOverall`). Both the node and the target must count exactly the same bytes, so `hashedBytes` (§6 `#pvTechDescr`) has to be honoured when comparing.
- Left to the deployer: token format and distribution, Monitoring Extent, whether to keep hashing past the extent (implementation-specific, same PVGuid), and how the network guarantees that FDO traffic really passes the choke point.

**Watch out for:**
- The examples in §7 `#message-meaning` do not match §6 `#pvTechDescr`. §6 defines an array, but the examples are maps. The CBOR hex encodes a two-entry map with a `guid` key, while the JSON rendering and the note show three keys (`pvguid`, `hash`, `hashedBytes`). Agree on the encoding with your counterpart before implementing.
- Nothing in `Proxy.SendHash` names the hash algorithm, although §5 lists two. The algorithm has to be configured out of band.
- §5 says the PVGuid is computed over TO2 data, but the non-TLS rules also cover TO1, and §6 posts to a combined TO1/TO2 service.
- Busy-service rejection uses 400, not 429.
- The document says it is not a full answer to proof of possession. It gives evidence for one waypoint only.

**Related documents:** `fido-device-onboard` (v2.0) for the TO1/TO2 messages (`TO1.ProveToRV`, `TO2.HelloDevice`) and the rendezvous and owner roles the hash is checked by.
