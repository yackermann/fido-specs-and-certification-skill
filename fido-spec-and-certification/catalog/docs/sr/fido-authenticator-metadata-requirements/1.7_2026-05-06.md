# FIDO Authenticator Metadata Requirements

Version 1.7 · Review Draft · 2026-05-06 · **ACTIVE** · [source](https://fidoalliance.org/specs/fido-security-requirements/fido-authenticator-metadata-requirements-v1.7-rd-20260506.html)

## Summary

Lists which Metadata Statement fields are mandatory for Authenticator Certification, grouped as functional, security and biometric fields, each with a short note on when it applies. The submitted metadata is checked against the implementation: by the Security Secretariat at L1 and by the accredited lab at L2 and above. Publishing to the FIDO Metadata Service (MDS) is optional and can happen after certification. If the vendor does publish, the mandatory fields must match what was certified. §5 recommends using the MDS status report entries to record each certification as it is granted. Field definitions live in the Metadata Statement and MDS specifications, version 3.1.1 here.

Status: ACTIVE, although the file is labelled Review Draft (2026-05-06). v1.6 is active until 2027-01-13; v1.5.1 has no expiry (L3/L3+ track).

**Who needs it:** authenticator vendors and certification applicants, FIDO-accredited security labs

**Look here for:**
- Which functional fields must be supplied → Functional Metadata Fields `#functional-metadata-fields`
- Which security fields (key protection, attestation types, algorithms, FIPS data) are mandatory → §3 `#h2_security-metadata-fields`
- Biometric fields → §4 `#h2_biometric-metadata-fields`
- Recording certification status in MDS → §5 `#h2_use-of-metadata-service-1.1-status-dictionary`

**Changes from previous version:** Adds `multiDeviceCredentialSupport` as a mandatory functional field and `fipsRevision` and `fipsPhysicalSecurityLevel` as mandatory security fields. References are updated to Metadata Statement / MDS 3.1.1 (2026-01-05).

## Reading guide

**Start here:**
- §2 Introduction `#h2_introduction`: the process rules. Mandatory fields are evaluated by the Security Secretariat at L1 and by the accredited lab at L2 and above. They go in with the Certification Request and are checked against the implementation.
- Then the three field tables: Functional Metadata Fields `#functional-metadata-fields`, §3 `#h2_security-metadata-fields` and §4 `#h2_biometric-metadata-fields`. The document defines no field itself. Each row is a name plus an "applicable to" note, and the definitions live in fido-metadata-statement and fido-metadata-service.

**Section by section:**
- §2 Introduction `#h2_introduction`: publishing to MDS is optional and can wait until after certification. If you publish, the Mandatory fields that apply to your product must be present and must match what you submitted for certification.
- Functional Metadata Fields `#functional-metadata-fields`: an unnumbered section between §2 and §3. These fields are mandatory when applicable:
  - for everyone: `multiDeviceCredentialSupport`, `VerificationMethodDescriptor`, `verificationMethodANDCombination`, `attestationCertificateKeyIdentifiers`, `description`, `authenticatorVersion`, `protocolFamily`, `upv`, `userVerificationDetails`, `attachmentHint`, `isSecondFactorOnly`, `tcDisplay` and `tcDisplayContentType`;
  - `AAID` for UAF and `AAGUID` for "FIDO 2.0".
- §3 Security Metadata Fields `#h2_security-metadata-fields`: also mandatory when applicable.
  - For everyone: `CodeAccuracyDescriptor`, `PatternAccuracyDescriptor`, `assertionScheme`, `authenticationAlgorithm`, `publicKeyAlgAndEncoding`, `attestationTypes`, `keyProtection`, `matcherProtection`, `isKeyRestricted`, `isFreshUserVerificationRequired`, the certification fields `certificationDescriptor`, `certificateNumber` and `certificationRequirementsVersion`, and the FIPS fields `fipsRevision` and `fipsPhysicalSecurityLevel`.
  - Only for ECDAA attestation: `EcdaaTrustAnchor` and `attestationRootCertificate`.
  - Only at L2 and above: `cryptoStrength` and `operatingEnv`.
- §4 Biometric Metadata Fields `#h2_biometric-metadata-fields`: `BiometricAccuracyDescriptor`, `selfAttestedFRR`, `selfAttestedFAR`, `maxTemplates`, `maxRetries` and `blockSlowdown`, applicable to the FIDO Biometrics Component. The section states these are not mandatory to pass certification at L2 and below.
- §5 Status Dictionary `#h2_use-of-metadata-service-1.1-status-dictionary`: a recommendation (from the SRWG, not a MUST). Start the MDS status at "not FIDO Certified" and add one status report entry, with its date, for each certification as it is granted.

**What matters most:**
- Consistency is the real requirement. The metadata is verified against the product during certification, and anything later published to MDS must match it (§2 `#h2_introduction`). Settle `keyProtection`, `matcherProtection`, `attestationTypes` and the algorithm fields before you submit.
- `cryptoStrength` and `operatingEnv` apply from L2 (§3 `#h2_security-metadata-fields`). They have to be consistent with the claimed strength computed from fido-authenticator-allowed-cryptography-list and with the AROE chosen from fido-authenticator-allowed-restricted-operating-environments-list.
- New in this version and easy to forget when you reuse a v1.6 metadata statement: `multiDeviceCredentialSupport` (Functional), `fipsRevision` and `fipsPhysicalSecurityLevel` (§3).
- "When applicable" is left to judgment. The notes say only "all", UAF, FIDO 2.0, ECDAA or L2+, so agree with the lab on which fields are not applicable.

**Watch out for:**
- Many names do not match the 3.1.1 schemas. `VerificationMethodDescriptor`, `CodeAccuracyDescriptor`, `PatternAccuracyDescriptor`, `BiometricAccuracyDescriptor` and `EcdaaTrustAnchor` are type names; `AAID`/`AAGUID` are `aaid`/`aaguid` in the statement; and `attestationRootCertificate` is the plural `attestationRootCertificates`. I found no fields named `assertionScheme`, `isSecondFactorOnly` or `operatingEnv` in fido-metadata-statement or fido-metadata-service 3.1.1. Map each row to the current schema with your lab.
- §3 limits `attestationRootCertificate` to ECDAA. The Metadata Statement spec says the opposite: `attestationRootCertificates` is required and has no relevance for ECDAA, which uses `ecdaaTrustAnchors`.
- §5's title refers to the MDS 1.1 "Status Dictionary". In MDS 3.x this corresponds to status report entries, which carry `certificationDescriptor`, `certificateNumber` and the FIPS fields.
- The functional field table has no section number.
- The file is a Review Draft, but the catalog lists it as ACTIVE.

**Related documents:**
- fido-metadata-statement and fido-metadata-service (3.1.1): field definitions, status reports and certification fields.
- fido-authenticator-security-requirements: the requirements whose answers fill these fields.
