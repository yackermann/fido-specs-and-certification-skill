# FIDO Authenticator Allowed Restricted Operating Environments List

Version 1.7 · Review Draft · 2026-05-06 · **ACTIVE** · [source](https://fidoalliance.org/specs/fido-security-requirements/fido-authenticator-allowed-restricted-operating-environments-list-v1.7-rd-20260506.html)

## Summary

Companion to the Security and Privacy Requirements. It explains how an authenticator splits into hardware, a Restricted Operating Environment (ROE) and the Authenticator Application, and when an ROE counts as an Allowed ROE (AROE). The §3 criteria are: vendor-controlled security configuration, secure boot, full isolation from the rich OS and outside components, a security-focused design, and strong isolation from any co-hosted apps. §4 is the official list of technologies with blanket AROE status for L2, each with its key protection type. The list covers TEEs on ARM TrustZone, Intel VT, SGX and ME/TXE; TEEs certified to the GlobalPlatform TEE PP; Windows VBS (VTL1); the AMD PSP secure world; TCG TPMs; secure elements; and, under conditions, an embedded CPU with in-package RAM. Additions require an SPWG vote. Bespoke designs can instead be described in detail and judged case by case by the Security Secretariat.

Status: ACTIVE, although the file is labelled Review Draft (2026-05-06). v1.6 is active until 2027-01-13; v1.5.1 has no expiry (L3/L3+ track).

**Who needs it:** authenticator vendors targeting L2 and above, FIDO-accredited security labs

**Look here for:**

## Reading guide

**Start here:**
- Abstract `#h2_abstract`: the one rule that matters. An AROE is required for L2 and above, and authenticators outside an AROE can still reach L1.
- §4 `#h2_allowed-restricted-operating-environments`: check whether your platform technology is on the blanket list.
- §3 `#h2_requirements-for-restricted-operating-environment-to-be-allowed`: the criteria. Read these if your technology is bespoke or not listed.

**Section by section:**
- §2 Introduction `#h2_introduction`: the model. The authenticator includes everything it relies on (hardware, ROE firmware and the Authenticator Application), not just the app. An ROE may host other things, and its security can be shown through existing schemes such as Common Criteria. The certification focus per level: L1 covers scalable attacks on the server and the channel, L2 adds client-side scalable attacks such as malware, and L3/L3+ add physical attacks. The three figures are not reproduced in the text.
- §3 Requirements `#h2_requirements-for-restricted-operating-environment-to-be-allowed`: these MUSTs apply:
  - the vendor of the device, its delegates or suppliers control the security configuration;
  - the AROE protects itself against modification that weakens it, including while powered off, which means secure boot;
  - full isolation from the rich OS and external components except for protocol messages, so that nothing outside can change state, registers, memory or storage inside.
  
  These are SHOULDs: a security-focused design (no large graphics, signal processing, general app hosting or network stacks), co-hosted apps that are themselves security-oriented, and a security-oriented engineering practice (expert code review, patching, incident tracking, secure coding, documentation). If other apps outside the authenticator boundary run in the AROE, isolation from them must be strong and complete.
- §4 Allowed ROEs `#h2_allowed-restricted-operating-environments`: the official list, with a key protection type per entry:
  - TEE: ARM TrustZone, Intel VT, Intel SGX, Intel ME/TXE, the AMD PSP secure world, and any TEE certified to the GlobalPlatform TEE PP. That certification is sufficient, but it is not required for L2.
  - SW: Windows 10 VBS, for code at Virtual Trust Level 1.
  - SW: TCG TPMs (1.2 or 2.0). Keys may be stored or wrapped in hardware but exported to the device.
  - SE: secure OS on a tamper-resistant microcontroller.
  - Embedded CPU with in-package RAM. It qualifies only if CPU, flash and RAM share one package with no outside access (tamper resistance is not needed); it has secure boot and does not allow installing apps; in-boundary apps are small and fully vendor-controlled; and it talks FIDO over approved transports (USB, NFC, BLE), with non-FIDO transports only for chip programming. Network stacks (Ethernet, TCP/IP) are disallowed.
  
  Additions need an SPWG vote on a new version of the document. Blanket approval covers any authenticator built on the technology. Bespoke designs are judged case by case by the FIDO Security Secretariat from a detailed hardware/software description, which adds time to certification.

**What matters most:**
- The level gate: no AROE, no L2 (Abstract `#h2_abstract`). For L1 and L1+, fido-authenticator-security-requirements says the ROE may simply be the HLOS.
- The blanket list (§4 `#h2_allowed-restricted-operating-environments`) is written for L2. Being on it does not by itself meet the physical-attack expectations of L3/L3+ described in §2 `#h2_introduction`. Those come from the Security Requirements.
- The embedded-MCU entry is conditional (§4). Every condition has to hold, so any one of these takes it off the list: no secure boot, a way to install apps, a network stack, or non-FIDO communication that is not small and security-oriented.
- §4 gives each entry a key protection type (TEE / SE / SW). TPMs and Windows VBS are classed as SW, not hardware. Keep this in view when you fill in key-protection metadata, although this document does not tie the two together itself.
- For unlisted designs, the evidence you write must address every §3 criterion (§3 `#h2_requirements-for-restricted-operating-environment-to-be-allowed`).

**Watch out for:**
- The case-by-case paragraph at the end of §4 refers to criteria in "section 4 below", but the criteria are in §3.
- The TPM row attributes its SW classification to a Note that does not appear in the document.
- §3 has a nested bullet with no parent item, and some typos, so the MUST/SHOULD split is clearest when read item by item.
- The file is a Review Draft, but the catalog lists it as ACTIVE. Its text matches v1.6 and v1.5.1.
