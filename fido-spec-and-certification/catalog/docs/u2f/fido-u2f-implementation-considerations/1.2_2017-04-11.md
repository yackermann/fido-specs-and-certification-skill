# FIDO U2F Implementation Considerations

Version 1.2 · Proposed Standard · 2017-04-11 · [source](https://fidoalliance.org/specs/fido-u2f-v1.2-ps-20170411/fido-u2f-implementation-considerations-v1.2-ps-20170411.html)

## Summary

Short guidance note for people building U2F tokens, clients and relying-party servers. It covers response timing (tokens should answer quickly, typically within 500 ms, without waiting for presence they don't need; clients should wait at least 3 seconds; presence may be remembered for up to 10 seconds), building key handles that wrap the private key (choose the strongest cipher the hardware protects well, and make a wrong-token key handle indistinguishable from a wrong-origin one so sites cannot probe other registrations), secure key generation, challenge parameters, and revocation (U2F has no device revocation, so relying parties should let users report lost tokens and stop accepting them). It also says tokens must increment a counter on every authentication, either globally or per application, starting at 0, so relying parties can spot cloning. U2F keys must not be used for anything else, and there are UI suggestions for FIDO clients.

The raw message format document points here for counter details. U2F 1.2 is the only certifiable U2F version.

**Who needs it:** authenticator vendors, platform & client developers, relying parties & server developers

**Look here for:**
- Expected response and user-presence timing → §2.1 `#h3_timing-considerations`
- Rules for wrapped key handles → §2.2 `#h3_generation-of-key-handles`
- What to do about lost or stolen tokens → §2.5 `#h3_revocation-of-tokens`
- Counter behaviour and clone detection → §2.6 `#h3_token-counters`
- Restricting U2F keys to U2F use → §2.7 `#h3_key-usage`

## Reading guide

**Start here:** the whole substance is §2 `#h2_implementation-considerations`, eight short subsections. Token builders should read §2.1 `#h3_timing-considerations`, §2.2 `#h3_generation-of-key-handles` and §2.6 `#h3_token-counters` first; RP developers §2.4 `#h3_challenge-parameters`, §2.5 `#h3_revocation-of-tokens` and §2.6 `#h3_token-counters`.

**Section by section:**
- §2.1 `#h3_timing-considerations`: tokens should reply fast, usually within 500 ms, and not wait for presence a request does not need; clients should wait at least 3 s before giving up; a detected presence should be kept for 10 s or until an operation consumes it, whichever is first.
- §2.2 `#h3_generation-of-key-handles`: for wrapped key handles, pick the cipher the hardware protects best (the text notes a "weak" cipher can be better protected than AES on some chips), and make "key handle from another token" and "key handle for another origin" indistinguishable to the RP, including by timing.
- §2.3 `#h3_secure-key-generation`: use a recommended PRNG with good entropy; if entropy is weak, mix in the challenge parameter.
- §2.4 `#h3_challenge-parameters`: RP challenges should carry at least 8 random bytes, following SP 800-63-1.
- §2.5 `#h3_revocation-of-tokens`: no device identifiers, so no revocation lists; each RP should let users report lost or stolen tokens and stop accepting them.
- §2.6 `#h3_token-counters`: the token must increment a counter on every authentication, global or per application parameter, starting at 0; RPs choose their own response to non-increasing values.
- §2.7 `#h3_key-usage`: keys made by U2F registration must not be used for anything else.
- §2.8 `#h3_ui-considerations-for-fido-clients`: clients should show which origin is creating or using U2F keys and may let users allow or deny RPs.

**What matters most:**
- Indistinguishable bad-key-handle errors (§2.2 `#h3_generation-of-key-handles`) are a privacy property: without them one site can test whether a token is registered at another.
- Counter monotonicity on every authentication (§2.6 `#h3_token-counters`) is what the raw message formats rely on for clone detection; the choice between global and per-application counters is left to the vendor.
- The timing numbers (§2.1 `#h3_timing-considerations`) are the reference values for token responsiveness and client timeouts.
- Clone remediation and lost-token handling are entirely RP policy (§2.5 `#h3_revocation-of-tokens`, §2.6 `#h3_token-counters`).

**Watch out for:**
- Requirement words are written in lower case ("must", "should") although §1.1 `#h3_key-words` points to RFC 2119; treat the counter and key-usage rules as firm and the rest as guidance.
- §2.4 `#h3_challenge-parameters` uses the 1.0 JavaScript API terms SignData and EnrollData, which no longer exist in the 1.2 JavaScript API.
- §2.2 `#h3_generation-of-key-handles` gives no wrapping algorithm; the format of a key handle stays vendor-defined.

**Related documents:** fido-u2f-raw-message-formats (counter field, bad-key-handle error, challenge parameter), fido-u2f-overview (§7 and §8.1 explain key wrapping and counters), fido-u2f-javascript-api (where the challenge is passed), fido-u2f-hid-protocol / fido-u2f-nfc-protocol / fido-u2f-bt-protocol (transport-level timing), fido-authenticator-security-requirements (certified requirements for key protection and RNG).
