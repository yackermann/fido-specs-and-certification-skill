# FIDO U2F Authenticator Transports Extension

Version 1.2 · Proposed Standard · 2017-04-11 · [source](https://fidoalliance.org/specs/fido-u2f-v1.2-ps-20170411/fido-u2f-authenticator-transports-extension-v1.2-ps-20170411.html)

## Summary

Defines an optional, non-critical X.509 extension that lets a U2F authenticator state in its attestation certificate which transports it supports, so relying parties can tailor their UI. The attestation certificate must be X.509 v3 and DER-encoded, profiled on RFC 5280. The document sets up the FIDO OID arc (`1.3.6.1.4.1.45724`) and its U2F sub-arc (`id-fido-u2f`, arc 2), and defines `id-fido-u2f-ce-transports` as a BIT STRING with bits for Bluetooth Classic, Bluetooth LE, USB, NFC and internal USB. Clients and relying parties may ignore the extension. Two examples show the encoding for a Bluetooth Classic authenticator and a USB + NFC authenticator.

The same FIDO OID arc carries later certificate extensions such as the AAGUID extension (`1.3.6.1.4.1.45724.1.1.4`) used in WebAuthn attestation, and WebAuthn cites this document. U2F 1.2 is the only certifiable U2F version.

**Who needs it:** authenticator vendors (attestation certificate issuance), relying parties & server developers, certification applicants

## Reading guide

**Start here:** §3.2.1 `#h4_fido-u2f-certificate-transports-extension` for the ASN.1 and bit assignments, then the two encodings in §3.3 `#h3_examples` to check your own DER output. §2 `#h2_attestation-certificates` sets the certificate profile.

**Section by section:**
- §2 `#h2_attestation-certificates`: attestation certificates carrying the extension MUST be X.509 v3; the document profiles RFC 5280 and everything MUST be DER-encoded.
- §3.1 `#h3_fido-u2f-oid-arc`: `id-fido` = 1.3.6.1.4.1.45724 and `id-fido-u2f` = `{id-fido 2}`.
- §3.2 `#h3_fido-u2f-certificate-extensions`: certificate extensions arc `id-fido-u2f-ce` = `{id-fido-u2f 1}`.
- §3.2.1 `#h4_fido-u2f-certificate-transports-extension`: `id-fido-u2f-ce-transports` (1.3.6.1.4.1.45724.2.1.1) with syntax `FIDOU2FTransports`, a BIT STRING: bit 0 `bluetoothRadio` (Classic), 1 `bluetoothLowEnergyRadio`, 2 `uSB`, 3 `nFC`, 4 `uSBInternal`. The extension is non-critical and clients and RPs MAY ignore it.
- §3.3 `#h3_examples` (§3.3.1 `#h4_bt-classic-authenticator`, §3.3.2 `#h4_usb-nfc-authenticator`): full DER of the extension; Bluetooth Classic is BIT STRING `03 02 07 80`, USB + NFC is `03 02 04 30`.

**What matters most:**
- Bit numbering follows ASN.1 named bits: bit 0 is the most significant bit of the first content byte, and the unused-bits byte must match the highest bit set (§3.3 `#h3_examples`). Getting this backwards is the usual mistake.
- Marking the extension non-critical (§3.2.1 `#h4_fido-u2f-certificate-transports-extension`); a critical flag would make strict verifiers reject the certificate.
- The extension sits in the batch attestation certificate, so it describes the model, not one unit; it is a UI hint, not a security claim.

**Watch out for:**
- Nothing makes the extension mandatory, and RPs MAY ignore it (§3.2.1 `#h4_fido-u2f-certificate-transports-extension`); do not rely on its presence.
- The bit list predates later transports; there is no bit for anything beyond the five listed.
- Its transport set mirrors the `Transport` enum of the U2F JavaScript API (`bt`, `ble`, `usb`, `nfc`, `usb-internal`).

**Related documents:** fido-u2f-raw-message-formats (the attestation certificate inside the registration response), fido-u2f-javascript-api (transport hints given by the RP), fido-metadata-statement (attestation roots and transport-related metadata), webauthn (attestation certificate requirements built on the same FIDO OID arc).
