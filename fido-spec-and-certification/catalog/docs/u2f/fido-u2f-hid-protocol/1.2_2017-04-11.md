# FIDO U2F HID Protocol Specification

Version 1.2 · Proposed Standard · 2017-04-11 · [source](https://fidoalliance.org/specs/fido-u2f-v1.2-ps-20170411/fido-u2f-hid-protocol-v1.2-ps-20170411.html)

## Summary

Specifies U2FHID, the framing that carries U2F raw messages over USB using the HID class. Messages are split into fixed-size HID reports: an initialization packet (4-byte channel ID, command byte with bit 7 set, 2-byte payload length) followed by sequence-numbered continuation packets. Channels let several host applications share one device; `U2FHID_INIT` on the broadcast channel allocates a channel ID and returns the protocol version, device version numbers and capability flags. The document defines transaction rules (one transaction at a time, busy and timeout handling, abort and resynchronization, packet sequencing), channel locking, the USB interface and endpoint descriptors, and the HID report descriptor with the FIDO usage page used for device discovery.

Commands: mandatory `U2FHID_MSG` (wraps a raw U2F APDU), `U2FHID_INIT`, `U2FHID_PING` and `U2FHID_ERROR`; optional `U2FHID_WINK` and `U2FHID_LOCK`; and a vendor-specific command range. CTAP 2.3 lists this document as superseded by its CTAPHID transport, which uses the same FIDO usage page; U2FHID may still be implemented for backward compatibility. U2F 1.2 is the only certifiable U2F version.

**Who needs it:** authenticator vendors (USB devices), platform & client developers, test labs

**Look here for:**
- Initialization and continuation packet layouts → §2.4 `#h3_message--and-packet-structure`
- How channels are allocated and shared → §2.3 `#h3_concurrency-and-channels`, §4.1.2 `#h4_u2fhid_init`

## Reading guide

**Start here:** §2.4 `#h3_message--and-packet-structure` for the packet layouts, §2.3 `#h3_concurrency-and-channels` with §4.1.2 `#h4_u2fhid_init` for how a host gets a channel, and §2.5 `#h3_arbitration` for what happens when two applications collide.

**Section by section:**
- §2 `#h2_u2fhid-protocol-implementation`, §2.1–§2.2 `#h3_u2fhid-implementation-rationale`, `#h3_protocol-structure-and-data-framing`: U2FHID frames raw U2F messages only; over HID every raw message uses extended-length APDU encoding. Terminology: transaction (request plus response), message, packet (one HID report).
- §2.3 `#h3_concurrency-and-channels`: 32-bit channel IDs allocated by the device (algorithm vendor-specific); 0 is reserved and 0xFFFFFFFF is the broadcast channel used for allocation.
- §2.4 `#h3_message--and-packet-structure`: initialization packet (CID, CMD with bit 7 set, BCNTH/BCNTL, data) and continuation packets (CID, SEQ 0x00–0x7F); packets are always full report size, unused bytes should be zero. With 64-byte reports the maximum payload is 7609 bytes.
- §2.5 `#h3_arbitration` (§2.5.1–§2.5.4): one transaction at a time; another channel gets a busy error immediately; stalled transactions time out and the device returns to idle; a host can abort and resynchronize on its own channel; out-of-order packets are tracked and stray continuation packets ignored.
- §2.6 `#h3_channel-locking`, §2.7 `#h3_protocol-version-and-compatibility`: optional channel lock for multi-transaction vendor operations; hosts must support older device versions with the commands those versions offer.
- §3 `#h2_hid-device-implementation`, §3.1 `#h3_interface--and-endpoint-descriptors`: HID class interface with one IN and one OUT interrupt endpoint; the 64-byte / 5 ms values are the reference choice, and hosts must read the real values from the descriptors. Low-speed devices are impractical.
- §3.2 `#h3_hid-report-descriptor-and-device-discovery`: discovery works by matching the FIDO usage page and U2FHID usage in the report descriptor; report sizes should match endpoint sizes.
- §4.1 `#h3_mandatory-commands`: `U2FHID_MSG` (§4.1.1 `#h4_u2fhid_msg`), `U2FHID_INIT` (§4.1.2 `#h4_u2fhid_init`: 8-byte nonce in, nonce + CID + protocol version + three device version bytes + capability flags out, 17 bytes; hosts must accept longer responses), `U2FHID_PING` (§4.1.3 `#h4_u2fhid_ping`), `U2FHID_ERROR` (§4.1.4 `#h4_u2fhid_error`, response only, with ERR_INVALID_CMD, ERR_INVALID_PAR, ERR_INVALID_LEN, ERR_INVALID_SEQ, ERR_MSG_TIMEOUT, ERR_CHANNEL_BUSY).
- §4.2 `#h3_optional-commands`: `U2FHID_WINK` (§4.2.1 `#h4_u2fhid_wink`, advertised by CAPABILITY_WINK) and `U2FHID_LOCK` (§4.2.2 `#h4_u2fhid_lock`, 0–10 s, 0 releases). §4.3 `#h3_vendor-specific-commands`: vendor command range.

**What matters most:**
- Nonce matching on `U2FHID_INIT` responses sent on the broadcast channel, since several hosts may be allocating at once (§4.1.2 `#h4_u2fhid_init`).
- Correct busy and timeout behaviour across channels and strict sequence checking (§2.5 `#h3_arbitration`); these are where multi-application hosts break.
- Always sending full-size reports and using extended-length APDUs inside `U2FHID_MSG` (§2.4 `#h3_message--and-packet-structure`, §2 `#h2_u2fhid-protocol-implementation`).
- Endpoint sizes, intervals and numbering are the vendor's choice; hosts must not hard-code 64 bytes (§3.1 `#h3_interface--and-endpoint-descriptors`).

**Watch out for:**
- The numeric values of commands, error codes, the usage page and capability flags are not in this text; they are delegated to the [U2FHIDHeader] header file.
- §2.5.3 `#h4_transaction-abort-and-re-synchronization` talks about a SYNC command that has no entry in §4; in practice resynchronization is done through `U2FHID_INIT` on the current channel, which §4.1.2 `#h4_u2fhid_init` describes as synchronizing a channel.
- CTAP 2.3 declares this document superseded; its CTAPHID binding (CTAP §11) is the current definition and U2FHID remains only for backward compatibility.

**Related documents:** fido-u2f-raw-message-formats (payload of `U2FHID_MSG`, and the legacy `U2F_VERSION` encoding usable only over HID), fido-client-to-authenticator-protocol 2.3 (CTAPHID, which supersedes this), fido-u2f-nfc-protocol and fido-u2f-bt-protocol (other transports), fido-u2f-implementation-considerations (timing).
