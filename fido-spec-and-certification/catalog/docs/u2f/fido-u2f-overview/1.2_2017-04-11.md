# Universal 2nd Factor (U2F) Overview

Version 1.2 · Proposed Standard · 2017-04-11 · [source](https://fidoalliance.org/specs/fido-u2f-v1.2-ps-20170411/fido-u2f-overview-v1.2-ps-20170411.html)

## Summary

Non-normative introduction to FIDO Universal 2nd Factor (U2F) 1.2, meant as the first read before the detailed U2F specifications. It walks through the design: the device mints a separate key pair per origin at registration and signs a challenge at authentication; the key handle lets low-cost devices keep no per-site storage by wrapping the private key and origin hash; a different origin cannot exercise another origin's key, which blocks most phishing relays; an attestation certificate lets a relying party identify the device model; and a signature counter can expose cloned devices. It also covers the user-presence test, sharing one device among users and registering several devices to one account, the privacy recap (no global device identifier, even within one site), and extending U2F to Bluetooth LE, NFC and native apps.

U2F 1.2 is the only certifiable U2F version. CTAP 2.x refers to this protocol as CTAP1 and defines how CTAP2 clients interoperate with CTAP1/U2F authenticators, so the model described here still underpins second-factor security keys.

**Who needs it:** authenticator vendors, platform & client developers, relying parties & server developers, certification applicants (U2F)

**Look here for:**
- Why each site gets its own key pair → §4 `#h2_site-specific-public-private-key-pairs`
- How U2F resists man-in-the-middle and phishing relays → §6 `#h2_man-in-the-middle-protections-during-authentication`
- How a device can work with no per-site storage (wrapped key handles) → §7 `#h2_allowing-for-inexpensive-u2f-devices`

## Reading guide

**Start here:** §4 `#h2_site-specific-public-private-key-pairs` for the core model (per-origin key pair, key handle bound to the origin hash), then §6 `#h2_man-in-the-middle-protections-during-authentication` for what the client data and origin check buy you, then §8 `#h2_verifying-that-a-u2f-device-is-genuine` and §8.1 `#h3_counters-as-a-signal-for-detecting-cloned-u2f-devices` for attestation and counters. The whole document is informative (§1 `#h2_what-is-this-document` says so); nothing here is a conformance requirement.

**Section by section:**
- §1–§3 `#h2_what-is-this-document`, `#h2_background`, `#h2_goal-strong-authentication-and-privacy-for-the-web`: positioning against UAF, the two-layer spec split (crypto core vs transport framing) and a recommended reading order for the detailed U2F specs, top layer (JS API) down to transport.
- §4 `#h2_site-specific-public-private-key-pairs`: the device encodes the requesting origin into the key handle and refuses to sign when the origin hash presented at authentication does not match. This is what stops a key from acting as a cross-site supercookie.
- §5 `#h2_alerting-the-user-u2f-device-activation-browser-infobars`: user-presence test for registration and signing, browser infobars, and the 1.2 addition that a signature may be requested without user presence, flagged as such in the response.
- §6 `#h2_man-in-the-middle-protections-during-authentication`: client data (challenge, origin seen by the browser, optional ChannelID key) is hashed into the signed data, so the RP can detect a relay that shows the wrong origin or channel. Also spells out the case U2F does not cover: a phishing site that intercepts registration on a password-plus-optional-U2F account.
- §7 `#h2_allowing-for-inexpensive-u2f-devices`: storage options for keys, from fully wrapped key handles (private key plus origin hash encrypted under a device wrapping key) to on-board tables indexed by the handle.
- §8 `#h2_verifying-that-a-u2f-device-is-genuine`, §8.1 `#h3_counters-as-a-signal-for-detecting-cloned-u2f-devices`: batch attestation keys shared across many units (privacy), the idea of a public list of vendor attestation keys (what later became MDS), and counters kept per key, global or bucketed, signed together with the client data hash; a counter going backwards indicates a clone.
- §9 `#h2_client-malware-interactions-with-u2f-devices`: malware with direct device access is out of scope; OS-level clients can enforce origin checks.
- §10 `#h2_u2f-device-user-experience` (§10.1 `#h3_registration-creating-a-key-pair`, §10.2 `#h3_authentication-generating-a-signature`): the RP-driven flows; the first device with a positive presence test answers, and several devices may answer the same key handle.
- §11 `#h2_u2f-device-usage-scenarios`: devices know no users, so sharing one device and registering several devices per account both work; the RP sends all key handles at sign time.
- §12–§13 `#h2_u2f-privacy-considerations-a-recap`, `#h2_other-privacy-related-issues`: privacy properties, the remaining leak where an origin can test whether two of its accounts share a device (§13.1 `#h3_an-origin-can-discover-that-two-accounts-share-a-u2f-device`), and vendor-specific reset ideas for revoking keys (§13.2 `#h3_revoking-a-key-from-an-origin`).
- §14–§15 `#h2_non-usb-transports`, `#h2_expanding-u2f-to-non-browser-apps`: transports, and the AppID/facet indirection that lets a web origin and its native apps share one key; the device receives the hash of the AppID, not of the origin.

**What matters most:**
- The origin binding in the key handle (§4 `#h2_site-specific-public-private-key-pairs`) and the RP-side check of the client data origin (§6 `#h2_man-in-the-middle-protections-during-authentication`) are the two halves of phishing resistance; an RP that skips the client data check loses the second half.
- RPs need to check user presence in the response, since 1.2 allows signatures without it (§5 `#h2_alerting-the-user-u2f-device-activation-browser-infobars`).
- Counter handling is left to the RP and only detects clones when both copies are used (§8.1 `#h3_counters-as-a-signal-for-detecting-cloned-u2f-devices`).
- Key-handle wrapping is not specified by the protocol; §8 `#h2_verifying-that-a-u2f-device-is-genuine` points to certification as the way to judge it.

**Watch out for:**
- Parts of the text are older than 1.2: §3 `#h2_goal-strong-authentication-and-privacy-for-the-web` says only USB is specified while §14 `#h2_non-usb-transports` lists USB, BLE and NFC, and the §1 reading list uses old document names (for example "USB Framing of APDUs" for the HID spec).
- ChannelID (§6 `#h2_man-in-the-middle-protections-during-authentication`) is optional and only helps when both browser and origin use it; without it, the document admits a MITM holding a valid certificate for the real origin goes undetected.
- The attestation publishing mechanism in §8 `#h2_verifying-that-a-u2f-device-is-genuine` is described as future work; the real mechanism is the Metadata Service.

**Related documents:** fido-u2f-raw-message-formats (the actual bytes behind §4–§8), fido-u2f-javascript-api (the browser calls in §10), fido-u2f-implementation-considerations (timing, key handles, counters), fido-appid-and-facets (§15), fido-u2f-hid-protocol / fido-u2f-nfc-protocol / fido-u2f-bt-protocol (transports), fido-client-to-authenticator-protocol 2.3 (§10 maps CTAP2 onto CTAP1/U2F), fido-metadata-service (attestation trust today).
