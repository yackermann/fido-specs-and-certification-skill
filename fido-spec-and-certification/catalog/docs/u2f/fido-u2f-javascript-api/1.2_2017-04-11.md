# FIDO U2F JavaScript API

Version 1.2 · Proposed Standard · 2017-04-11 · [source](https://fidoalliance.org/specs/fido-u2f-v1.2-ps-20170411/fido-u2f-javascript-api-v1.2-ps-20170411.html)

## Summary

Defines the JavaScript API that relying-party web pages used to reach U2F tokens through the browser before WebAuthn. There are two levels: a required low-level MessagePort API with request and response dictionaries, and an optional high-level `u2f.register` / `u2f.sign` API that wraps it with callbacks. A registration request carries the AppID, one RegisterRequest per accepted protocol version and the already registered keys (so the client can skip tokens that are registered already). A sign request carries the AppID, a challenge and the registered keys. Responses return the protocol version, the raw token output and the client data, websafe-base64 encoded. The document also defines the transport hints (`bt`, `ble`, `nfc`, `usb`, `usb-internal`), the error codes (OK, OTHER_ERROR, BAD_REQUEST, CONFIGURATION_UNSUPPORTED, DEVICE_INELIGIBLE, TIMEOUT) and backward compatibility with the 1.0 `signRequests` form.

Browsers now expose WebAuthn instead, whose `appid` extension lets a site keep using credentials registered through this API. U2F 1.2 is the only certifiable U2F version.

**Who needs it:** relying parties & server developers (legacy U2F deployments), platform & client developers

## Reading guide

**Start here:** the non-normative Background `#h2_background` (what changed from the 1.0 API and the advice to avoid the low-level port), §3.2.1 `#h4_methods` for the `u2f.register` / `u2f.sign` signatures, then §5.1 `#h3_registration` and §5.2 `#h3_generating-signed-identity-assertions` for what the RP prepares and receives.

**Section by section:**
- §3 `#h2_api-levels`, §3.1 `#h3_low-level-messageport-api`: the MessagePort level is the required one; how a page obtains the port is left to the browser. `U2fRequest` (§3.1.1 `#h4_dictionary-u2frequest-members`) has `type`, `appId` (defaults to the page origin), `timeoutSeconds` and `requestId`, which the client MUST echo. `U2fResponse` (§3.1.2 `#h4_dictionary-u2fresponse-members`) carries either a response or an `Error` (§3.1.3 `#h4_dictionary-error-members`), recognized by a non-zero `errorCode`.
- §3.2 `#h3_high-level-javascript-api`: optional `u2f` namespace; callbacks MUST receive either the response or an Error object.
- §4 `#h2_u2f-transports`: the `Transport` values `bt`, `ble`, `nfc`, `usb`, `usb-internal`, given by the RP as hints per key handle.
- §5.1 `#h3_registration` (§5.1.1–§5.1.4): the RP MUST choose versions, an AppID and a random challenge; one `RegisterRequest` per version (the client SHOULD treat the order as priority), plus a `RegisteredKey` (§5.1.2 `#h4_dictionary-registeredkey-members`) for each token already registered, which SHOULD be supplied so the client registers a new token only. `RegisterResponse` (§5.1.4 `#h4_dictionary-registerresponse-members`) returns `version`, `registrationData` and `clientData`, both websafe-base64.
- §5.2 `#h3_generating-signed-identity-assertions` (§5.2.1–§5.2.2): one challenge and AppID for all `registeredKeys`; a per-key `appId` is allowed but ordinarily omitted. The client verifies the caller's application identity, builds client data and the raw authenticate message, and SHOULD try every key handle on every transport it supports whatever the hints say. `SignResponse` returns `keyHandle`, `signatureData`, `clientData`; if several tokens answer, the client returns one.
- §5.3 `#h3_error-codes`, §5.3.1 `#h4_constants`: OK (reserved), OTHER_ERROR, BAD_REQUEST, CONFIGURATION_UNSUPPORTED, DEVICE_INELIGIBLE (already registered on register, unknown key handle on sign), TIMEOUT.
- §5.4 `#h3_backward-compatibility-with-u2f-1.0-api`: RPs MAY send 1.0-style `SignRequest` objects and clients MAY accept `signRequests` in place of `registeredKeys`.

**What matters most:**
- Server-side verification is outside this document: the RP decodes `registrationData`, `signatureData` and `clientData` and checks them per the raw message formats (§5.1.4 `#h4_dictionary-registerresponse-members`, §5.2.2 `#h4_dictionary-signresponse-members`).
- Passing the existing `registeredKeys` on registration is what prevents double registration and produces DEVICE_INELIGIBLE (§5.1 `#h3_registration`, §5.3.1 `#h4_constants`).
- AppID choice at registration is permanent for those keys (§5.1 `#h3_registration`); it is also the value a WebAuthn RP later supplies through the `appid` extension.
- Detect errors by a non-zero `errorCode`, never by the absence of response fields (§3.1.2 `#h4_dictionary-u2fresponse-members`, §3.2.1 `#h4_methods`).

**Watch out for:**
- The Background `#h2_background` still calls this version 1.1, and it discourages direct use of the MessagePort level that §3 `#h2_api-levels` calls required.
- Example 1 in §3.2.1 `#h4_methods` calls `u2f.sign(reqs, callback)`, the old 1.0 shape, not the 1.2 signature shown above it.
- This API is legacy: browsers expose WebAuthn instead. Do not carry these `Transport` strings over to WebAuthn unchecked.

**Related documents:** fido-u2f-raw-message-formats (contents of `registrationData`, `signatureData`, `clientData`), fido-appid-and-facets (AppID rules and facet checking), fido-u2f-overview, webauthn (the replacement API and its `appid` extension), fido-u2f-implementation-considerations (challenge entropy).
