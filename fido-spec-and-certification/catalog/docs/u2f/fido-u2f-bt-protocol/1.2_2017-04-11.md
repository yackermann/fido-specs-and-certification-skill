# FIDO Bluetooth® Specification v1.0

Version 1.2 · Proposed Standard · 2017-04-11 · [source](https://fidoalliance.org/specs/fido-u2f-v1.2-ps-20170411/fido-u2f-bt-protocol-v1.2-ps-20170411.html)

## Summary

Specifies how U2F messages travel over Bluetooth Low Energy (titled FIDO Bluetooth Specification v1.0 inside the U2F 1.2 suite). Both sides must conform to Bluetooth Core 4.0 or later. Clients and authenticators must pair, keep a long-term key and encrypt everything, and the authenticator must require LE Security Mode 1 Level 2 or 3 before any U2F traffic. The authenticator exposes the FIDO U2F GATT service (UUID 0xFFFD) with characteristics u2fControlPoint (client writes requests), u2fStatus (notifications carry responses), u2fControlPointLength, u2fServiceRevision and u2fServiceRevisionBitfield, alongside the Device Information and Generic Access services. Requests and responses use a small framing with commands PING, KEEPALIVE (status PROCESSING or TUP_NEEDED), MSG and ERROR, and long messages are fragmented to the control-point length. The document also covers advertising flags for pairing and non-pairing mode, notifications, and client- and authenticator-side guidance on pairing, throughput and address types.

CTAP 2.3 lists this document as superseded by its own BLE binding, which keeps the 0xFFFD service UUID; the U2F version may still be implemented for backward compatibility. U2F 1.2 is the only certifiable U2F version.

**Who needs it:** authenticator vendors (BLE devices), platform & client developers, test labs

## Reading guide

**Start here:** §7 `#h2_protocol-overview` for the end-to-end sequence, §5 `#h2_framing` for the frame format and constants, §6.1 `#h3_u2f-service` for the GATT service, and §13.3 `#h3_handling-command-completion` for the timing constants that govern connection life.

**Section by section:**
- §2 `#h2_conformance`: both sides SHALL conform to Bluetooth Core 4.0 or later. Despite the title, only Bluetooth Low Energy is specified.
- §3 `#h2_pairing`, §4 `#h2_link-security`: clients and authenticators MUST bond with a long-term key and SHALL encrypt everything; short-term keys are forbidden. The authenticator SHALL enforce LE Security Mode 1 Level 2 or 3 before any U2F message. Pairing is the only way the client knows it has the right device.
- §5.1–§5.2 `#h3_request-from-client-to-authenticator`, `#h3_response-from-authenticator-to-client`: CMD/STAT byte plus 2-byte length. Clients send PING or MSG; a response whose status equals the request command is success, ERROR carries an encapsulation-layer error code. U2F status words (for example 0x6985) travel inside a successful MSG response. All APDUs SHALL use extended-length encoding.
- §5.3 `#h3_command-status-and-error-constants`: PING 0x81, KEEPALIVE 0x82, MSG 0x83, ERROR 0xBF; keep-alive status PROCESSING 0x01 / TUP_NEEDED 0x02; error codes 0x01–0x05 and ERR_OTHER 0x7F, with 0x06, 0x0A, 0x0B reserved because HID uses them.
- §6 `#h2_gatt-service-description`: authenticator is GATT server, client is GATT client, with mandatory sub-procedures listed for each.
- §6.1 `#h3_u2f-service`: primary service 0xFFFD with u2fControlPoint (write, 20–512 bytes), u2fStatus (notify), u2fControlPointLength (read, 20–512), u2fServiceRevision (0x2A28, `1.0`) and u2fServiceRevisionBitfield (bit 7 = 1.1, bit 6 = 1.2). When more than one version is offered the client SHALL write the chosen version for the connection.
- §6.2 `#h3_device-information-service`, §6.3 `#h3_generic-access-profile-service`: DIS with manufacturer, model and firmware strings (not uniquely identifying) and GAP device name and appearance.
- §8 `#h2_authenticator-advertising-format`: advertise the 0xFFFD UUID; pairing mode uses exactly one of LE Limited / LE General Discoverable, non-pairing mode clears both; DIS SHALL include PnP ID.
- §9–§10 `#h2_requests`, `#h2_responses`: writes to the control point, replies by notification. The authenticator SHALL send KEEPALIVE every kKeepAliveMillis while working; clients SHALL NOT resend on KEEPALIVE and SHALL NOT switch devices on TUP_NEEDED before their own timeout.
- §11 `#h2_framing-fragmentation`: initialization fragment (high bit set in the first byte, total length) and continuation fragments with SEQ 0x00–0x7F that wraps to 0; fragment size is the control-point length for writes and ATT_MTU−3 for notifications.
- §12 `#h2_notifications`: notification subscription persists per bond; clients MUST NOT cache the subscription state themselves.
- §13 `#h2_implementation-considerations`: system-wide pairing risk (§13.1 `#h3_bluetooth-pairing-client-considerations`), pairing-mode design and the Service Data flags for platforms such as iOS (§13.2 `#h3_bluetooth-pairing-authenticator-considerations`), command completion rules with kMaxCommandTransmitDelayMillis 1500 ms, kErrorWaitMillis 2000 ms and kKeepAliveMillis 500 ms (§13.3 `#h3_handling-command-completion`), throughput (§13.4 `#h3_data-throughput`), advertising channels (§13.5 `#h3_advertising`) and resolvable private addresses (§13.6 `#h3_authenticator-address-type`).

**What matters most:**
- Enforcing encryption and bonding before any U2F traffic, and only accepting reconnections from bonded clients without user action (§4 `#h2_link-security`, §7 `#h2_protocol-overview`).
- Keep-alive cadence (at least every 500 ms while processing or waiting for presence) and the client's no-resend rule (§10 `#h2_responses`); KEEPALIVE is the only signal a client gets that the device is still working.
- Fragment sizes taken from u2fControlPointLength and the MTU, with correct sequence wrap (§11 `#h2_framing-fragmentation`).
- Connection lifetime: the client MUST send the next command within 1500 ms, and the authenticator MUST keep the link at least 2000 ms after a response that did not consume user presence (§13.3 `#h3_handling-command-completion`).
- Version negotiation through the two revision characteristics (§6.1 `#h3_u2f-service`).

**Watch out for:**
- The revision values (1.0, 1.1, 1.2) are versions of this Bluetooth specification, not of U2F, and the bitfield has no bit for 1.0.
- Many §13 `#h2_implementation-considerations` items are advice, but §13.3 `#h3_handling-command-completion` contains MUST-level rules hidden under that heading.
- The u2fServiceRevision length is given as 20–512 bytes in the table although the defined value is 3 bytes.
- CTAP 2.3 declares this document superseded by its BLE binding (CTAP §11); the U2F version remains for backward compatibility.

**Related documents:** fido-u2f-raw-message-formats (MSG payload), fido-client-to-authenticator-protocol 2.3 (current BLE binding and CTAP1/U2F interop), fido-u2f-hid-protocol (shared error code space), fido-u2f-implementation-considerations, fido-u2f-authenticator-transports-extension (`bluetoothLowEnergyRadio` bit in the attestation certificate).
