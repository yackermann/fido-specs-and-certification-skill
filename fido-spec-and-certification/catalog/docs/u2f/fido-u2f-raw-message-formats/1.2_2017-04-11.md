# FIDO U2F Raw Message Formats

Version 1.2 · Proposed Standard · 2017-04-11 · [source](https://fidoalliance.org/specs/fido-u2f-v1.2-ps-20170411/fido-u2f-raw-message-formats-v1.2-ps-20170411.html)

## Summary

Normative definition of the transport-independent U2F messages exchanged between a FIDO client and a U2F token, encoded as ISO 7816-4 style APDUs (short or extended length). It defines three commands: `U2F_REGISTER` (INS 0x01), `U2F_AUTHENTICATE` (INS 0x02, with control byte 0x03 enforce-user-presence-and-sign, 0x07 check-only, 0x08 dont-enforce-user-presence-and-sign) and `U2F_VERSION` (INS 0x03, which returns the string `U2F_V2`), plus a vendor-specific INS range. It gives the byte layout of each request and response: the registration response carries the 0x05 reserved byte, the uncompressed P-256 public key, the key handle, an X.509 attestation certificate and an ECDSA signature; the authentication response carries a user-presence byte, a 4-byte big-endian counter and a signature. It lists the status words with U2F meaning (0x9000, 0x6985, 0x6A80, 0x6700, 0x6E00, 0x6D00) and the ClientData JSON (`typ`, `challenge`, `origin`, `cid_pubkey`) that the client builds and hashes (SHA-256) into the challenge parameter; the application parameter is the SHA-256 of the AppID.

The HID, NFC and Bluetooth specifications carry these messages. CTAP 2.x calls them CTAP1/U2F messages, lists this document as superseded (still allowed for backward compatibility) and maps its own commands onto them for older authenticators. U2F 1.2 is the only certifiable U2F version.

**Who needs it:** authenticator vendors, platform & client developers, relying parties & server developers (signature verification), test labs

## Reading guide

**Start here:** §2 `#h2_introduction` for the setup / processing / verification phases and the request-vs-response naming trap, §3.1.1 `#h4_command-and-parameter-values` for the command table, then §4.3 `#h3_registration-response-message-success` and §5.4 `#h3_authentication-response-message-success`, which define exactly which bytes are signed.

**Section by section:**
- §3 `#h2_u2f-message-framing`: ISO 7816-4 APDU framing. CLA is reserved for the transport and set to 0 by the host. §3.1.2 `#h4_short-encoding` and §3.1.3 `#h4_extended-length-encoding` give Lc/Le rules; which encoding a transport allows is decided by the transport spec, not here.
- §3.3 `#h3_status-codes`: the six status words a FIDO client acts on (0x9000, 0x6985 user presence required, 0x6A80 bad key handle, 0x6700, 0x6E00, 0x6D00). Vendor codes are allowed but clients treat them as generic errors.
- §4.1 `#h3_registration-request-message---u2f_register`: challenge parameter = SHA-256 of the client data; application parameter = SHA-256 of the UTF-8 AppID.
- §4.2–§4.3 `#h3_registration-response-message-error-test-of-user-presence-required`, `#h3_registration-response-message-success`: tokens SHOULD test user presence before registering. The success response is 0x05, 65-byte uncompressed P-256 key, key-handle length and handle, DER attestation certificate (its length comes from parsing it), then an ECDSA signature over 0x00 | appParam | challengeParam | keyHandle | publicKey, verified with the attestation certificate key.
- §5.1 `#h3_authentication-request-message---u2f_authenticate`: control byte chosen by the client, never the RP: 0x07 check-only, 0x03 enforce presence, 0x08 presence optional. Check-only is only for detecting an already registered token during registration; real authentications MUST use 0x03 or 0x08.
- §5.2–§5.3 `#h3_authentication-response-message-error-test-of-user-presence-required`, `#h3_authentication-response-message-error-bad-key-handle`: error cases; a key handle from another token or for another AppID MUST give bad-key-handle.
- §5.4 `#h3_authentication-response-message-success`: user-presence byte (bit 0, other bits SHALL be 0), 4-byte big-endian counter, signature over appParam | presence byte | counter | challengeParam, verified with the registered public key.
- §6 `#h2_other-messages`: `U2F_VERSION` returns `U2F_V2` with no terminator; vendor INS range 0x40–0xBF, never sent by the FIDO client.
- §7 `#h2_client-data`: ClientData (`typ`, `challenge`, `origin`, `cid_pubkey`) and the ChannelID JwkKey (§7.2 `#h3_dictionary-jwkkey-members`). The client MUST send the client data itself to the RP so the RP can rehash it.
- §8 `#h2_examples`: complete registration and authentication vectors with keys, hashes and signature base strings; useful as server test vectors.
- §9 `#h2_implementation-considerations`: the pre-1.2 `U2F_VERSION` layout that was not ISO 7816-4 compliant; clients may still accept it over HID.

**What matters most:**
- Building the signature base strings in the exact order of §4.3 `#h3_registration-response-message-success` and §5.4 `#h3_authentication-response-message-success`; note the key-handle length byte is not signed at registration and the presence byte and counter sit between the two hashes at authentication.
- The check-only reply is 0x6985, which signals success despite being an error status (§5.1 `#h3_authentication-request-message---u2f_authenticate`). Clients and conformance tests rely on it.
- RPs should check the presence bit, since 0x08 allows signatures without user presence (§5.1 `#h3_authentication-request-message---u2f_authenticate`, §5.4 `#h3_authentication-response-message-success`).
- RPs must recompute the challenge parameter from the received client data and check `typ`, `challenge` and `origin` (§7.1 `#h3_dictionary-clientdata-members`).

**Watch out for:**
- CTAP 2.3 states that this document is superseded by CTAP; it remains usable for backward compatibility, and CTAP §10 restates the framing and maps CTAP2 requests onto these commands.
- Trust in the attestation certificate is declared out of scope here (§4.3 `#h3_registration-response-message-success`); use the Metadata Service.
- `cid_pubkey` (ChannelID) is optional: absent when the browser lacks ChannelID, the string `unused` when the origin does not use it, a JwkKey otherwise (§7.1 `#h3_dictionary-clientdata-members`). RP parsers must accept all three forms.
- Numeric constants are said to live in an external header file ([U2FHeader]); the command table in §3.1.1 `#h4_command-and-parameter-values` is the in-document source.

**Related documents:** fido-u2f-hid-protocol, fido-u2f-nfc-protocol, fido-u2f-bt-protocol (how these APDUs travel), fido-u2f-javascript-api (base64 wrapping of these messages for web pages), fido-u2f-implementation-considerations (counter rules referenced from §5.4), fido-appid-and-facets (the AppID behind the application parameter), fido-client-to-authenticator-protocol 2.3 (supersedes this and defines CTAP1/U2F interop), fido-u2f-authenticator-transports-extension (optional extension in the attestation certificate).
