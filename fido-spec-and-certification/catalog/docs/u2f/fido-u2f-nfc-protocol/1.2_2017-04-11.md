# FIDO NFC Protocol Specification v1.0

Version 1.2 · Proposed Standard · 2017-04-11 · [source](https://fidoalliance.org/specs/fido-u2f-v1.2-ps-20170411/fido-u2f-nfc-protocol-v1.2-ps-20170411.html)

## Summary

Short specification of how a FIDO client talks to a U2F authenticator over NFC. No extra framing is added: commands are the U2F raw message APDUs, in short or extended length encoding. Each session starts with a SELECT of the FIDO U2F applet (AID `A0000006472F0001`), to which the authenticator answers with its version string `U2F_V2`; register and authenticate commands follow. The authenticator has to answer every command within 800 ms. When a response does not fit a short APDU, it must reply in extended length if the request used extended length, or else use ISO 7816-4 response chaining. The implementation considerations recommend designing the contactless interface to ISO/IEC 14443 or ISO/IEC 18092.

CTAP 2.3 lists this document as superseded by its own NFC binding, which keeps the same applet AID; the U2F binding may still be implemented for backward compatibility. U2F 1.2 is the only certifiable U2F version.

**Who needs it:** authenticator vendors (NFC devices), platform & client developers, test labs

**Look here for:**
- Overall command sequence and the 800 ms response limit → §2 `#h2_protocol`
- Whether any NFC-specific framing is used → §3 `#h2_framing`
- Extended length vs APDU chaining for long responses → §4 `#h2_apdu-length`
- Applet AID and the SELECT response → §5 `#h2_applet-selection`
- Which contactless standards to design and test against → §6 `#h2_implementation-considerations`

## Reading guide

**Start here:** the document is four short normative sections; read §2 `#h2_protocol` through §5 `#h2_applet-selection` in order, then §6 `#h2_implementation-considerations` for the RF-layer standards.

**Section by section:**
- §2 `#h2_protocol`: session order is applet SELECT, success, then register or authenticate commands. The authenticator MUST answer every command within 800 ms.
- §3 `#h2_framing`: no NFC-specific framing (SHALL NOT add any); commands are the raw U2F APDUs, and both short and extended-length encodings are allowed.
- §4 `#h2_apdu-length`: for responses too large for a short APDU, the authenticator MUST answer in extended length if the request was extended, and MUST use ISO 7816-4 response chaining if the request was short.
- §5 `#h2_applet-selection`: the client SHALL always start with SELECT of AID `A0000006472F0001` (RID A000000647, AC 2F, AX 0001). The authenticator SHALL return its version string, `U2F_V2` followed by 9000; later versions MAY return other strings.
- §6 `#h2_implementation-considerations`: authenticators should follow ISO/IEC 14443 or ISO/IEC 18092 and have independent conformance testing; phones acting as readers should follow NFC Forum Analog 2.0 or later.

**What matters most:**
- The 800 ms response limit applies to every command (§2 `#h2_protocol`); token firmware has to fit key unwrapping and signing into it, and the document gives no keep-alive mechanism for NFC.
- Supporting both short-APDU chaining and extended length, matched to the request encoding (§4 `#h2_apdu-length`); a registration response with its attestation certificate is normally longer than 256 bytes.
- Answering SELECT with the version string, not an empty 9000 (§5 `#h2_applet-selection`); clients use it to tell U2F from other applets.
- Clients should not assume the version string is always `U2F_V2` (§5 `#h2_applet-selection`).

**Watch out for:**
- §4 `#h2_apdu-length` refers to a "Section A.4" and promises an example that the published document does not contain; take the chaining details from ISO 7816-4 itself.
- The document says nothing about how user presence is established over NFC; the raw message semantics apply unchanged.
- CTAP 2.3 lists this document as superseded by its own NFC binding (CTAP §11); the U2F binding remains for backward compatibility.

**Related documents:** fido-u2f-raw-message-formats (the APDUs carried here, short and extended encodings), fido-client-to-authenticator-protocol 2.3 (current NFC binding, CTAP1/U2F interop), fido-u2f-hid-protocol and fido-u2f-bt-protocol (other transports), fido-u2f-implementation-considerations (timing guidance).
