# Functional Certification

Version 1.3.9 · Final · 2021-10-10 · **ACTIVE** · [source](https://fidoalliance.org/wp-content/uploads/2021/10/Functional_Certification_Program_Policy_v1.3.9_FINAL.pdf)

## Summary

The Functional Certification Program Policy governs FIDO functional (conformance and interoperability) certification for U2F, UAF and FIDO2 servers, clients and authenticators. Each implementation is certified on its own. Certification passes through three steps: Conformance Self-Validation with the FIDO test tools, interoperability testing at an Interoperability Event or through On Demand testing, and Certification Issuance. Applicants submit a Certification Request, test tool results, interop results, a signed Vendor Self-Assertion Checklist and fees. UAF and U2F authenticators must also register metadata. Authenticators do not receive a Functional Certificate. They must pass Level 1 Authenticator Certification, with some L1 security requirements demonstrated during interop, and then follow the Authenticator Certification Policy. The policy also covers the First Implementer and Universal Server programs, derivative certification, use of the certification mark, revocation and disputes.

Two sunset rules apply. A superseded specification version is retired at least 6 months (servers) or 18 months (clients and authenticators) after the new version's Certification Availability Date. Policy versions follow Major.Minor.Patch: a Minor version sunsets 90 days after publication, and a Patch version replaces its predecessor immediately. In v1.3.9, CTAP1/CTAP2 certification is clarified and the authenticator profile (consumer, enterprise, hybrid) appears on certificates. The document is PDF only, so the references below give section numbers and pages instead of anchors.

**Who needs it:** certification applicants (server, client and authenticator vendors), relying parties deploying derivative servers

**Look here for:**
- What are the steps to functional certification? → §3 (p. 15)
- When does an old specification or policy version stop being accepted? → §2.3 (p. 12–13), §2.4.1 Table 2 (p. 14)
- Which L1 security requirements are checked during interop, and how does that relate to the Vendor Questionnaire? → §5.4.4, §5.4.4.1 (p. 34–36)
- What must be submitted for certification, and what are the possible outcomes? → §6.3 (p. 37–39)
- Does a product qualify for derivative certification? → §7, Table 7-1 (p. 42–43)

## Reading guide

**Start here:** §3 Functional Certification Process Overview (p. 15–16) for the three steps and the rule that certification never expires. Then §2 Overall Functional Certification Policies (p. 11) for what counts as one implementation and the CTAP1/CTAP2 and profile rules. §6.3 Certification Requests and Issuance (p. 37–39) lists what you submit. Authenticator vendors should add §5.4.4 (p. 34–36) and §6.1 (p. 37), because their path ends in Authenticator Certification, not in a functional certificate. The PDF has no anchors; section numbers and pages below follow the TOC.

**Section by section:**
- §2 Overall Functional Certification Policies (p. 11): eight implementation classes (UAF server, client, authenticator and client/authenticator combo; U2F server and authenticator; FIDO2 server and authenticator). Each implementation is certified in full, even inside one device, and certification belongs to the implementation, not the SDK or company. An authenticator that also supports CTAP1 must pass both CTAP1 and CTAP2 conformance, with one interop, one Vendor Questionnaire and one certificate. CTAP 2.1 authenticators claiming the hybrid profile must run and pass the hybrid test cases and declare the profile on the Self-Assertion Checklist.
- §2.1 FIDO First Implementer (p. 11–12) and §2.2 Universal Server (p. 12): First Implementer lets early adopters of a new spec claim conformance, but not "FIDO Certified", when no full interop matrix exists. It requires mandatory features, a passing test tool run and a TMLA, and ends once full certification becomes possible. Universal Server means passing both UAF and FIDO2 server certification.
- §2.3 Specification Version Retirement (p. 12–13): a version is available once the first interop event can be held (two implementations per class from different companies). The old version sunsets at least 6 months later for servers and at least 18 months for clients and authenticators.
- §2.4 Policy Version Retirement and §2.4.1 Table 2 (p. 13–14): Major.Minor.Patch versioning. Minor versions sunset 90 days after publication, patches replace the previous version immediately, and after a Major sunset no derivatives are allowed against the old version.
- §4 Conformance Self-Validation (p. 17–19): "trust but verify" with the FIDO test tools. UAF authenticators first need a Vendor ID (one per company, part of the AAID). The official run must go start to finish with no reboot, crash or reconfiguration. After it, the implementation is frozen, and interop must happen within 90 days. §4.1.1 routes test tool bugs through dispute resolution. §4.2 and §4.2.1 cover reference implementations, including browsers used as FIDO2 reference clients.
- §5.2 Interoperability Testing Events (p. 21–25): register 14 days ahead, with test tool results confirmed 7 days before. Missing the first half-day forfeits the event. §5.2.6 requires two implementations per class from different companies and a full matrix with 100% interoperability. Code changes during the event mean re-running all tests and conformance. Failures are assigned by root cause, and results are final with no re-test after the event. §5.2.3.1 covers confidential certification, §5.2.5 the 50% credit for returning certified implementations.
- §5.3 On Demand Testing (p. 25–31): virtual only, facilitated by the Secretariat against at least three reference implementations per class from different companies (at most six, about half market leaders). The vendor cannot choose them, and a re-test uses the same matrix. Not available for new technology until the reference library is large enough (§5.3.1).
- §5.4.1–5.4.3 Interoperability Testing Procedures (p. 32–34): UAF tests register, authenticate, transaction and de-register, with authentication caching disabled. U2F uses Chrome's native client, and servers must handle negative register and authenticate when the client can produce them. FIDO2 covers register, authenticate, Client PIN, resident key, server key, multi-account and ignoring unknown extensions, plus the browser+internal authenticator combo. In all three, the server must have the authenticator's metadata installed, registered with FIDO.
- §5.4.4 Level 1 Authenticator Certification Testing Procedures and §5.4.4.1 Vendor Questionnaire Instructions (p. 34–36): Table 3 lists Security Requirements (1.4, 1.9, 3.1, 3.2, 3.4, 3.9, 3.11, 4.4, 4.8, 4.11, 6.2, 6.3, per protocol) that L1 authenticators demonstrate to the proctor during interop. The interop results then serve as VQ evidence. L1+ and higher skip this; a lab evaluates instead.
- §6 Certification Issuance (p. 37–41): authenticators get no functional certificate (§6.1). §6.3 lists entry conditions (good standing, invoices paid, a product intended for commercial use) and submissions per implementation, with Vendor ID and metadata for UAF and metadata per transport for U2F. Decision within 30 days: approval, rejection (three resubmissions before failure), delay or failure. Certificate contents include the authenticator profile and the number format `SSSVVVVDDDDDDDDNNN`. §6.4 Revocation gives 30–180 days to fix a problem, and the Board Certification Committee decides.
- §7 Derivative Certification (p. 42–45): Table 7-1 scenarios. Cosmetic variants, bug-fix releases and non-FIDO feature additions need nothing; a changed FIDO function needs full certification. Derivative servers (relying parties using a certified server) only sign the website trademark agreement (§7.1). Client derivatives follow the Derivative Test Plan without interop (§7.2). Authenticators are redirected to the Authenticator Certification Policy. §7.3 allows batching derivatives of one base, and matcher-level changes at L1 need a FIAR reviewed by the Security Secretariat.
- §8 Certification Mark Usage and §9 Certification Administration (p. 46–47): the mark requires certification plus a signed TMLA, and confidential certifications cannot use it. Misuse is reviewed monthly. Disputes go to the Certification Review Team; §9.2 sets up a troubleshooting team of up to five people.
- Appendix A, Table A-1 (p. 48 onward): checklist of every action with where to submit, whether a fee applies and processing time.

**What matters most:**
- An uninterrupted official conformance run, then no changes, then interop within 90 days (§4.1, p. 17–18). Any change resets the clock.
- 100% interoperability with every matrix partner (§5.2.6, p. 24–25; §5.3.7.1, p. 30). A single failed pairing fails you if the root cause is on your side, and event results are final.
- Authenticators must pass conformance and interop on every transport they support (§3, p. 15) and must go on to at least L1 Authenticator Certification (§5.4.3–5.4.4, §6.1). Plan the Table 3 demonstrations before the interop slot.
- CTAP1+CTAP2 authenticators and hybrid-profile claims (§2, p. 11): select the right test cases, because the profile printed on the certificate comes from the test tool report and the checklist.
- Derivative eligibility (§7, Table 7-1): any added, removed or modified FIDO functionality means a new certification, not a derivative.

**Watch out for:**
- Leftovers from earlier versions. The 1.3.9 revision history removes shipped and in-person interop types, yet §6.3 still lists "On Demand, Shipped" and "In-Person" on certificates, and §5.3.4 still mentions an In-Person Testing Request.
- §2.4.1 Table 2 gives Major policy versions the spec sunset periods (6 or 18 months after the Certification Availability Date), which mixes the two sunset rules of §2.3 and §2.4.
- §5.3.6.1 requires three reference implementations per class for On Demand, but the pass criteria in §5.3.7.1 repeat the event rule of two per class. §5.3.1 sends new technology to interop events with a pointer to §5.1, which is informal testing; the events are §5.2.
- §5.4.3 says "All UAF, U2F and FIDO2 implementations" must pass L1 testing; read it as authenticators, as §5.4.4 and §6.1 do.
- Dated from 2021: requirement numbers in Table 3 refer to the Authenticator Security Requirements of that time, so check them against the current `fido-authenticator-security-requirements` and the FIDO certification website before relying on them.

**Related documents:** `fido-authenticator-certification-policy` (where authenticators continue after functional testing, including derivative, delta and recertification). `fido-authenticator-security-requirements` (the L1 requirements in Table 3 and the Vendor Questionnaire). `fido-server-requirements` (what FIDO2 server certification tests). `fido-metadata-statement` (the metadata authenticators must register). `fido-biometric-component-certification-policy` for the separate biometric program.
