# Server Requirements (WebAuthn Level 3 and CTAP2.3)

Version 2.3 · Review Draft · 2026-02-26 · **ACTIVE (FIDO2 servers: WebAuthn L3 + CTAP 2.3)** · [source](https://fidoalliance.org/specs/fidoserver/fido-server-v2.3-rd-20260226.html)

## Summary

The FIDO2 Server Requirements bring together, in one place, the WebAuthn rules that apply to a FIDO2 server (relying-party side). They also set which optional features a server must support so that it works with as many authenticators as possible. Servers must use fresh random challenges and validate attestations, including certificate chains and lookups through the FIDO Metadata Service. They must support basic and self attestation, the packed, TPM, U2F and Android SafetyNet formats (Android Key is optional), and assertion verification with UP/UV flag checks. They must be able to run without any extensions, and the appid extension is recommended. The document also lists COSE algorithms and curves as Required, Recommended or Optional. RS1, RS256, ES256, P-256 and Ed25519 are among the required entries. For deprecated polymorphic identifiers such as ES256, servers should also accept the fully specified forms such as ESP256, while still requesting the old identifier. Servers must also follow the FIDO privacy principles.

v2.3 targets WebAuthn Level 3 and CTAP 2.3. It is a Review Draft, but FIDO lists it as the active requirement set for FIDO2 server functional certification. Certification is run under the Functional Certification Program Policy.

**Who needs it:** relying parties and FIDO2 server developers, server certification applicants

**Look here for:**
- How must a server validate attestations, and which attestation types must it accept? → §2.1 `#validating-attestation`, §2.2 `#attestation-types`
- Which attestation formats are mandatory? → §2.3 `#attestation-formats`
- What must a server check when verifying an assertion? → §3 `#authn-and-assertion`
- Which extensions must or should a server handle? → §5 `#extensions`
- Which COSE algorithms and curves are required? → §6 `#other`

## Reading guide

**Start here:** §1 Introduction `#intro` for the two framing rules (WebAuthn wins on conflict; the wire protocol between app and server is free as long as signed bytes survive unchanged), then §2 `#registration-and-attestation` and §6 `#other`, which together hold almost every MUST in the document. The document is short and mostly points into WebAuthn: read it with `webauthn` open at §7.1, §7.2 and §8.

**Section by section:**
- §1 Introduction `#intro`: no transport is mandated (REST or anything else), but protocols MUST NOT alter signed objects such as `clientDataJSON` and `attestationObject`. Field names in WebAuthn are for convenience; the server may use its own.
- §2 Registration and Attestations `#registration-and-attestation`: registration is mandatory, and every request MUST use a fresh random challenge. Fixed, counter-based or otherwise predictable challenges are called out as unacceptable.
- §2.1 Validating Attestations `#validating-attestation`: the RP steps of WebAuthn §7.1 are normative for servers. Servers MUST validate attestation certificate chains and MUST be able to validate through the FIDO Metadata Service. Allow/deny or step-up policies based on metadata are MAY.
- §2.2 Attestation Types `#attestation-types`: basic and self attestation MUST; Privacy CA (AttCA) and ECDAA MAY.
- §2.3 Attestation Formats `#attestation-formats` with §2.3.1–2.3.5 (`#packed-attestation`, `#tpm-attestation`, `#android-key-attestation`, `#android-attestation`, `#u2f-attestation`): packed, TPM, U2F and Android SafetyNet MUST be supported and validated with the matching WebAuthn §8 "Validation Procedure"; Android Key is MAY. Other registry formats are MAY, and new formats SHOULD be registered.
- §3 Authentication and Assertions `#authn-and-assertion`: authentication MUST be supported, with a random challenge per request, signature validation, and the full WebAuthn §7.2 procedure. UP and/or UV flags SHALL be checked.
- §4 Communication Channel Requirements `#communication-channel-requirements`: a single SHOULD on Token Binding when TLS is used and it is available.
- §5 Extensions `#extensions`: the server MUST be able to register and authenticate with no extensions at all (it need not be deployed that way). Extensions are MAY; `appid` is SHOULD for U2F backward compatibility.
- §6 Other `#other`: WebAuthn §5.3.5 security requirements MUST be observed. COSE algorithm table: Required are RS1, RS256, ES256 and EdDSA; Recommended include ES384, ESP256, ESP384, Ed25519, Ed448 and ML-DSA-44/65/87. Curve table: P-256 and Ed25519 Required. Also the polymorphic-identifier rule (below) and a MUST to comply with the FIDO privacy principles.

**What matters most:**
- Mandatory format coverage in §2.3 `#attestation-formats`: a server that only handles `packed` and `none` does not meet the requirements; TPM, U2F and SafetyNet are MUST.
- Chain validation and MDS-based validation in §2.1 `#validating-attestation` are both MUST, separate from merely parsing the attestation statement.
- The no-extensions mode in §5 `#extensions`, which conformance testing relies on.
- RS1 (RSA PKCS#1 v1.5 with SHA-1) is Required in §6 `#other`, for TPM-era authenticators, even though many crypto libraries disable it by default.
- §6 `#other`: ES256, ES384, ES512 and EdDSA are polymorphic identifiers deprecated by RFC 9864. Servers SHOULD also accept the fully specified forms (ESP256 and so on). When requesting the fully specified identifier, the server MUST also request the polymorphic one.

**Watch out for:**
- The title targets WebAuthn Level 3, but the `[WebAuthn]` reference behind most section links points to Level 2, so WebAuthn § numbers may not match the L3 text.
- Token Binding in §4 `#communication-channel-requirements` is cited only as IETF drafts from 2018, and ECDAA (§2.2 `#attestation-types`) and Android SafetyNet (§2.3.4 `#android-attestation`) are carried over from earlier versions. Check the current `webauthn` text before investing in these legacy paths; SafetyNet is still a MUST here.
- The document is a Review Draft whose status text says it should not be implemented from. FIDO nevertheless uses it as the active server certification requirement set.

**Related documents:** `webauthn` (v3), the actual procedures §2 and §3 point to. `fido-metadata-service` and `fido-metadata-statement` for the MDS validation §2.1 requires. `fido-functional-certification-policy` for how server certification is run. `fido-registry` and `fido-security-ref` for background on algorithms and challenge randomness.
