# Client to Authenticator Protocol (CTAP)

Version 2.3 · Proposed Standard · 2026-02-26 · [source](https://fidoalliance.org/specs/fido-v2.3-ps-20260226/fido-client-to-authenticator-protocol-v2.3-ps-20260226.html)

## Summary

CTAP (Client to Authenticator Protocol) 2.3 is the current FIDO Alliance specification for how a client platform talks to a roaming authenticator. It covers the CBOR command set (makeCredential, getAssertion, getInfo, clientPIN, reset, bio enrollment, credential management, selection, large blobs, config), PIN/UV auth protocols and tokens, and feature sections such as enterprise attestation, alwaysUv, minimum PIN length, PIN complexity policy, JSON-based messages and long touch for reset. It also defines CTAP1/U2F interoperability and the USB HID, NFC, BLE and hybrid transport bindings. It is the authenticator-side companion to W3C WebAuthn: WebAuthn defines the browser API, and CTAP carries those requests to external authenticators.

Authenticators conforming to this version report `FIDO_2_3` in getInfo `versions`. §9 lists what such an authenticator must support, including hmac-secret, PIN/UV auth protocol two, credMgmt when `rk` is true, and credProtect when it supports user verification. This is the version current FIDO2 authenticator certification targets; confirm the exact test scope with the FIDO certification team.

**Who needs it:** authenticator vendors, platform & client developers, certification applicants and labs for FIDO2 authenticators

**Look here for:**
- What a FIDO_2_3 authenticator must implement → §9 `#mandatory-features`
- getInfo members, option IDs and version strings → §6.4 `#authenticatorGetInfo`
- Requiring a long touch before reset → §7.7 `#sctn-feature-descriptions-longTouchForReset`
- How hybrid (phone) transport works → §11.5 `#sctn-hybrid`
- PIN/UV auth tokens and permissions → §6.5 `#authenticatorClientPIN`
- Defined extensions (credProtect, largeBlob, hmac-secret, thirdPartyPayment, ...) → §12 `#sctn-defined-extensions`

**Changes from previous version:** Adds the `FIDO_2_3` version string and states that `FIDO_2_2` was never defined. Adds the Long touch for Reset feature (§7.7) with an authenticatorConfig subcommand to enable it (§6.11.5). The longTouchForReset getInfo member becomes tri-state, and the required touch is now 5 seconds or more, where 2.2 said 10 seconds. New getInfo members: encCredStoreState (0x1E) and authenticatorConfigCommands (0x1F). The hybrid section gains data-transfer-channel and data-transfer subsections (§11.5.1.1–11.5.1.2).

## Reading guide

**Start here:**
- §5 Terminology `#sctn-terminology`: defines "protected by some form of user verification", pre-flight, the user action timeout (at least 10 s) and the NFC user-presence rules. The command algorithms depend on these terms.
- §6.4 authenticatorGetInfo `#authenticatorGetInfo`: every behaviour switch (option IDs such as `clientPin`, `uv`, `pinUvAuthToken`, `makeCredUvNotRqd`, `alwaysUv`, `noMcGaPermissionsWithClientPin`) is defined here, and the command algorithms branch on them.
- §6.5.5.7 Operations to Obtain a pinUvAuthToken `#gettingPinUvAuthToken`: the permission model (mc, ga, cm, be, lbw, acfg, pcmr) that every protected command checks.
- §9 Mandatory features `#mandatory-features`: what a `FIDO_2_3` authenticator must ship.

**Section by section:**
- §6 Authenticator API `#authenticator-api`: the preamble lists the stateful commands (getNextAssertion, the credMgmt enumerations, fragmented largeBlobs writes). An authenticator MAY assume 30 s between calls and MAY fail out-of-pattern calls with CTAP2_ERR_NOT_ALLOWED. It MUST drop that state when the pinUvAuthToken that started it expires.
- §6.1.2 makeCredential algorithm `#sctn-makeCred-authnr-alg`: the step order matters. Zero-length pinUvAuthParam (an authenticator-selection touch, then PIN_NOT_SET or PIN_INVALID) comes first. Then pubKeyCredParams validation: the first supported algorithm wins, but every entry is still validated. Then option handling: `up`=false gives INVALID_OPTION, and `rk` without the rk option ID gives UNSUPPORTED_OPTION. Then the alwaysUv and makeCredUvNotRqd gates (PUAT_REQUIRED vs OPERATION_DENIED depending on clientPin and noMcGa), enterprise attestation, pinUvAuthToken checks (mc permission, permissions RP ID binding) and excludeList. A match in excludeList still collects user presence before returning CREDENTIAL_EXCLUDED; credProtect-3 credentials are skipped without UV. With rk=false the authenticator MUST now create a non-discoverable credential, and `attestationFormatsPreference` selects the format ("none" alone omits attestation).
- §6.1.3 Discoverable credentials `#sctn-discoverable`: credProtect 2/3 credentials are hidden from allowList-less discovery unless UV is done. A deleted or overwritten credential's ID must stop working, even if the key is wrapped inside it.
- §6.2.2 getAssertion algorithm `#sctn-getAssert-authnr-alg`: `rk` gives UNSUPPORTED_OPTION. Under alwaysUv with `up` true, an enabled built-in UV is used implicitly. The applicable-credentials filter applies credProtect. With no allowList and several credentials, results are ordered newest first: authenticators without a display return numberOfCredentials, and those with a display let the user pick and set userSelected. User name and display name MUST NOT be returned without UV. The UP/UV flag table explains pre-flight (`up`=0).
- §6.3 getNextAssertion `#authenticatorGetNextAssertion`: the 30 s timer is mandatory here except over NFC; §6.3.1 gives the platform's account-picker logic.
- §6.5.1–6.5.3 PIN rules and global state `#authnrClientPin-pin-composition`, `#authnrClientPin-globalState`, `#authnrClientPin-puaprot-util`: minimum 4 code points, maximum 63 bytes, NFC normalization, stored as LEFT(SHA-256,16). pinRetries is at most 8. maxUvRetries is 1–25. Running out of PIN retries also disables built-in UV. Token state covers the per-transport initial usage limit (30 s USB/BLE, 19.8 s NFC), an optional rolling timer, a max usage period (SHOULD default ≤10 min), and the userPresent/userVerified flags that commands consume.
- §6.5.5 clientPIN subcommands `#authnrClientPin-cmd-dfn`: getKeyAgreement, setPIN, changePIN, getPINRetries/getUVRetries. The authenticator decrements the retry counter before comparing. A mismatch triggers `regenerate`, and three consecutive mismatches give PIN_AUTH_BLOCKED (power cycle needed). A PIN change invalidates all tokens and the persistent token. `powerCycleState` is informational only.
- §6.5.5.7 token issuance `#gettingPinUvAuthToken`: getPinToken (superseded; fixed mc+ga, rejects permissions/rpId), getPinUvAuthTokenUsingPinWithPermissions (0x09) and ...UsingUvWithPermissions (0x06). Each permission is checked against its getInfo option, and failure gives UNAUTHORIZED_PERMISSION. `pcmr` must be requested alone and returns the persistentPinUvAuthToken. forcePINChange blocks token issuance (PIN_POLICY_VIOLATION, or PIN_INVALID for getPinToken).
- §6.5.6–6.5.8 protocols and PRF inputs `#pinProto1`, `#pinProto2`, `#prfValues`: protocol 1 uses SHA-256 ECDH, AES-CBC with a zero IV and a 16-byte truncated HMAC. Protocol 2 uses split HKDF keys, a random IV, a full HMAC and a 32-byte token. §6.5.8 lists the byte patterns MACed per command.
- §6.6 Reset `#authenticatorReset`: needs user presence and, without a display, arrival within 10 s of power-up. The section lists what is wiped or reset (EA disabled; alwaysUv, minPINLength, persistent token and long touch reset) and allows per-transport support.
- §6.7 BioEnrollment `#authenticatorBioEnrollment` and §6.8 CredentialManagement `#authenticatorCredentialManagement`: subcommand flows with their pinUvAuthParam inputs. Read-only credMgmt operations accept the persistent token with pcmr. §6.8.7 `#rpid-truncation` allows storing at least 32 bytes of the RP ID with a defined truncation.
- §6.9 Selection `#authenticatorSelection`: touch-to-select. CTAP2.1+ platforms should use it instead of the zero-length pinUvAuthParam trick.
- §6.10 LargeBlobs `#authenticatorLargeBlobs`: a fragmented get/set of one serialized array with a 16-byte hash trailer (at least 1024 bytes; fragments ≤ maxMsgSize−64). Writes need the lbw permission only when UV is configured or alwaysUv is on. §6.10.3–6.10.7 cover platform-side AES-GCM/DEFLATE per-credential blobs and garbage collection.
- §6.11 Config `#authenticatorConfig`: enableEnterpriseAttestation, toggleAlwaysUv, setMinPINLength (length can only grow; can force a PIN change, enable the complexity policy, set the minPinLength RP list), enableLongTouchForReset and vendorPrototype. It needs acfg only when UV is configured or alwaysUv is on. §6.12/6.13 `#prototypeAuthenticatorBioEnrollment`, `#prototypeAuthenticatorCredentialManagement` cover the optional `FIDO_2_1_PRE` 0x40/0x41 commands.
- §7 Feature descriptions `#sctn-feature-descriptions`: enterprise attestation (vendor-facilitated vs platform-managed, values 1/2), alwaysUv (incl. §7.2.4 `#sctn-feature-descriptions-alwaysUv-disable-u2f`: U2F MUST be disabled unless built-in UV protects it), the certifications map, minimum PIN length, PIN complexity, JSON-based messages for the Digital Credentials API (hybrid only) and long touch (≥5 s).
- §8 Message encoding `#message-encoding`: CTAP2 canonical CBOR (differs from RFC 8949 deterministic encoding), max 4 nesting levels, 1024-byte default message size, unknown map keys ignored. §8.1 `#commands` says unknown commands give INVALID_COMMAND and unknown subcommands INVALID_SUBCOMMAND; §8.2 `#error-responses` has the status codes.
- §10 CTAP1/U2F interop `#u2f-interoperability`: platform mapping of makeCredential/getAssertion to U2F_REGISTER/AUTHENTICATE (ES256 only, no rk/uv, excludeList via check-only plus a dummy registration). §10.4 `#cross-version-credentials`: U2F-created credentials MUST be assertable over CTAP2.
- §11.1 `#sctn-secure-interaction`: FIDO state must not be reachable through non-FIDO interfaces. NFC/smart-card applets must never be implicitly selected.
- §11.2 USB HID `#usb`: 64-byte reports, channels via CTAPHID_INIT on the broadcast CID, transaction locking, CANCEL (no reply to the CANCEL itself; the request ends with KEEPALIVE_CANCEL), KEEPALIVE at least every 100 ms, and capability flags in the INIT response.
- §11.3 NFC `#nfc`: AID A0000006472F0001. The select response is "U2F_V2" if U2F is supported, otherwise "FIDO_2_0". Short and extended APDUs MUST both be supported, with chaining. NFCCTAP_GETRESPONSE handles long operations; replies are RECOMMENDED within 800 ms.
- §11.4 BLE `#ble`: LTK-based encrypted link (Security Mode 1 Level 2/3), FIDO GATT service 0xFFFD, fidoControlPoint/fidoStatus framing, fidoServiceRevisionBitfield, keepalives and advertising rules.
- §11.5 Hybrid `#sctn-hybrid`: QR code (`FIDO:/` digit-encoded CBOR, flow hint keys incl. Digital Credentials), BLE-advert proximity proof (UUID fff9, trial-decrypted EID), a WebSocket tunnel or BLE L2CAP channel (§11.5.1.1 `#hybrid-data-transfer-channel`), a Noise handshake, the post-handshake getInfo and message types (§11.5.1.2 `#hybrid-data-transfer`), and linking for state-assisted reconnection (§11.5.2 `#hybrid-state-assisted`).
- §12 Extensions `#sctn-defined-extensions`: credProtect (levels 1–3; output must reflect the level actually set), credBlob (≥32 bytes), largeBlobKey (rk only; returned in response member 0x05/0x07, not in authData), largeBlob (alternative; mutually exclusive with the largeBlobs command), minPinLength and pinComplexityPolicy (both gated by the minPinLengthRPIDs list), hmac-secret (separate UV and non-UV secrets; `up`=false gives UNSUPPORTED_OPTION), hmac-secret-mc (requires hmac-secret in the same request), thirdPartyPayment.

**What matters most:**
- Error selection when UV is missing: PUAT_REQUIRED if clientPin can grant mc/ga, otherwise OPERATION_DENIED. Conformance tests check these branches (§6.1.2 `#sctn-makeCred-authnr-alg`, §6.2.2 `#sctn-getAssert-authnr-alg`).
- Using a token in an operation that tests UP clears all permissions except lbw and consumes cached UP/UV. Platforms need a fresh token afterwards (§6.5.5.7 `#gettingPinUvAuthToken`).
- getInfo consistency: minPINLength present iff clientPin is supported; maxSerializedLargeBlobArray iff largeBlobs; maxCredBlobLength iff credBlob; alwaysUv true forces makeCredUvNotRqd false; PIN/UV protocol 2 is required (§6.4 `#authenticatorGetInfo`, §9 `#mandatory-features`).
- PIN brute-force limits: decrement before compare, max 8 PIN retries, power-cycle block after 3 consecutive misses, uvRetries 1–25 (§6.5.2.3 `#authnrClientPin-globalState-retries`).
- Reset preconditions and what must be cleared (§6.6 `#authenticatorReset`).
- Left to implementers: token lifetimes below the defaults, rolling timers, whether reset works over NFC, the credProtect default, extra PIN constraints, enterprise attestation constraints.

**Watch out for:**
- §15 Security Considerations `#security-considerations` only points to the FIDO Security Reference.
- §6.5.8 `#prfValues` still lists an authenticatorClientPIN pattern (06 08), but no clientPIN subcommand 0x08 is defined. It also omits bio removeEnrollment (0106) and credMgmt updateUserInformation (07), which §6.7/§6.8 do MAC. This matches the 2.1 original, not the 2.1 errata edition.
- The §6.8 preamble says cm with a permissions RP ID can list that RP's credentials, but the algorithm in §6.8.4 `#enumeratingCredentials` requires no RP ID.
- §6.11 returns INVALID_PARAMETER for an unsupported config subcommand; §8.1 `#commands` requires INVALID_SUBCOMMAND.
- In §11.3.7.2 `#nfc-ctap-response`, cancel sets P1=0x11, yet the same text says P1/P2 MUST be 0x00.
- §11.5.1.2 `#hybrid-data-transfer` names the QR handshake KNpsk0 and then NKpsk0. Context (§11.5.2) indicates KNpsk0 for QR and NKpsk0 for state-assisted. Much of §11.5 uses lower-case "must" and Go reference code.
- §6.4 maxPINLength says both "63 or fewer bytes" and "less than 63 octets".
- §7.4.1 names the option `setMinPinLength` (getInfo uses `setMinPINLength`). §7.5.2 repeats the minimum-PIN-length text. §7.7.2 calls the subcommand "longTouchForReset" (it is enableLongTouchForReset), and no subcommand disables it.
- The JSON message schema IDs still say v2_2 (§7.6 `#sctn-feature-descriptions-jsonBasedMessages`).
- The deprecated `uv` option key and getPinToken remain for CTAP2.0 platforms. CTAP2.0 authenticators reject the `up` key.
