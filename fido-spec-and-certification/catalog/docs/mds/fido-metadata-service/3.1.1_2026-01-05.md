# FIDO Metadata Service

Version 3.1.1 · Proposed Standard · 2026-01-05 · [source](https://fidoalliance.org/specs/mds/fido-metadata-service-v3.1.1-ps-20260105.html)

## Summary

The FIDO Metadata Service (MDS) specification defines how relying parties get authenticator metadata from FIDO. The MDS publishes a single signed BLOB, a JWS-signed JWT, at a well-known URL (mds.fidoalliance.org). Each entry in the BLOB is keyed by AAID, AAGUID or attestation certificate key identifiers. An entry carries the full Metadata Statement, status reports, biometric status reports and the time of the last status change. Status values cover certification levels (FIDO_CERTIFIED_L1 to L3plus, NOT_FIDO_CERTIFIED, SELF_ASSERTION_SUBMITTED, REVOKED), security notices such as ATTESTATION_KEY_COMPROMISE and USER_VERIFICATION_BYPASS, and info statuses like UPDATE_AVAILABLE. The processing rules tell a FIDO server how to download and cache the BLOB, send its local serial number to avoid re-downloads, check the signing chain and CRLs, reject older serial numbers, and handle entries that matter to its policy.

MDS is what makes attestation trust work in practice. The FIDO2 Server Requirements require servers to support validation through MDS, and the certification policies feed certification status and biometric data into it. The structure of each statement is defined in the Metadata Statement specification. This document does not state what changed in 3.1.1.

**Who needs it:** relying parties and FIDO server developers, authenticator vendors (whose certification status is published here)

## Reading guide

**Start here:** §2.2 `#sctn-arch` (one signed file, downloaded and cached by the server), then §3.2 `#sctn-mds-blob-proc-rules`, which is the normative checklist a FIDO server MUST follow, then §3.1.1 `#sctn-mds-blob-pe` and §3.1.4 `#sctn-authnr-stat` for what each entry and status means. §2 `#sctn-overview` and §4 `#sctn-considerations` are informative.

**Section by section:**
- §3 `#sctn-mds-details`: using MDS is the RP's choice; metadata may also come from vendors or other trusted sources.
- §3.1.1 `#sctn-mds-blob-pe`: `MetadataBLOBPayloadEntry`. Exactly how an entry is keyed matters: `aaid` MUST be set for UAF, `aaguid` MUST be set for FIDO2, and `attestationCertificateKeyIdentifiers` (lower-case hex, RFC 5280 method 1 key identifier) MUST be set when neither is, which is the U2F case. Required members are `metadataStatement`, `statusReports` and `timeOfLastStatusChange`; `rogueListURL` needs a non-empty `rogueListHash`.
- §3.1.2 `#sctn-bio-stat-rep`: `BiometricStatusReport` with `certLevel` and `modality`; the modality MUST be a biometric USER_VERIFY name that also appears in the statement's `userVerificationDetails`.
- §3.1.3 `#sctn-stat-rep`: `StatusReport`. The latest entry MUST reflect the current status. `authenticatorVersion` semantics depend on the status (minimum certified version, vulnerable version, available update). `batchCertificate` / `certificate` are standard base64, not base64url. `certificationProfiles` (`consumer`, `enterprise`), `sunsetDate`, and `fipsRevision` / `fipsPhysicalSecurityLevel`, present if and only if the status is FIPS140_CERTIFIED_L*. Firmware version in the attestation certificate is OID 1.3.6.1.4.1.45724.1.1.5.
- §3.1.4 `#sctn-authnr-stat` with §3.1.4.1 `#sctn-cert-stats`, §3.1.4.2 `#sctn-sec-not-stats`, §3.1.4.3 `#sctn-info-stats`: certification statuses (NOT_FIDO_CERTIFIED, SELF_ASSERTION_SUBMITTED, legacy FIDO_CERTIFIED, FIDO_CERTIFIED_L1 to L3plus, FIPS140_CERTIFIED_L1–L4, RETIRED, REVOKED), security notices (USER_VERIFICATION_BYPASS, ATTESTATION_KEY_COMPROMISE, USER_KEY_REMOTE_COMPROMISE, USER_KEY_PHYSICAL_COMPROMISE) and UPDATE_AVAILABLE. RPs SHOULD reject new registrations of REVOKED models and SHOULD use the certificate fields to scope an attestation key compromise. Servers MUST silently ignore unknown status values.
- §3.1.5 `#sctn-rogue-list-entry`: rogue list of individual authenticators identified by their ECDAA secret key `sk`.
- §3.1.6 `#sctn-mds-payload-blob`: `legalHeader`, `no` (serial; MUST increase by exactly one on every change), `nextUpdate` (discouraged, to be removed) and `entries`.
- §3.1.7 `#sctn-mds-blob`, §3.1.7.1 `#sctn-examples`: the BLOB is a compact JWS (header.payload.signature, unpadded base64url); the header SHALL carry `iat`. The example is informative.
- §3.2 `#sctn-mds-blob-proc-rules`: get the root trust anchor from mds.fidoalliance.org; send `localCopySerial` (or `If-None-Match`; the parameter wins if both are sent) to get 304 when nothing changed; resolve the signing chain from `x5u` (MUST be same web origin as the BLOB), else `x5c`, else the trust anchor itself; verify the chain and CRLs for every certificate; verify the signature; ignore BLOBs whose `no` is not greater than the cached one; then per relevant entry update status and cached statement.
- §4 `#sctn-considerations`: design rationale and implementer guidance: check once a day and always send the local serial.

**What matters most:**
- Chain and revocation checking of the BLOB signer, and the same-origin rule for `x5u` (§3.2 `#sctn-mds-blob-proc-rules`). CRL checking is mandatory only for the BLOB chain; checking certificates inside statements is the server vendor's decision.
- Rollback protection by serial number (§3.1.6 `#sctn-mds-payload-blob`, §3.2 `#sctn-mds-blob-proc-rules`).
- Looking up the right entry for an attestation: AAGUID for FIDO2, AAID for UAF, key identifier of the attestation certificate for U2F (§3.1.1 `#sctn-mds-blob-pe`).
- Status handling is RP policy except where the text says otherwise: REVOKED, the compromise statuses, and UPDATE_AVAILABLE, where the RP MUST reject the statement if `authenticatorVersion` did not increase (§3.1.4.3 `#sctn-info-stats`).
- Tolerance: ignore unknown fields and unknown statuses, and do not fail when an entry disappears from a later BLOB (§3.2 `#sctn-mds-blob-proc-rules`, §3.1.4.3 `#sctn-info-stats`).

**Watch out for:**
- `nextUpdate` is still `required` in the IDL but the note says not to depend on it, and §4 `#sctn-considerations` still describes it as the next scheduled update. Code should not require it.
- §3.1.7 `#sctn-mds-blob` still says the JWT hash algorithm is used to hash metadata statements, a leftover from versions that referenced statements by hash; 3.x embeds statements in each entry.
- The sample payload in §3.1.1 `#sctn-mds-blob-pe` uses the phased-out FIDO_CERTIFIED status and has no `legalHeader`; the document carries an open "update this example" issue.
- The rogue list identifies devices by their ECDAA secret key (§3.1.5 `#sctn-rogue-list-entry`), so it is useful only for ECDAA attestation, not for batch attestation.
- Both §3.1.3 `#sctn-stat-rep` and §3.1.4.1 `#sctn-cert-stats` state that certification does not cover multi-device (synced) keys.
- The text does not say what changed in 3.1.1.

**Related documents:** fido-metadata-statement 3.1.1 (the `metadataStatement` object), fido-convenience-metadata-service 1.0 (display-only names and logos keyed by AAGUID, sharing this BLOB's serial numbering), fido-server-requirements (MDS support required of certified servers), fido-authenticator-certification-policy and fido-biometric-component-certification-policy (where certification and biometric status reports come from), fido-authenticator-security-requirements (`certificationRequirementsVersion`), fido-ecdaa-algorithm (rogue list `sk`), webauthn and fido-uaf-protocol (attestation that MDS trust anchors verify).
