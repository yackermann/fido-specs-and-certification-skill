# FIDO Convenience Metadata Service

Version 1.0 · Proposed Standard · 2025-05-21 · [source](https://fidoalliance.org/specs/mds/fido-convenience-metadata-service-v1.0-ps-20250521.html)

## Summary

The Convenience Metadata Service defines a lightweight feed with only display information for authenticators and passkey providers. It lets relying parties show users recognizable names and logos next to their registered credentials. The feed is served from c-mds.fidoalliance.org as a payload with a serial number `no`, which is strictly consecutive. The payload maps each AAGUID to `ConvenienceDetails`: `friendlyNames`, where an en-US name is mandatory and other languages are keyed by IETF language tag, plus a light-mode `icon`, `iconDark`, `providerLogoLight` and `providerLogoDark` as data: URLs. Provider logos must use the SVG Tiny Portable/Secure profile, be square, contain no raster content and carry the English name in `<title>`. Clients can send their cached serial (`localCopySerial` or If-None-Match) to receive HTTP 304 when nothing changed.

All data here also appears in the full FIDO Metadata Service, and the serial number moves whenever either feed changes. The feed is not meant for security decisions. Attestation trust and certification status still come from MDS and the Metadata Statement. Entries are keyed by AAGUID only.

**Who needs it:** relying parties and FIDO server developers building credential-management UIs, passkey providers and authenticator vendors supplying names and logos

- Which display fields are available per authenticator? → §3.1.2 `#sctn-convenience-details`

## Reading guide

**Start here:** §2 `#sctn-overview` (informative: display-only data, all of it also in the full MDS), then §3.1.3 `#sctn-cmds-pe` for the payload shape and §3.1.2 `#sctn-convenience-details` for the per-AAGUID fields. The whole normative content fits in §3 and §4.

**Section by section:**
- §1 `#sctn-notation`: WebIDL conventions that matter for parsing: members are optional unless marked `required`, never null, and strings and lists must not be empty unless stated otherwise.
- §3 `#sctn-cmds-details`, §3.1 `#sctn-cmds-fmt`: data comes from authenticator vendors, so names and logos stay consistent across relying parties.
- §3.1.1 `#sctn-types-fn`: `FriendlyNames` keyed by IETF language tag, with fallback from region-specific to general language; entries SHOULD stay within 63 characters.
- §3.1.2 `#sctn-convenience-details`: `friendlyNames` (an `en-US` name is mandatory), `icon` (PNG or SVG data: URL, light mode), `iconDark`, `providerLogoLight`, `providerLogoDark` (SVG). SVG is mandatory for `icon` once any of the other three is present. The device icon is more specific than the provider logo and should be preferred when present.
- §3.1.3 `#sctn-cmds-pe`: `ConvenienceMetadataPayload` is a flat JSON object with a required serial `no` plus one member per AAGUID. `no` MUST increase by exactly one whenever this feed or the full MDS BLOB changes.
- §3.2 `#sctn-mds-blob-proc-rules`: servers SHOULD download and cache from c-mds.fidoalliance.org, passing `localCopySerial` or `If-None-Match` to get 304; the serial comes back in ETag, and the query parameter wins if both are sent.
- §4 `#sctn-svg-requirements`: provider logos MUST follow SVG Tiny Portable/Secure (version 1.2, baseProfile `tiny-ps`), vector only, square, `<title>` = English friendly name, no comments.
- §5 `#sctn-considerations`: informative heading with no content beyond one sentence.

**What matters most:**
- This feed is for UI only; the Abstract `#abstract` and §2 `#sctn-overview` send every security question (attestation, certification status) to the full MDS.
- Parsing: every top-level member except `no` is an AAGUID key (§3.1.3 `#sctn-cmds-pe`); code must not expect an `entries` array as in MDS.
- Because the shared serial also moves when the full MDS changes (§3.1.3 `#sctn-cmds-pe`), a new `no` does not imply that convenience data changed.
- Only the `en-US` friendly name is mandatory; every icon and logo is optional, so UIs need a fallback (§3.1.2 `#sctn-convenience-details`).

**Watch out for:**
- The document defines no signature, JWT wrapping or certificate chain for this feed, unlike MDS; the §3.2 heading still says "Metadata BLOB" and the processing rules are only SHOULD.
- Only AAGUIDs are keys, so UAF (AAID) and U2F (key identifier) authenticators have no entries.
- The JSON example in §3.1.3 `#sctn-cmds-pe` has trailing commas and is not valid JSON; it is informative.
- The §3.1.3 heading says "Payload Entry" but defines the whole payload.

**Related documents:** fido-metadata-service 3.1.1 (signed, security-relevant source of the same data, shared serial numbering, same 304 mechanism), fido-metadata-statement 3.1.1 (where `friendlyNames`, icons and provider logos are defined for vendors, with the same SVG rules), webauthn (AAGUID in attested credential data, which is the lookup key).
