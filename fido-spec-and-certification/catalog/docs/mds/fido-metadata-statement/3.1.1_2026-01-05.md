# FIDO Metadata Statement

Version 3.1.1 · Proposed Standard · 2026-01-05 · [source](https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.1.1-ps-20260105.html)

## Summary

The FIDO Metadata Statement specification defines the JSON document that describes an authenticator model, so that servers and relying parties can interoperate with it and make risk decisions. A statement is identified by AAID (UAF), AAGUID (FIDO2) or attestation certificate key identifiers. It declares the protocol family and versions (`upv`), supported algorithms and public key encodings, and attestation types. It also covers user verification methods with accuracy descriptors (code, biometric, pattern), key and matcher protection, and transaction confirmation display. The statement also carries the attestation root certificates that servers use as trust anchors. Some fields serve passkey providers and synced credentials: light and dark icons and provider logos (SVG profile rules in §4.1), `multiDeviceCredentialSupport`, an embedded `authenticatorGetInfo`, and `cxConfigURL` for credential exchange. The schema version is 3. Allowed values come from the FIDO Registry of Predefined Values.

Vendors submit statements during FIDO certification. The Metadata Service then distributes them inside its signed BLOB. Statements are meant to stay stable, and a major change in functionality, such as a new user verification method, requires a new model identifier. This document does not state what changed in 3.1.1.

**Who needs it:** authenticator and passkey-provider vendors (writing statements), FIDO server developers and relying parties (consuming them), certification applicants

## Reading guide

**Start here:** §2.3 `#sctn-architecture` for how a statement flows from vendor submission through MDS to the server's attestation and policy checks, then the `MetadataStatement` IDL at the top of §4 `#sctn-md-keys`, whose `required` markers are the authoritative list of mandatory fields. Keep the FIDO Registry open: almost every string value comes from it.

**Section by section:**
- §2 `#sctn-overview` (§2.1 `#sctn-scope`, §2.2 `#sctn-audience`): informative; distribution and verification of statements belong to the Metadata Service spec.
- §3.1 `#sctn-type-aaguid`: AAGUID as a dashed 36-character string; it MUST be the same for substantially identical authenticators and unique across models.
- §3.2–§3.4 `#sctn-type-cad`, `#sctn-type-bad`, `#sctn-type-pad`: accuracy descriptors. Code: `base`, `minLength` (required), `maxRetries`, `blockSlowdown`. Biometric: FRR, FAR, `iAPARThreshold`, `maxTemplates`, at least one value MUST be set or `baDesc` omitted; values are self-attested unless biometric certification verified them. Pattern: `minComplexity`. A `blockSlowdown` of 0 requires the fallback methods to be listed.
- §3.5–§3.6 `#sctn-type-vmd`, `#sctn-type-vmac`: one USER_VERIFY method per descriptor (never USER_VERIFY_ALL); an inner list is an AND combination and MUST NOT be empty.
- §3.7–§3.8 `#sctn-type-rgbpe`, `#sctn-type-dpngcd`: PNG characteristics for transaction confirmation displays.
- §3.9 `#sctn-type-ecdaata`: ECDAA issuer trust anchor, UAF only.
- §3.10–§3.12 `#sctn-type-ed`, `#sctn-type-fn`, `#sctn-type-ad`: UAF extension descriptors (`fail_if_unknown`), friendly names (SHOULD stay within 63 characters) and alternative descriptions (SHALL NOT exceed 200).
- §3.13 `#sctn-type-agid`: `authenticatorGetInfo` mirrors the CTAP getInfo response, binary values base64.
- §4 `#sctn-md-keys`: every field. Required: `description`, `authenticatorVersion`, `protocolFamily`, `schema` (3), `upv`, `authenticationAlgorithms`, `publicKeyAlgAndEncodings`, `attestationTypes`, `keyProtection`, `matcherProtection`, `tcDisplay` (empty when no transaction confirmation), `attestationRootCertificates`. Conditionally required: `aaid` (UAF), `aaguid` (FIDO2), `attestationCertificateKeyIdentifiers` (neither), `friendlyNames` with an `en-US` entry, `attachmentHint` (MUST for CTAP 2.2 or newer, SHOULD for 2.1), `tcDisplayContentType` / `tcDisplayPNGCharacteristics`, `ecdaaTrustAnchors`, and `authenticatorGetInfo` (MUST for native CTAP authenticators). Defaults when absent: `isKeyRestricted` and `isFreshUserVerificationRequired` true, `multiDeviceCredentialSupport` `unsupported`.
- §4.1 `#sctn-svg-requirements`: provider SVGs MUST follow the SVG Tiny Portable/Secure profile, square, vector only, `<title>` set to the English friendly name, no comments.
- §5 `#sctn-mdsfmt` (§5.1 `#sctn-uaf-example`, §5.2 `#sctn-u2f-example`, §5.3 `#sctn-fido2-example`): informative examples for each protocol family.
- §6.1 `#sctn-cons-updates`: statements are meant to be stable; `authenticatorVersion` must rise when an update fixes severe security issues; keys registered under one model identifier cannot be used under another.

**What matters most:**
- Trust anchors (§4 `#sctn-md-keys`, `attestationRootCertificates`): each entry is an anchor, not a chain, and may be a root, an intermediate or the attestation certificate itself; if one anchor covers several models, the model must be derivable from the certificate (AAID or AAGUID extension, OIDs 1.3.6.1.4.1.45724.1.1.1 and .1.1.4, or key identifiers). Surrogate basic attestation requires an empty array.
- Consistency with getInfo (§4 `#sctn-md-keys`): `authenticatorVersion` should equal getInfo `firmwareVersion`; FIDO2 `attachmentHint` MUST match getInfo `transports`; `upv` uses 1.0 / 1.1 / 1.3 for CTAP 2.0 / 2.1 / 2.3 (1.2 is reserved because CTAP 2.2 was skipped) and 1.0–1.2 for U2F.
- Certification status lives only in MDS status reports; the `certifications` member of an embedded getInfo is not verified by FIDO (§4 `#sctn-md-keys`, `authenticatorGetInfo`).
- `keyProtection` and `matcherProtection` describe effective security, and `matcherProtection` must reflect the weakest implementation or component (§4 `#sctn-md-keys`).
- `isFreshUserVerificationRequired` = false obliges the server to check the UV caching time (§4 `#sctn-md-keys`).
- Server tolerance: a server MUST accept every public key encoding defined for algorithms it supports, whatever the statement lists (§4 `#sctn-md-keys`, `publicKeyAlgAndEncodings`).

**Watch out for:**
- `multiDeviceCredentialSupport` changes the meaning of the whole statement: with `implicit` (or the BE flag set) keys may be backed up and restored to other models, and the AAGUID may change over time (§4 `#sctn-md-keys`).
- `supportedExtensions` and `ecdaaTrustAnchors` apply to UAF only; FIDO2 extensions are read from `authenticatorGetInfo`.
- `icon` may be PNG or SVG, but SVG becomes mandatory once any of `iconDark`, `providerLogoLight`, `providerLogoDark` is present (§4 `#sctn-md-keys`).
- The FIDO2 example in §5.3 `#sctn-fido2-example` is not fully consistent with the rules: its introduction says `authenticatorVersion` 2 while the JSON has 5, `attachmentHint` lists `wireless` although getInfo `transports` is only `usb` and `nfc`, and the getInfo AAGUID is plain hex rather than base64.
- `userVerificationDetails` may be omitted, in which case any method, including none, is possible (§4 `#sctn-md-keys`).
- The text does not say what changed in 3.1.1.

**Related documents:** fido-metadata-service 3.1.1 (BLOB that carries statements, status reports, `authenticatorVersion` rules for UPDATE_AVAILABLE), fido-registry (all constant values), fido-client-to-authenticator-protocol 2.3 (getInfo members and versions), webauthn (BE flag, attestation formats), fido-uaf-protocol and fido-uaf-authnr-cmds (AAID, upv, surrogate attestation), fido-authenticator-metadata-requirements and fido-authenticator-certification-policy (how statements are reviewed in certification), fido-biometrics-requirements (FAR/FRR/IAPAR thresholds), fido-authenticator-security-requirements (cryptoStrength), cxf (`cxConfigURL` context).
