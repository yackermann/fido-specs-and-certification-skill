# FIDO UAF Registry of Predefined Values

Version 1.2 · Proposed Standard · 2020-10-20 · [source](https://fidoalliance.org/specs/fido-uaf-v1.2-ps-20201020/fido-uaf-reg-v1.2-ps-20201020.html)

## Summary

The UAF Registry of Predefined Values collects the identifiers and constants that only UAF uses. Values shared across FIDO families (algorithms, key encodings, user verification methods and so on) are in the separate FIDO Registry. This document defines the assertion scheme names (the default is UAFV1TLV), the tags that appear in UAF protocol messages (0x3E01 to 0x3E06), and the predefined extensions. For each extension it gives the identifier, the fail-if-unknown flag, the data format and the processing expected from the server, client, ASM and authenticator. It also defines the UAF Application Identifier (AID) used to select the UAF applet on Secure Elements.

The extensions are user verification method (`fido.uaf.uvm`), user ID (`fido.uaf.userid`), Android SafetyNet (`fido.uaf.safetynet`), Android Key Attestation (`fido.uaf.android.key_attestation`), user verification caching (`fido.uaf.uvc-req` / `fido.uaf.uvc-resp`), require resident key (`fido.uaf.rk`) and attestation conveyance (`fido.uaf.ac`). Authenticators declare supported extensions in their Metadata Statement.

**Who needs it:** authenticator vendors, ASM and client developers, FIDO Server developers

**Look here for:**
- Protocol tag values → §4.1 `#h3_tags-used-in-the-protocol`
- Asking for or confirming a specific user verification method → §5.1 `#h3_user-verification-method-extension`
- Android Key Attestation in UAF registration → §5.4 `#h3_android-key-attestation`
- Letting an authenticator reuse a recent user verification → §5.5 `#h3_user-verification-caching`
- Extensions for integrating CTAP2 authenticators → §5.6 `#h3_require-resident-key-extension`, §5.7 `#h3_attestation-conveyance-extension`
- UAF applet AID for Secure Elements → §6.1 `#h3_fido-uaf-application-identifier-aid`

**Changes from previous version:** Chapter 5 is renamed from "Predefined (untagged) Extensions" to "Predefined Extensions" and grows from two extensions (SafetyNet, Android Key Attestation) to seven. The new ones are user verification method; user ID; user verification caching, with new tag TAG_USER_VERIFICATION_CACHING 0x0108; require resident key, with new tag TAG_RESIDENT_KEY 0x0109; and attestation conveyance (`direct`, `indirect` or `none`). The last two exist to ease integration of CTAP2 authenticators. New protocol tags TAG_APCV1CBOR_AUTH_ASSERTION (0x3E05) and TAG_APCV1CBOR_SIGNED_DATA (0x3E06) support the Android Protected Confirmation assertion format. TAG_ATTESTATION_BASIC_FULL, TAG_ATTESTATION_BASIC_SURROGATE and TAG_ATTESTATION_ECDAA (0x3E07–0x3E09) are no longer listed here.

## Reading guide

**Start here:** §4 `#h2_predefined-tags` for the TLV conventions and tag values every UAF authenticator and server parses, then §5 `#h2_predefined-extensions` for the extension you actually need (each one is a self-contained block giving identifier, fail-if-unknown flag, data format, and client, authenticator and server processing). §3.1 `#h3_assertion-schemes` is one paragraph but fixes the default scheme name.

**Section by section:**
- §2 Overview `#h2_overview` (informative): UAF-only constants live here; cross-family values (ALG_*, key protection, matcher protection, user verification methods) live in the shared FIDO Registry.
- §3.1 Assertion Schemes `#h3_assertion-schemes`: scheme names are 8 characters; `UAFV1TLV` is the default, and its authenticator MUST create a UAuth key pair for an ALG_* suite and uses TLV-encoded KRD and SignData. The other schemes (APCV1CBOR, WAV1CBOR) are defined in their own documents, not here.
- §4 Predefined Tags `#h2_predefined-tags`: tags and lengths are 2 bytes; only the low 14 bits should be used; bit 0x2000 marks a critical tag (receiver must abort if it cannot process it) and 0x1000 a composite tag.
- §4.1 Tags used in the protocol `#h3_tags-used-in-the-protocol`: the assertion tags (0x3E01–0x3E06), the leaf tags (TAG_KEYID, TAG_FINAL_CHALLENGE_HASH, TAG_AAID, TAG_COUNTERS, TAG_ASSERTION_INFO, TAG_AUTHENTICATOR_NONCE …), TAG_EXTENSION (0x3E11/0x3E12), and the user verification tags. Raw UVI/UVS (0x0103, 0x0105) SHALL NOT leave the authenticator; the exported UVI/UVS (0x0104, 0x0106) MUST be key-specific, not reused, and servers MUST accept up to 32 bytes. New in 1.2: UVC 0x0108 and resident key 0x0109.
- §5.1 UVM `#h3_user-verification-method-extension` (`fido.uaf.uvm`): the request lists single-bit UVM values (all listed methods SHALL be used); the response reports UVM plus keyProtection and matcherProtection, and the authenticator SHALL report truthfully. Server checks are SHOULD.
- §5.2 User ID `#h3_user-id-extension` (`fido.uaf.userid`): an RP index, not for display; fail-if-unknown false.
- §5.3 SafetyNet `#h3_android-safetynet-extension`: handled by the client or ASM, not the authenticator. The client MUST call the SafetyNet API itself and MUST NOT forward the request to the ASM (an explicit exception to the protocol's pass-through rule); the nonce is a JSON object holding hashAlg and the final challenge hash. Data "p" = platform lacks support, "a" = temporarily unavailable.
- §5.4 Android Key Attestation `#h3_android-key-attestation`: registration only. Servers MUST first run normal registration processing, then validate the chain to a root in the extension's `attestationRootCertificates` (accepting a missing keyCertSign bit on the issuer), and check the leaf: attestationChallenge equals the final challenge hash, the public key matches the surrogate attestation key, and the authorisation list (origin generated, purpose sign, SHA-256, acceptable key size and userAuthType, no authTimeout, no allApplications, no noAuthRequired unless the authenticator is silent).
- §5.5 UVC `#h3_user-verification-caching`, with §5.5.1 `#h4_uvc-request`, §5.5.2 `#h4_uvc-response`: lets a recent user verification count. At registration the authenticator always verifies and records regMaxUVC; at signing it compares elapsed time with min(maxUVC, regMaxUVC) and verifies or errors according to verifyIfExceeded. The response is fail-if-unknown true, so a server that did not ask for it or does not understand it MUST fail. §5.5.3 `#h4_privacy-considerations` and §5.5.4 `#h4_security-considerations` explain why web pages may not set verifyIfExceeded and why the response must be flagged.
- §5.6 Resident key `#h3_require-resident-key-extension` (`fido.uaf.rk`) and §5.7 Attestation conveyance `#h3_attestation-conveyance-extension` (`fido.uaf.ac`): bridges for CTAP2 authenticators. rk=false in a response means the server must send key handles (second-factor use). For ac, the client SHALL pass through (direct), may anonymise (indirect) or SHALL strip (none) the attestation.
- §6.1 AID `#h3_fido-uaf-application-identifier-aid`: RID A000000647, AC AF, AX 0001, used by the APDU binding.

**What matters most:**
- Critical-tag handling (bit 0x2000) and the 32-byte UVI/UVS minimum are easy to miss in parsers (§4).
- UVC is the one extension here whose response cannot be ignored; servers must reject unsolicited or unknown UVC responses (§5.5.2).
- Android Key Attestation server checks are MUST-level and include a deliberate RFC 5280 deviation (§5.4).
- SafetyNet and Key Attestation responses are not covered by the authenticator signature, so a MITM can strip them; their absence proves nothing (§5.3, §5.4).

**Watch out for:**
- The attestation type identifiers (0x3E07–0x3E09) are no longer here; in 1.2 the Authenticator Commands document lists them as ATTESTATION_BASIC_FULL, ATTESTATION_BASIC_SURROGATE and ATTESTATION_ECDAA.
- The UVI, UVS and UVC byte examples in §4.1 show a one-byte length field and, for UVC, a value longer than the defined UINT16 + UINT8 structure; follow the table (2-byte tag, 2-byte length), not the example.
- §5.6 says authenticators "should" store keys; whether rk is honoured is visible only from the response.

**Related documents:** fido-uaf-protocol (how extensions are carried and the registration rules §5.4 depends on); fido-uaf-authnr-cmds (TLV command structures, attestation identifiers); fido-uaf-apccbor (APCV1CBOR tags 0x3E05/0x3E06); fido-uaf-webauthn (CTAP2 integration that uses rk and ac); fido-uaf-apdu (uses the AID); the shared FIDO Registry and Metadata Statement documents (UVM/protection values and `supportedExtensions`).
