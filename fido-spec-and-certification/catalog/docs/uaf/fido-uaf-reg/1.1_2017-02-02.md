# FIDO UAF Registry of Predefined Values

Version 1.1 · Proposed Standard · 2017-02-02 · [source](https://fidoalliance.org/specs/fido-uaf-v1.1-ps-20170202/fido-uaf-reg-v1.1-ps-20170202.html)

## Summary

The 1.1 edition of the UAF Registry of Predefined Values, the version FIDO lists for certification. It defines the UAFV1TLV assertion scheme name, the UAF protocol tags (including TAG_ATTESTATION_BASIC_FULL, TAG_ATTESTATION_BASIC_SURROGATE and TAG_ATTESTATION_ECDAA at 0x3E07–0x3E09), two untagged extensions (Android SafetyNet and Android Key Attestation) and the UAF Secure Element applet AID. Compared with 1.2, it lacks the user verification method, user ID, user verification caching, resident key and attestation conveyance extensions, and the APCV1CBOR tags.

**Who needs it:** authenticator vendors, ASM/client developers and server developers targeting UAF 1.1

**Look here for:**
- Protocol tag values → §4.1 `#h3_tags-used-in-the-protocol`
- Android Key Attestation extension → §5.2 `#h3_android-key-attestation`
- UAF applet AID → §6.1 `#h3_fido-uaf-application-identifier-aid`

## Reading guide

**Use this version when:** you implement or certify against UAF 1.1, the UAF version FIDO certifies. A 1.1 server or authenticator should expect only the tags and the two extensions defined here; anything from the 1.2 registry is an addition.

**Differences from 1.2:**
- §4.1 `#h3_tags-used-in-the-protocol` still lists TAG_ATTESTATION_BASIC_FULL (0x3E07), TAG_ATTESTATION_BASIC_SURROGATE (0x3E08) and TAG_ATTESTATION_ECDAA (0x3E09), with ECDAA marked optional for now; 1.2 drops these from the registry. 1.1 has no APCV1CBOR tags (0x3E05/0x3E06), no TAG_USER_VERIFICATION_CACHING (0x0108) and no TAG_RESIDENT_KEY (0x0109). The UVI/UVS tags and rules are the same.
- §5 `#h2_predefined-untagged-extensions` has only SafetyNet and Android Key Attestation. The UVM, user ID, UVC, resident-key and attestation-conveyance extensions do not exist in this edition.
- §5.2 Android Key Attestation `#h3_android-key-attestation` is allowed in authentication messages as well as registration (1.2 restricts it to registration). Its server rule requires chain validation to a metadata root without the explicit allowance, added in 1.2, for an issuer lacking the keyCertSign bit, and it names the field `authType` where 1.2 says `userAuthType`.
- §5.1 SafetyNet `#h3_android-safetynet-extension` is the same apart from naming the result object AttestationResult (1.2: AttestationResponse).

**Section by section:** structure as in 1.2 for §3, §4 and §6; see that page's reading guide. Read §4 `#h2_predefined-tags` for TLV rules (critical bit 0x2000, composite bit 0x1000, 14-bit tag space), §4.1 for every tag value a UAFV1TLV parser needs, and §6.1 `#h3_fido-uaf-application-identifier-aid` for the Secure Element AID (A000000647 AF 0001). The SafetyNet extension is handled by the client or ASM only, and neither extension response is signed by the authenticator.
