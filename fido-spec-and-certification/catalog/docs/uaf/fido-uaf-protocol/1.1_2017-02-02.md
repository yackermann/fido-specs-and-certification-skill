# FIDO UAF Protocol Specification

Version 1.1 · Proposed Standard · 2017-02-02 · [source](https://fidoalliance.org/specs/fido-uaf-v1.1-ps-20170202/fido-uaf-protocol-v1.1-ps-20170202.html)

## Summary

The 1.1 edition of the UAF Protocol Specification, the version FIDO lists for certification. It defines the same message set, shared structures, policy matching, version negotiation (minor version 1), processing rules and security considerations as 1.2. Compared with 1.2: there is no CollectedClientData path for CTAP2/WebAuthn platforms, no Token Binding field in ChannelBinding, and no guidance on revealing KeyIDs. Only TLV assertions are processed; other schemes are skipped. `text/plain` transactions are ASCII, and content types are limited to text/plain and image/png. Attestation types are written as `TAG_ATTESTATION_*`.

**Who needs it:** FIDO Server developers and relying parties, UAF client developers, authenticator vendors targeting UAF 1.1 certification

**Look here for:**
- Server checks on a registration response → §3.4.6.5 `#h5_registration-response-processing-rules-for-fido-server`
- Server checks on an authentication response → §3.5.7.5 `#h5_authentication-response-processing-rules-for-fido-server`
- Policy and MatchCriteria → §3.2 `#h3_processing-rules-for-the-server-policy`, §3.1.11 `#h4_matchcriteria-dictionary`
- Attestation models → §4.1.2 `#h4_authenticator-attestation`

## Reading guide

**Use this version when:** you implement or certify a UAF server, client or authenticator against UAF 1.1, the UAF version FIDO certifies. Messages in this edition carry upv 1.1 (§3.1.3 `#h4_operationheader-dictionary`). Note that the shared-structure subsections are numbered one lower than in 1.2 from ChannelBinding onwards (e.g. MatchCriteria is §3.1.11 here, §3.1.12 in 1.2); anchors are the same.

**Differences from 1.2** (from comparing the two texts):
- No CollectedClientData: `fcParams` is always FinalChallengeParams (§3.1.7 `#h4_finalchallengeparams-dictionary`), and the server rules have no client-data branch or `hashAlg` hashing.
- ChannelBinding (§3.1.8 `#h4_tls-channelbinding-dictionary`) has no `tokenBinding` field; tlsUnique is already marked deprecated.
- No §2.4 on stable identifiers and no §4.2.2 on revealing KeyIDs (§4.2 `#h3_implementation-considerations` covers only challenge randomness).
- Server processing (§3.4.6.5 `#h5_registration-response-processing-rules-for-fido-server`, §3.5.7.5 `#h5_authentication-response-processing-rules-for-fido-server`) skips any assertion that is not TAG_UAFV1_REG_ASSERTION / TAG_UAFV1_AUTH_ASSERTION, and lacks 1.2's explicit rejection of unknown fields belonging to fail-if-unknown extensions.
- Transactions (§3.5.1 `#h4_transaction-dictionary`): only text/plain or image/png, and text/plain is ASCII (≤200 characters).
- Deriving MatchCriteria.userVerification from metadata (§3.1.11.1 `#h5_dictionary-matchcriteria-members`) is only possible when every userVerificationDetails entry has a single element; otherwise the server must list AAIDs. 1.2 replaces this with an OR-combination rule.
- The client deregistration rules (§3.6.4.2 `#h5_deregistration-request-processing-rules-for-fido-uaf-client`) do not return NO_SUITABLE_AUTHENTICATOR when nothing matches, and the ASM status table has no SYSTEM_INTERRUPTED.
- Attestation types are written TAG_ATTESTATION_*.

**Section by section:** structure as in 1.2; see that page's reading guide. The parts certification relies on are the same: AppID/FacetID rules in the OperationHeader, policy construction and matching (§3.1.12 Policy `#h4_policy-dictionary`, §3.2 `#h3_processing-rules-for-the-server-policy`), version negotiation (§3.3 `#h3_version-negotiation`), the server registration and authentication rules (attestation by type, FCHash, counters, transaction hash), deregistration semantics (§3.6 `#h3_deregistration-operation`), and attestation background in §4.1.2 `#h4_authenticator-attestation`. The isKeyRestricted wording in the counter checks is already present in this edition.
