# FIDO UAF Protocol Specification

Version 1.2 · Proposed Standard · 2020-10-20 · [source](https://fidoalliance.org/specs/fido-uaf-v1.2-ps-20201020/fido-uaf-protocol-v1.2-ps-20201020.html)

## Summary

The UAF Protocol Specification is the core normative UAF document. It defines the JSON messages that a FIDO Server and a UAF Client exchange for registration, authentication, transaction confirmation and deregistration. It also defines the shared structures (OperationHeader, FinalChallengeParams, ChannelBinding, Extension, MatchCriteria, Policy), the policy language servers use to say which authenticators are acceptable, version negotiation, and step-by-step processing rules for the server, the client and the authenticator in each operation.

The considerations chapter covers metadata, basic and ECDAA attestation, error handling, silent authenticators, TLS binding, KHAccessToken isolation, replay and clone protection, and interoperability. The chapter on assertion schemes defines the default TLV scheme, UAFV1TLV. The layers below are specified in the ASM API, Authenticator Commands and Registry documents; the app-facing APIs and HTTPS profile are in the client API/transport document. Server-side conformance largely means following the server processing rules in this document.

**Who needs it:** relying parties and FIDO Server developers, UAF client developers, authenticator vendors (authenticator processing rules and attestation)

**Look here for:**
- Server checks on a registration response → §3.4.6.5 `#h5_registration-response-processing-rules-for-fido-server`
- Server checks on an authentication response → §3.5.7.5 `#h5_authentication-response-processing-rules-for-fido-server`
- How a policy selects authenticators → §3.2 `#h3_processing-rules-for-the-server-policy`, §3.1.12 `#h4_matchcriteria-dictionary`
- Transaction content types and limits → §3.5.1 `#h4_transaction-dictionary`
- Using WebAuthn-style client data instead of FinalChallengeParams → §3.1.8 `#h4_collectedclientdata-dictionary`
- Basic vs. ECDAA attestation → §4.1.2 `#h4_authenticator-attestation`

**Changes from previous version:** The protocol minor version is now 2. The new CollectedClientData structure (§3.1.8) is an alternative to FinalChallengeParams for CTAP2/WebAuthn platforms; the server processing rules branch on which one was sent and hash it with `fcp.hashAlg`. ChannelBinding gains a `tokenBinding` field (RFC 8471). New §2.4 lists aaid, AppID and keyID as stable elements that other specs may rely on. New §4.2.2 tells servers not to reveal KeyIDs before some basic authentication, to prevent account enumeration. Servers must now reject assertions that carry unknown fields of extensions marked fail-if-unknown. Assertions in other schemes are processed by that scheme's rules if supported, where 1.1 skipped them; this opens the way for APCV1CBOR and WAV1CBOR. `text/plain` transaction content is UTF-8 (was ASCII), still at most 200 characters, and other content types are permitted, with text/plain and image/png recommended. Other changes: the pass-through status SYSTEM_INTERRUPTED; a rewritten rule for deriving MatchCriteria from `userVerificationDetails`; a client deregistration rule that returns NO_SUITABLE_AUTHENTICATOR; KeyIDs may also be generated by the ASM; attestation identifiers written without the `TAG_` prefix; new examples.

## Reading guide

**Start here:** §2.3 `#h3_protocol-conversation` for the four operations as flows, §3.1 `#h3_shared-structures-and-types` for the structures every message reuses (OperationHeader, FinalChallengeParams, ChannelBinding, Extension, MatchCriteria, Policy), then the two server rule sets that conformance testing leans on most: §3.4.6.5 `#h5_registration-response-processing-rules-for-fido-server` and §3.5.7.5 `#h5_authentication-response-processing-rules-for-fido-server`. Client implementers should add §3.2 `#h3_processing-rules-for-the-server-policy` and §3.3 `#h3_version-negotiation`. §4 is mostly informative rationale; §5 points the UAFV1TLV structures to the Authenticator Commands document.

**Section by section:**
- §2 Overview `#h2_overview`: scope and architecture (informative). §2.4 `#h3_relationship-to-other-specifications` fixes aaid, AppID and keyID as stable identifiers other specs may depend on.
- §3 intro `#h2_protocol-details`: all protocol elements mandatory unless stated; messages are UTF-8 JSON; TLS is assumed.
- §3.1.3 OperationHeader `#h4_operationheader-dictionary`: `upv` MUST be 1.2; `op` is Reg/Auth/Dereg ("Auth" covers transaction confirmation); `appID` (≤512) with three client rules: empty → use the caller's FacetID, equal to FacetID → accept, HTTPS URL → fetch the trusted facet list and accept only a listed facet; `serverData` (≤1536) is opaque to everyone but the server; `exts`.
- §3.1.4 AAID `#h4_authenticator-attestation-id-aaid-typedef`: `VVVV#MMMM` hex, case-insensitive; a new AAID is required when security characteristics change. §3.1.5 KeyID `#h4_keyid-typedef`: base64url 32–2048 bytes, unique per AAID; (AAID, KeyID) identifies a registration; 2ndF roaming authenticators can use the key handle as KeyID. §3.1.6 ServerChallenge `#h4_serverchallenge-typedef`: 8–64 random bytes.
- §3.1.7 FinalChallengeParams `#h4_finalchallengeparams-dictionary` (appID, challenge, facetID, channelBinding) and §3.1.8 CollectedClientData `#h4_collectedclientdata-dictionary` (WebAuthn-style challenge, origin, hashAlg, tokenBinding): the response's `fcParams` carries one of the two, and the server's checks differ by type.
- §3.1.9 ChannelBinding `#h4_tls-channelbinding-dictionary`: serverEndPoint, tlsServerCertificate, tlsUnique (deprecated), cid_pubkey, tokenBinding, each with MUST rules for when it is absent, "unused" or set. Servers MUST support all methods and MAY reject on mismatch. §3.1.10 JwkKey `#h4_jwkkey-dictionary` for ChannelID keys.
- §3.1.11 Extension `#h4_extension-dictionary`: id, data, fail_if_unknown; unknown extensions are passed through by client and ASM and flags preserved; the authenticator errors on unknown fail_if_unknown ones. Security-relevant extensions need a signed counterpart in the assertion; a security-degrading one must be critical (tag 0x3E11).
- §3.1.12 MatchCriteria `#h4_matchcriteria-dictionary`: `aaid` may be combined only with keyIDs, attachmentHint, authenticatorVersion and exts; without `aaid`, both `authenticationAlgorithms` and `assertionSchemes` MUST be present. Bit-flag fields match on any common bit; `userVerification` has its own algorithm around USER_VERIFY_ALL (§3.1.12.1 `#h5_dictionary-matchcriteria-members`). `attestationTypes` order is preference; `authenticatorVersion` in policy is deprecated.
- §3.1.13 Policy `#h4_policy-dictionary`: `accepted` is a list (OR) of sets (AND, i.e. several authenticators together), ordered by preference and never empty; `disallowed` always wins.
- §3.2 Policy processing `#h3_processing-rules-for-the-server-policy`: client rules for registration and authentication; an operation is approved only when a whole combination is satisfied. §3.2.1 examples (informative).
- §3.3 Version negotiation `#h3_version-negotiation`: client intersects {upv, asmVersion} pairs from itself, the message and each authenticator and picks the highest upv, then highest asmVersion.
- §3.4 Registration `#h3_registration-operation`: request (§3.4.2 `#h4_registrationrequest-dictionary`: header, challenge, username ≤128, policy), response (§3.4.5 `#h4_registrationresponse-dictionary`: header, fcParams, assertions). Server generation (§3.4.6.1 `#h5_registration-request-generation-rules-for-fido-server`): MUST put already-registered AAID/KeyIDs in `disallowed`, SHOULD disallow authenticators whose metadata status is unacceptable, should MAC serverData if relying on it. Client processing (§3.4.6.2 `#h5_registration-request-processing-rules-for-fido-uaf-clients`): FacetID check, build fcp, one preferred attestation type per ASM call, plus the ASM-status-to-ErrorCode table. Server response processing (§3.4.6.5): check upv, serverData, fcp fields (appID, facetID, channel binding, challenge freshness) or the CollectedClientData fields; per assertion check syntax and fail-if-unknown fields, scheme vs metadata, policy, FCHash (metadata hash for FinalChallengeParams, `hashAlg` for client data), preferred attestation (RECOMMENDED skip), authenticator version, RegCounter, then attestation by type (basic full: RFC 5280 chain to a metadata root then signature; surrogate: only if metadata has no roots, verify with the new key; ECDAA: verify against `ecdaaTrustAnchors`); store public key, KeyID, counters, version, AAID and PNG characteristics.
- §3.5 Authentication `#h3_authentication-operation`: Transaction (§3.5.1 `#h4_transaction-dictionary`: contentType; content base64url; text/plain is UTF-8 and ≤200 characters; PNG characteristics required for image/png). Server generation (§3.5.7.1 `#h5_authentication-request-generation-rules-for-fido-server`): step-up policies MUST name AAID and KeyID; transaction content per participating AAID's metadata, preferring PNG characteristics reported at registration. Server processing (§3.5.7.5): fcp checks as for registration, then per assertion: scheme, policy, version, lookup by (AAID, KeyID), SignCounter must increase unless unsupported, FCHash, for authenticationMode 2 the transaction hash must be in the cached transaction hashes, verify signature, update counter.
- §3.6 Deregistration `#h3_deregistration-operation`: no response message; empty aaid + empty keyID = all keys for the appID (must be the only entry), aaid + empty keyID = all keys of that model. Client rules (§3.6.4.2 `#h5_deregistration-request-processing-rules-for-fido-uaf-client`) include the FacetID check and NO_SUITABLE_AUTHENTICATOR when nothing matches.
- §4.1 Design considerations `#h3_protocol-core-design-considerations`: metadata, attestation (§4.1.2 `#h4_authenticator-attestation`; basic full and surrogate in §4.1.2.1 `#h5_basic-attestation`, with attestation keys shared by at least 100,000 devices; ECDAA in §4.1.2.2 `#h5_direct-anonymous-attestation-ecdaa`), error handling, silent authenticators (§4.1.6 `#h4_silent-authenticators`: removable keys, no transaction confirmation, metadata must say USER_VERIFY_NONE), TLS expectations (§4.1.7 `#h4_tls-protected-communication`).
- §4.2 Implementation `#h3_implementation-considerations`: challenge randomness; §4.2.2 `#h4_revealing-keyids` (reveal KeyIDs only after some prior authentication, to avoid account enumeration).
- §4.3 Security `#h3_security-considerations`: client trust model and KHAccessToken (§4.3.3 `#h4_fido-client-trust-model`), TLS binding trade-offs (§4.3.4 `#h4_tls-binding`), serverData and key handles (§4.3.7 `#h4_serverdata-and-keyhandle`), metadata over client-reported data (§4.3.8), policy tampering detected by the server (§4.3.9 `#h4_policy-verification`), replay (§4.3.10), clones (§4.3.11 `#h4_protection-against-cloned-authenticators`), RegCounter as fraud signal (§4.3.12). §4.4 `#h3_interoperability-considerations` describes app types.
- §5 UAFV1TLV `#h3_assertion-scheme-uafv1tlv`: mandatory for servers and authenticators; servers MUST implement all non-optional algorithms, key formats and attestation types in the registries.

**What matters most:**
- The server response rules are the conformance core: every "continue with next assertion" branch, the FCHash computation for both fcp types, the attestation-by-type logic and the counter checks (§3.4.6.5, §3.5.7.5).
- AppID/FacetID handling on the client, including the empty-AppID case, which binds the key to one facet (§3.1.3.1 `#h5_dictionary-operationheader-members`).
- Policy construction rules (aaid combinations, mandatory algorithms/schemes, registered keys in `disallowed`) and client matching, including the USER_VERIFY_ALL logic (§3.1.12, §3.4.6.1).
- Transaction confirmation: content limits and hash comparison against cached content (§3.5.1, §3.5.7.5).
- Channel binding: clients must send what they have; servers must understand all types and decide how strict to be (§3.1.9, §4.3.4).

**Watch out for:**
- Both server rule sets still say UAFV1TLV is the only defined scheme, while the same rules now hand other schemes to their own documents (APCV1CBOR, WAV1CBOR).
- The CollectedClientData checks in the authentication rules speak of a "registration request", and the generation rules write `p.allowed` for the field named `accepted`.
- The SignCounter and RegCounter rules treat `isKeyRestricted` false as "counter not supported", which reads like a slip; the WAV1CBOR document copies it.
- §3.5.7.4 says to fill `AuthenticationResponse.FinalChallengeParams`, but the field is `fcParams`.
- tlsUnique is deprecated and Token Binding / ChannelID support depends on the platform; servers that require bindings can break legitimate clients behind TLS-intercepting proxies (§4.3.4).
- §4 is marked non-normative as a whole, yet several of its subsections contain MUST statements (attestation, silent authenticators).

**Related documents:** fido-uaf-authnr-cmds (KRD/SignedData byte layout, authenticator processing), fido-uaf-asm-api (ASM requests and status codes), fido-uaf-client-api-transport (app APIs, ErrorCodes, HTTPS profile), fido-uaf-reg (tags, predefined extensions), fido-uaf-apccbor and fido-uaf-webauthn (additional 1.2 assertion schemes that plug into §3.4.6.5/§3.5.7.5), and the shared AppID and Facet, Metadata Statement, Metadata Service, Registry and ECDAA documents.
