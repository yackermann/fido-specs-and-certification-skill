# FIDO UAF Authenticator-Specific Module API

Version 1.1 · Proposed Standard · 2017-02-02 · [source](https://fidoalliance.org/specs/fido-uaf-v1.1-ps-20170202/fido-uaf-asm-api-v1.1-ps-20170202.html)

## Summary

The 1.1 edition of the ASM API, the version FIDO lists for certification. It defines the same JSON request set (GetInfo, Register, Authenticate, Deregister, GetRegistrations, OpenSettings), status codes, processing rules, and the KHAccessToken and access-control guidance as 1.2, with `asmVersion` 1.1. Compared with 1.2, it has no CTAP2 interface chapter, no Java (Android) or C++ (iOS) ASM interfaces (only the Android intent/AIDL and Windows bindings), no SYSTEM_INTERRUPTED status, no appID-in-final-challenge check, and no forwarding of request extensions to the authenticator.

**Who needs it:** authenticator vendors writing ASMs and UAF client developers targeting UAF 1.1

**Look here for:**
- Status code mapping → §3.2.2 `#h4_mapping-authenticator-status-codes-to-asm-status-codes`
- Register processing → §3.6.3 `#h4_detailed-description-for-processing-the-register-request`
- Platform bindings (Android, Windows) → §5 `#h2_using-the-asm-api-on-various-platforms`
- KHAccessToken → §6.1 `#h3_khaccesstoken`

## Reading guide

**Use this version when:** you build or certify a UAF 1.1 ASM or client (UAF 1.1 is the version FIDO certifies). Requests in this edition carry `asmVersion` 1.1, and the processing rules here are what a 1.1 client expects from an ASM.

**Differences from 1.2** (from a text comparison):
- §3.2 `#h3_statuscode-interface` has no UAF_ASM_STATUS_SYSTEM_INTERRUPTED (0x12). §3.3.1 `#h4_dictionary-asmrequest-members` requires asmVersion 1.1.
- §3.6.3 `#h4_detailed-description-for-processing-the-register-request` does not check that RegisterIn.appID equals the appID inside the decoded final challenge (1.2 adds this, returning ACCESS_DENIED on mismatch).
- Neither Register nor Authenticate (§3.7.4 `#h4_detailed-description-for-processing-the-authenticate-request`) forwards `ASMRequest.exts` to the authenticator as TAG_EXTENSION, and the request descriptions do not mention exts.
- §3.9.3 `#h4_detailed-description-for-processing-the-getregistrations-request` does not say what to return for non-bound authenticators (1.2: an empty list).
- §5 `#h2_using-the-asm-api-on-various-platforms` has only the Android intent API (with AIDL alternative) and Windows; there is no Java ASM API for Android, no C++ API for iOS, and no CTAP2 interface chapter.
- §6.1 KHAccessToken `#h3_khaccesstoken` lacks 1.2's explicit permission for alternative key-handle binding methods of equal strength and its list of platform assumptions.

**Section by section:** structure of §2–§4 as in 1.2; see that page's reading guide. Key parts: the status mapping table in §3.2.2 `#h4_mapping-authenticator-status-codes-to-asm-status-codes` (USER_NOT_ENROLLED maps differently for Register and Sign); Register and Authenticate processing, including KHAccessToken construction, final-challenge hashing, the bound-authenticator KeyID database and username disambiguation; Deregister with an empty keyID meaning all keys for the appID (§3.8.2 `#h4_detailed-description-for-processing-the-deregister-request`); the Android ASM intent with type `application/fido.uaf_asm+json` (§5.1 `#h3_android-asm-intent-api`); Windows DLL discovery through the HKCU/HKLM `Software\FIDO\UAF\ASM` keys (§5.2 `#h3_windows-asm-api`); and the MUST-level isolation, storage and silent-authenticator consent rules plus the access-control table in §6 `#h2_security-and-privacy-guidelines` and §6.2 `#h3_access-control-for-asm-apis`. Pair this edition with fido-uaf-authnr-cmds 1.1 and fido-uaf-protocol 1.1.
