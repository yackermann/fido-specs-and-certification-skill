# FIDO UAF Authenticator-Specific Module API

Version 1.2 · Proposed Standard · 2020-10-20 · [source](https://fidoalliance.org/specs/fido-uaf-v1.2-ps-20201020/fido-uaf-asm-api-v1.2-ps-20201020.html)

## Summary

The ASM API specifies the interface between a UAF Client and an Authenticator-Specific Module (ASM). The ASM is the platform component that knows how to reach a particular authenticator (over SPI, USB, Bluetooth and so on) and hides that from the client. The API is JSON-based, with these requests: GetInfo, Register, Authenticate, Deregister, GetRegistrations and OpenSettings. The document defines each request's input and output objects, the ASM status codes and how authenticator status codes map onto them, and what the ASM does internally for each request. That includes hashing the final challenge, building the TLV authenticator commands, managing KeyHandles and the KeyID database for bound authenticators, and checking the caller.

Platform bindings are given for Android (intent API with an AIDL alternative, plus a Java interface), iOS (C++ interface) and Windows. A security chapter covers KHAccessToken and access control. An optional chapter maps CTAP2 commands onto UAF authenticator commands. The authenticator side of each call is in Authenticator Commands; the client side is in the Protocol and client API documents.

**Who needs it:** authenticator vendors writing ASMs, UAF client and platform developers

**Look here for:**
- ASM status codes and how authenticator codes map to them → §3.2.2 `#h4_mapping-authenticator-status-codes-to-asm-status-codes`
- What the ASM must do on Register → §3.6.3 `#h4_detailed-description-for-processing-the-register-request`
- What the ASM must do on Authenticate → §3.7.4 `#h4_detailed-description-for-processing-the-authenticate-request`
- How a client discovers ASMs on Android → §5.1.1 `#h4_discovering-asms`
- Exposing a UAF authenticator over CTAP2 → §6 `#h2_ctap2-interface`
- How KHAccessToken binds keys to callers → §7.1 `#h3_khaccesstoken`

**Changes from previous version:** `asmVersion` is now 1.2. New §6 CTAP2 Interface (optional) lets an ASM present its authenticator as an external CTAP2 authenticator over CTAP transports, and maps authenticatorMakeCredential, GetAssertion, GetNextAssertion, Cancel, Reset and GetInfo onto UAF commands. New Java ASM API for Android (§5.2) and C++ ASM API for iOS (§5.3), intended for KeyStore/KeyChain-based authenticators whose ASM runs inside the relying party app. New status UAF_ASM_STATUS_SYSTEM_INTERRUPTED (0x12). Register processing now checks that the appID matches the appID inside the final challenge. Register and Authenticate pass `ASMRequest.exts` to the authenticator as TAG_EXTENSION. The security chapter is renumbered from 6 to 7.

## Reading guide

**Start here:** §3 intro `#h2_asm-requests-and-responses` (JSON in, JSON out; the processing rules assume UAFV1TLV, and custom command interfaces must behave equivalently), §3.2.2 `#h4_mapping-authenticator-status-codes-to-asm-status-codes` (status translation), then the two big processing descriptions §3.6.3 `#h4_detailed-description-for-processing-the-register-request` and §3.7.4 `#h4_detailed-description-for-processing-the-authenticate-request`. Finish with §7 `#h2_security-and-privacy-guidelines`, which holds most of the MUSTs that certification relies on.

**Section by section:**
- §2 Overview `#h2_overview` (informative): the ASM hides the physical link to one or more authenticators; platforms may expose ASM functions through other APIs (KeyStore, KeyChain) provided the ASM talks to the authenticator as defined here.
- §3.2 StatusCode `#h3_statuscode-interface`: UAF_ASM_STATUS_* values. Unknown authenticator codes are treated as ERR_UNKNOWN → ERROR; a client that does not know an ASM code SHALL treat it as ERROR.
- §3.2.2 mapping: mostly pass-through. USER_NOT_ENROLLED → USER_NOT_ENROLLED for Register but ACCESS_DENIED for Sign; CMD_NOT_SUPPORTED → OK if the ASM can do the job itself (e.g. deregistering a bound key) else ERROR; ATTESTATION_NOT_SUPPORTED and PARAMS_INVALID → ERROR (an ASM bug); timeout → retry, then ERROR.
- §3.3–3.4 ASMRequest/ASMResponse `#h3_asmrequest-dictionary`, `#h3_asmresponse-dictionary`: requestType, asmVersion (MUST be 1.2), authenticatorIndex (MUST NOT be set for GetInfo), args, exts.
- §3.5 GetInfo `#h3_getinfo-request`: AuthenticatorInfo (§3.5.2 `#h4_authenticatorinfo-dictionary`) is what the client matches against policy: isUserEnrolled (MUST be true for authenticators without UV, per OS user for bound ones), assertionScheme, algorithm, attestationTypes, UV/key/matcher protection, isSecondFactorOnly, isRoamingAuthenticator, tcDisplay rules. Indices should be persistent.
- §3.6 Register `#h3_register-request`: verify or enrol the user (obtaining a UserVerificationToken if supported), check that RegisterIn.appID equals the appID inside the decoded final challenge, build KHAccessToken, hash the final challenge with the authenticator's algorithm, send TAG_UAFV1_REGISTER_CMD with extensions as TAG_EXTENSION, store CallerID/AppID/KeyHandle/KeyID for bound authenticators, return base64url assertion.
- §3.7 Authenticate `#h3_authenticate-request`: ACCESS_DENIED if no user enrolled; the ASM MUST have the user verified; second-factor authenticators need keyIDs; bound authenticators map keyIDs to KeyHandles via the database, roaming ones treat keyIDs as KeyHandles; pick the best-fitting transaction and base64url-decode its content; when a first-factor authenticator returns several usernames, keep the newest per username and let the user choose, then re-send Sign.
- §3.8 Deregister `#h3_deregister-request`: an empty keyID MUST deregister every key for the appID; bound authenticators delete database entries. §3.9 GetRegistrations `#h3_getregistrations-request` (bound only; empty list otherwise). §3.10 OpenSettings `#h3_opensettings-request`.
- §5 Platforms `#h2_asm-apis-for-various-platforms`: Android intent `org.fidoalliance.intent.FIDO_OPERATION` with type `application/fido.uaf_asm+json`, startActivityForResult, no UI for GetInfo (§5.1 `#h3_android-asm-intent-api`), AIDL variant for UI-less ASMs (§5.1.2 `#h4_alternate-android-aidl-service-asm-implementation`); in-process Java (§5.2 `#h3_java-asm-api-for-android`) and C++ iOS (§5.3 `#h3_c-asm-api-for-ios`) interfaces for KeyStore/KeyChain authenticators; Windows DLLs found under `Software\FIDO\UAF\ASM` (§5.4 `#h3_windows-asm-api`).
- §6 CTAP2 Interface `#h2_ctap2-interface` (optional): an ASM can expose its UAF authenticator over CTAP2. MakeCredential (§6.1.1 `#h4_processing-rules-for-authenticatormakecredential`) maps rp.id or webauthn_appid to AppID, clientDataHash to FinalChallengeHash, user.id to `fido.uaf.userid`, and synthesises authData (AAGUID = AAID padded with zeros, credential ID = key handle) with fmt "fido-uaf". GetAssertion (§6.2.1 `#h4_processing-rules-for-authenticatorgetassertion`) maps txAuth extensions to transaction content; GetNextAssertion is unsupported; GetInfo reports FIDO_2_0 (§6.6.1 `#h4_processing-rules-for-authenticatorgetinfo`).
- §7 Security `#h2_security-and-privacy-guidelines`: credential isolation between clients and between ASMs, a short allow-list of what an ASM may store, consent UI for every silent-authenticator registration. §7.1 KHAccessToken `#h3_khaccesstoken` (AppID, plus ASMToken, PersonaID and CallerID for bound authenticators, hashed; equal-strength alternatives allowed). §7.2 access-control table `#h3_access-control-for-asm-apis`.

**What matters most:**
- KHAccessToken (or an equivalent binding) is mandatory for bound authenticators and is what stops another app or ASM from using the keys (§7.1).
- User verification is required for every Register and Authenticate regardless of authenticator type (§7.2), and silent authenticators need explicit consent at registration (§7).
- The appID/final-challenge consistency check in Register is new in 1.2 and easy to omit (§3.6.3).
- Correct status mapping matters to the client's error handling and to conformance tooling (§3.2.2).

**Watch out for:**
- §3.7.4 says to add extensions "to the TAG_UAFV1_REGISTER_CMD" during Authenticate; it means the Sign command. It also says "Go to step #8" in an unnumbered list.
- The response status lists per request do not include SYSTEM_INTERRUPTED, and the Authenticate list omits INSUFFICIENT_AUTHENTICATOR_RESOURCES, although §3.2 defines both.
- The mapping table names the timeout code UAF_STATUS_CMD_TIMEOUT rather than UAF_CMD_STATUS_TIMEOUT.
- In the CTAP2 chapter, fmt "fido-uaf", credential type "public-key-uaf" and an authData taken from the UAF signed data are UAF-specific choices that a standard WebAuthn relying party will not recognise; the chapter does not discuss this. The UV flag is set whenever the authenticator is not silent.
- §5.3's C++ listing has an include directive with no header name and type names (IEnumerator, ICallback) that do not match its own declarations; treat it as illustrative.

**Related documents:** fido-uaf-authnr-cmds (the TLV commands the ASM sends, KeyHandle and KHAccessToken handling inside the authenticator); fido-uaf-protocol (client side, final challenge, policy); fido-uaf-client-api-transport (the client's own API, built on AuthenticatorInfo); fido-uaf-webauthn (the reverse direction: CTAP2 authenticators used through UAF, with its own CTAP2-to-ASM error table); fido-uaf-reg (extensions such as `fido.uaf.userid`).
