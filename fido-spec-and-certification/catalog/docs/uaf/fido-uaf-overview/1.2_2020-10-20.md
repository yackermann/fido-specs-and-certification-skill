# FIDO UAF Architectural Overview

Version 1.2 · Proposed Standard · 2020-10-20 · [source](https://fidoalliance.org/specs/fido-uaf-v1.2-ps-20201020/fido-uaf-overview-v1.2-ps-20201020.html)

## Summary

The UAF Architectural Overview is the non-normative entry point to the UAF specification set. It sets out what UAF is for (passwordless and second-factor login with authenticators on or attached to the user's device), names the building blocks (UAF Client, UAF Server, the UAF protocols, the Authenticator-Specific Module layer, the authenticator, and metadata-based validation of authenticator models) and walks through the main flows: enrolment, registration, authentication, step-up, transaction confirmation, deregistration and the adoption of new authenticator types.

It also gives the recommended reading order for the UAF and shared FIDO documents, a short privacy section, and positioning against OpenID/SAML/OAuth and against OATH, TCG, PKCS#11 and ISO 24727. It contains no requirements; the normative rules are in the protocol, authenticator commands, ASM API, client API/transport and registry documents. The reading list in §1.2 was not updated for 1.2 and does not mention the two new assertion-format documents (APCV1CBOR, WAV1CBOR).

**Who needs it:** anyone new to UAF: authenticator vendors, client and platform developers, relying parties and server developers, certification applicants

**Look here for:**
- Which UAF document covers which layer, and in what order to read them → §1.2 `#h3_fido-uaf-documentation`
- What the client, server, ASM and authenticator each do → §2 `#h2_fido-uaf-high-level-architecture`

## Reading guide

**Start here:** §1.2 `#h3_fido-uaf-documentation` for the map of documents and the suggested reading order, §2 `#h2_fido-uaf-high-level-architecture` for who does what, and §3.2 `#h3_authenticator-registration` / §3.3 `#h3_authentication` for the two flows everything else builds on. The whole document is informative; nothing here is tested directly.

**Section by section:**
- §1 Introduction `#h2_introduction`, §1.1 Background `#h3_background`: lists the six UAF specs and the shared FIDO documents (AppID/Facets, Metadata Statements, MDS, Registry, ECDAA, Security Reference, Glossary), and contrasts UAF (passwordless or multi-factor with local user verification) with U2F (second factor next to a password).
- §1.2 Documentation `#h3_fido-uaf-documentation`: one line per document saying what layer it covers. Recommended order: this overview, then the Glossary, then the UAF documents.
- §1.3 Goals `#h3_fido-uaf-goals`: design aims such as multi-factor support, RP choice of mechanism, extensibility, complementing federation, and user privacy.
- §2.1–2.2 Client `#h3_fido-uaf-client` and Server `#h3_fido-uaf-server`: the client talks to authenticators through the abstraction layer and to the RP through a user agent; the server validates attestation against metadata, keeps the authenticator-to-account mapping, and checks authentication and transaction-confirmation responses. The server may be on-premise or outsourced.
- §2.3 Protocols `#h3_fido-uaf-protocols`: the four operations (registration with discovery and attestation, authentication, transaction confirmation, deregistration).
- §2.4 Abstraction layer `#h3_fido-uaf-authenticator-abstraction-layer` (the ASM idea), §2.5 Authenticator `#h3_fido-uaf-authenticator`, §2.6 Metadata validation `#h3_fido-uaf-authenticator-metadata-validation`: attestation is verified with certificates the server gets out of band through metadata.
- §3 Usage scenarios `#h2_fido-uaf-usage-scenarios-and-protocol-message-flows`: enrolment with the authenticator is outside UAF (§3.1 `#h3_fido-uaf-authenticator-acquisition-and-user-enrollment`); step-up (§3.4 `#h3_step-up-authentication`); WYSIWYS transaction confirmation (§3.5 `#h3_transaction-confirmation`); deregistration when an account is closed or a device lost (§3.6 `#h3_authenticator-deregistration`); adding a new authenticator type is a metadata entry plus its attestation certificate (§3.7 `#h3_adoption-of-new-types-of-fido-uaf-authenticators`). The message flows are figures only.
- §4 Privacy `#h2_privacy-considerations`: no global device identifier, per-device/account/RP key pairs, local user verification with no biometric data sent, and attestation keys shared across batches of at least 100,000 units.
- §5 `#h2_relationship-to-other-technologies` (with OpenID, SAML, and OAuth `#openid-saml-and-oauth`) and §6 `#h2_oath-tcg-pkcs-11-and-iso-24727`: positioning only.

**What matters most:**
- Use §1.2 to route a question to the right normative document; the overview itself defines no message, field or rule.
- The privacy list in §4 summarises properties the normative specs enforce (for example the batch-size rule for basic attestation); check the protocol and authenticator commands documents for the actual requirement.

**Watch out for:**
- The 1.2 edition is the 1.1 text with new dates. The document lists and §1.2 omit fido-uaf-apccbor and fido-uaf-webauthn, and nothing mentions CTAP2/WebAuthn integration added in UAF 1.2.
- Some names are dated: "FIDO UAF Application API and Transport Binding" is fido-uaf-client-api-transport, and the U2F description predates FIDO2.
- §3.3 notes that a client may consult external services while verifying the user, provided the FIDO privacy principles hold; this is a statement of intent, not a rule.

**Related documents:** fido-uaf-protocol (the normative messages and processing rules), fido-uaf-client-api-transport, fido-uaf-asm-api, fido-uaf-authnr-cmds, fido-uaf-reg, fido-uaf-apdu, and for 1.2 additions fido-uaf-apccbor and fido-uaf-webauthn.
