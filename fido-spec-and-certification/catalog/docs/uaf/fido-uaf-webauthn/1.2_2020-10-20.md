# FIDO UAF WebAuthentication Assertion Format

Version 1.2 · Proposed Standard · 2020-10-20 · [source](https://fidoalliance.org/specs/fido-uaf-v1.2-ps-20201020/fido-uaf-webauthn-v1.2-ps-20201020.html)

## Summary

This UAF 1.2 document defines the WAV1CBOR assertion scheme, which lets a WebAuthn/CTAP2 authenticator be used through the UAF protocol. An ASM talks to the authenticator over CTAP2 and wraps the results in UAF assertion structures, so that a UAF server can register and authenticate the authenticator.

The registration assertion (TAG_WAV1CBOR_REG_ASSERTION) carries the WebAuthn authenticatorData with attested credential data concatenated with the client data hash, the attestation format name (`fmt`) and the attestation statement. The authentication assertion (TAG_WAV1CBOR_AUTH_ASSERTION) carries authenticatorData plus the client data hash, the AAGUID, the credential ID as the KeyID, and the signature. The processing rules describe how the ASM calls authenticatorGetInfo and the other CTAP2 commands, handles clientPin enrolment and builds the assertions, and how the FIDO Server verifies them, using the AAGUID for metadata lookup and policy matching. A final table maps CTAP2 error codes to ASM status codes.

This is a new document in UAF 1.2. It works together with the CTAP2 interface chapter of the ASM API 1.2, CollectedClientData in the Protocol 1.2, and the resident key and attestation conveyance extensions in the Registry 1.2.

**Who needs it:** ASM developers bridging CTAP2 authenticators into UAF, FIDO Server developers accepting such assertions

## Reading guide

**Start here:** §3 `#h2_data-structures-for-wav1cbor` for the two TLV wrappers around WebAuthn data, then §4.1 `#h3_registration-response-processing-rules-for-asm` to see how an ASM drives authenticatorMakeCredential, and §4.4 `#h3_authentication-response-processing-rules-for-fido-server` for what a UAF server must check. §2 is one informative sentence.

**Section by section:**
- §3.1 Registration Assertion `#h3_registration-assertion`: TAG_WAV1CBOR_REG_ASSERTION containing tbsData (authenticatorData *with* attestedCredentialData, followed by the clientDataHash), TAG_ATTESTATION_FORMAT (WebAuthn `fmt`) and TAG_ATTESTATION_STATEMENT (`attStmt`, signature in `sig`).
- §3.2 Authentication Assertion `#h3_authentication-assertion`: TAG_WAV1CBOR_AUTH_ASSERTION with TAG_WAV1CBOR_SIGNED_DATA (authenticatorData without attested data, followed by clientDataHash), TAG_AAGUID (may be empty), TAG_KEYID (the credential ID) and TAG_SIGNATURE over tbsData only.
- §4.1 ASM registration `#h3_registration-response-processing-rules-for-asm`: call authenticatorGetInfo and note rk, clientPin, up, uv and plat; enrol a clientPin if the UVM extension asks for it and none is set; hash the final challenge and use it as clientDataHash; consume `fido.uaf.rk` and `fido.uaf.ac`, translate other UAF extensions into WebAuthn extensions (unknown with fail_if_unknown true → UAF_ASM_STATUS_ERROR). rp.id is the AppID; user.id comes from `fido.uaf.userid`, and registration fails without it. The UVM extension sets the up/uv options (biometric/passcode → uv+up; clientPin → uv only; presence → up only; none → neither). CTAP errors map through §5.
- §4.2 Server registration `#h3_registration-response-processing-rules-for-fido-server`: replaces skipping at step 6.8 of protocol §3.4.6.5. Read claimedAAGUID from attested credential data; check metadata assertionScheme and policy; compute FCHash (metadata hash for FinalChallengeParams, `fcp.hashAlg` for CollectedClientData) and compare with the trailing clientDataHash; check up/uv bits against the requested UVM; verify attestation as basic full (chain to metadata roots, then `sig`), surrogate (no roots allowed, Android key attestation extension required) or ECDAA. Store credential public key, credential ID as KeyID, the counter, AAGUID, and AuthenticatorVersion 0.
- §4.3 ASM authentication `#h3_authentication-response-generation-rules-for-asm`: CallerID check for bound authenticators, KeyID-to-KeyHandle lookup (roaming: KeyIDs are the handles), username choice if several match, transaction mapped to `txAuthSimple` (text/plain) or `txAuthGeneric` (other types), authenticatorGetAssertion with the same up/uv mapping, GetNextAssertion when numberOfCredentials > 1, AAGUID copied if known (remembered or from GetInfo).
- §4.4 Server authentication: replaces skipping at step 6.5 of protocol §3.5.7.5. Look up UAuth.pub by AAGUID and KeyID (KeyID alone if AAGUID empty, first match wins); check scheme and policy; sign-counter clone check; clientDataHash == FCHash; up/uv vs UVM; transaction (txAuthSimple) or its hash (txAuthGeneric) must be in the RP's cached transactions; verify the signature; update the counter.
- §5 CTAP2 → ASM error mapping `#h2_mapping-ctap2-error-codes-to-asm-error-codes`: most codes become UAF_ASM_STATUS_ERROR; timeouts → USER_NOT_RESPONSIVE; PIN invalid/required/policy, UP required, operation denied → ACCESS_DENIED; PIN blocked → USER_LOCKOUT; PIN not set → USER_NOT_ENROLLED; key store full or request too large → INSUFFICIENT_AUTHENTICATOR_RESOURCES.

**What matters most:**
- tbsData is authenticatorData plus the hashed UAF final challenge; the server splits it by parsing the authenticatorData and comparing the remainder with FCHash (§4.2, §4.4).
- The UAF registration request must carry `fido.uaf.userid`, or the ASM cannot build the CTAP2 user entity (§4.1).
- Metadata is looked up by AAGUID rather than AAID, and AuthenticatorVersion is fixed at 0, so the firmware-version check from the UAFV1TLV rules does nothing here (§4.2).
- User verification is proven by the up/uv flags plus the optional UVM response, and the server must judge them against the requested UVM (§4.2, §4.4).

**Watch out for:**
- §3.2 and §4.4 expect the clientDataHash after authenticatorData, but the ASM rule in §4.3 copies only `result.authData` into TAG_WAV1CBOR_SIGNED_DATA (the registration rule in §4.1 does append the hash). Follow §3.2.
- §3.1 names the inner tag TAG_WAV1CBOR_REG_DATA, while §4.1 and §4.2 say TAG_WAV1CBOR_SIGNED_DATA. None of the WAV1CBOR tags, TAG_AAGUID, TAG_ATTESTATION_FORMAT or TAG_ATTESTATION_STATEMENT is allocated in the UAF Registry 1.2.
- §4.2 verifies attestation by looking for UAF attestation types (ATTESTATION_BASIC_FULL with TAG_ATTESTATION_CERT, surrogate, ECDAA) inside a WebAuthn attestation statement; there is no rule for each WebAuthn `fmt`.
- The step numbers for the hook points (6.8/6.5) differ from those cited by fido-uaf-apccbor (6.9/6.6); find the "skip unknown assertion scheme" step in the protocol text rather than trusting the number.
- The sign-counter rule in §4.4 treats `isKeyRestricted` false as "counter not supported", which looks like a slip.
- §4.1 reads `fido.uaf.rk` and `fido.uaf.ac` into parameters, but the options list sets only up/uv; how rk and ac reach the CTAP call is not spelled out. Option names also vary between userVerification/userPresence (§4.1) and uv/up (§4.3).
- No CTAP2 code maps to a user-cancelled status (KEEPALIVE_CANCEL → ERROR).
