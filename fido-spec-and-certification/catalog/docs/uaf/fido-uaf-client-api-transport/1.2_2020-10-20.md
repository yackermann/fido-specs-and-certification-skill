# FIDO UAF Application API and Transport Binding Specification

Version 1.2 · Proposed Standard · 2020-10-20 · [source](https://fidoalliance.org/specs/fido-uaf-v1.2-ps-20201020/fido-uaf-client-api-transport-v1.2-ps-20201020.html)

## Summary

The UAF Application API and Transport Binding Specification defines how a relying party's web page or native app talks to the UAF Client, and how UAF messages travel to the FIDO Server. It defines the shared types (UAFMessage, Version, Authenticator, DiscoveryData, ErrorCode). It then gives three client bindings: a DOM API for browsers (`navigator.fido.uaf` with discover, checkPolicy and processUAFOperation calls and their callbacks, plus privacy and same-origin rules); an Android intent API (FIDO_OPERATION intent types, permissions, an AIDL service alternative and caller checks); and an iOS custom-URL API using x-callback-url, with encrypted payloads.

The transport chapter sets TLS requirements and an HTTPS interoperability profile: GetUAFRequest, ReturnUAFRequest and SendUAFResponse objects, the ServerResponse and Token interfaces, and the `application/fido+uaf` media type. The message contents themselves are defined in the Protocol specification.

**Who needs it:** relying party web and app developers, UAF client and browser/platform developers, FIDO Server developers (HTTPS profile)

**Look here for:**
- Error codes returned to the calling app → §4.5 `#h3_errorcode-interface`
- Browser API methods → §5.2 `#h3_uaf-interface`
- Android intent operations → §6.2 `#h3_org.fidoalliance.intent.fido_operation-intent`
- iOS x-callback-url binding → §7.1 `#h3_ios-specific-definitions`
- TLS requirements → §8.2 `#h3_tls-security-requirements`
- HTTPS message exchange with the server → §8.3 `#h3_HttpsTransportInteroperabilityProfile`

**Changes from previous version:** New error code SYSTEM_INTERRUPTED (0x12). On Android 5 and later, UAF Clients MUST NOT (was SHOULD NOT) declare the FIDO_CLIENT permission. Relying party apps that use the AIDL service MUST bind with an explicit intent. On iOS, payloads are base64url rather than base64, a Swift example is added, and the result descriptions are rewritten around the x-callback-url `errorCode` instead of Android-style result codes. In the HTTPS profile, the client's Content-Type header is now a SHOULD, and servers MUST accept `application/fido+uaf`. Also: a pointer to how authenticator flags are combined, a leftover TODO note removed, and RFC 2119 keywords capitalised.

## Reading guide

**Start here:** §2.3.1 `#h4_protocol-conversation` for the app-side flow (fetch request, hand it to the client, post the response, report the server result back), §4 `#h2_shared-definitions` for the types every binding shares, then the binding you need: §5 DOM `#h2_dom-api`, §6 Android `#h2_android-intent-api` or §7 iOS `#h2_ios-custom-url-api`. Server developers can go straight to §3.1 `#h3_uaf-status-codes` and §8.3 `#h3_HttpsTransportInteroperabilityProfile`.

**Section by section:**
- §2 Overview `#h2_overview` (informative): the APIs and HTTPS profile are examples to aid interoperability, not mandatory patterns. Discovery has no server exchange; deregistration has no response; apps should not edit UAF messages because they may carry integrity protection.
- §3.1 UAF Status Codes `#h3_uaf-status-codes`: server-level result codes (1200 OK, 1202 accepted-pending, 1400–1408, 1480 unknown AAID, 1481 unknown KeyID with a recommendation that the client delete the key, 1490 channel binding refused, 1491 bad/replayed nonce, 1492–1498 unacceptable authenticator/key/algorithm/attestation/content, 1500). They are not HTTP status codes.
- §4.1 UAFMessage `#h3_uafmessage-dictionary`: `uafProtocolMessage` plus optional `additionalData`.
- §4.3 Authenticator `#h3_authenticator-interface`: the discovery view of an authenticator (AAID, versions, assertion scheme, algorithm, attestation types, UV/key/matcher protection, attachment hint, tcDisplay fields, icon, extension IDs). The client must synthesise title, description and icon if the ASM gives none; tcDisplay MUST be 0 without transaction confirmation; tcDisplayContentType MUST be set when it is non-zero; PNG characteristics MUST be listed for image/png. attachmentHint is a hint only, not attested.
- §4.4 DiscoveryData `#h3_discoverydata-dictionary` and §4.5 ErrorCode `#h3_errorcode-interface`: client-side error codes 0x00–0x12 and 0xFF, including WAIT_USER_ACTION (a progress code), INSECURE_TRANSPORT, UNTRUSTED_FACET_ID, NO_SUITABLE_AUTHENTICATOR and the 1.2 addition SYSTEM_INTERRUPTED.
- §5.2 uaf interface `#h3_uaf-interface`: `discover`, `checkPolicy` (MUST always call back, NO_ERROR if a suitable authenticator exists, without prompting), `processUAFOperation`, and `notifyUAFResult`, which applications MUST call when they get a server status code. §5.3–5.5 define the callbacks; ErrorCallback can fire repeatedly.
- §5.6–5.8 (informative) `#h3_privacy-considerations-for-the-dom-api`, `#h3_security-considerations-for-the-dom-api`, `#h3_implementation-notes-for-browser-plugin-authors`: no insecure mixed content (immediate INSECURE_TRANSPORT), same-origin transport, and the browser, not the page, supplies the origin.
- §6.1 Android definitions `#h3_android-specific-definitions`: FIDO_CLIENT permission MUST be declared before Android 5 and MUST NOT be from Android 5; an explicit `origin` needs ACT_AS_WEB_BROWSER, which the client MUST check; otherwise the facet is `android:apk-key-hash:`. Apps should pin later intents to the same client via componentName.
- §6.2 FIDO_OPERATION intent `#h3_org.fidoalliance.intent.fido_operation-intent`: one intent with MIME type `application/fido.uaf_client+json` and a UAFIntentType extra; extras table per type; all requests via startActivityForResult(); UAF_OPERATION_COMPLETION_STATUS MUST be sent back.
- §6.3 AIDL `#h3_alternate-android-aidl-service-uaf-client-implementation` and §6.4 `#h3_security-considerations-for-android-implementations`: same intents over a bound service (caller identified by Binder UID); RP apps MUST bind with an explicit intent; WebView injection must follow DOM rules.
- §7.1 iOS definitions `#h3_ios-specific-definitions`: x-callback-url on the `FidoUAFClient1` scheme, base64url JSON, facet from the `sourceApplication` bundle ID (MUST be used), a fresh per-request key (MUST), and a JWE response with `dir` + A128CBC-HS256. §7.2 `#h3_json-values` mirrors the Android operations; §7.3 `#h3_implementation-guidelines-for-ios-implementations` recommends skipping DISCOVER and CHECK_POLICY because every call switches apps.
- §8.1–8.2 `#h3_TransportSecurityRequirements`, `#h3_tls-security-requirements` (marked informative): authenticate the server for the reported origin, confidentiality and integrity, fail hard on any TLS error, no anon/null suites, supply and verify channel bindings.
- §8.3 HTTPS profile (optional to implement): POST only; GetUAFRequest → ReturnUAFRequest, SendUAFResponse → ServerResponse (§8.3.3–8.3.7 `#h4_getuafrequest-dictionary`, `#h4_returnuafrequest-dictionary`, `#h4_senduafresponse-dictionary`, `#h4_serverresponse-interface`); Token types (§8.3.9 `#h4_tokentype-enum`); anti-CSRF/XSSI advice (§8.3.10 `#h4_security-considerations`).

**What matters most:**
- Facet identity comes from the platform, never the app: browser origin, APK signing-key hash or iOS bundle ID; only ACT_AS_WEB_BROWSER callers may pass an origin (§6.1.2 `#h4_org.fidoalliance.uaf.permissions.act_as_web_browser`, §7.1.3 `#h4_origin`).
- Apps must report server results back (notifyUAFResult / UAF_OPERATION_COMPLETION_STATUS) so the client can drop keys the server rejected (§5.2.1 `#h4_methods`, §6.2.7 `#h4_uafintenttype.uaf_operation_completion_status`).
- Native apps own the TLS channel and must pass channelBindings themselves (§6.1.3 `#h4_channelbindings`); servers may answer 1490 when bindings are missing or wrong.
- HTTPS profile: servers MUST accept `application/fido+uaf`; when delivering a response the client MUST send that Content-Type; servers should refuse requests that a script tag or simple CORS request could forge (§8.3.6 `#h4_delivering-a-uaf-response`, §8.3.10).

**Watch out for:**
- notifyUAFResult and the Android/iOS `responseCode` refer to a "uafResult field of a ServerResponse"; ServerResponse actually names it `statusCode`.
- §7.1.1 says the iOS response is encrypted "with the public key", but §7.1.2 defines symmetric direct encryption with the caller's secret key; §7.1.2 is the rule.
- §8.1 and §8.2 are labelled non-normative inside a normative chapter and use lowercase "must"; §8.2 still cites a TLS 1.3 draft.
- §6.1.1 notes that the best way to mark FIDO clients on Android 5+ is still undetermined.
- The FacetID trust rules themselves are in the AppID and Facet specification, not here.

**Related documents:** fido-uaf-protocol (message contents, ChannelBinding, AppID/facet processing, policy); fido-uaf-asm-api (AuthenticatorInfo that feeds §4.3); fido-uaf-overview; the shared FIDO AppID and Facet, Registry and Metadata Statement documents.
