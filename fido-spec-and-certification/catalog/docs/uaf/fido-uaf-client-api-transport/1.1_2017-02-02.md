# FIDO UAF Application API and Transport Binding Specification

Version 1.1 · Proposed Standard · 2017-02-02 · [source](https://fidoalliance.org/specs/fido-uaf-v1.1-ps-20170202/fido-uaf-client-api-transport-v1.1-ps-20170202.html)

## Summary

The 1.1 edition of the UAF Application API and Transport Binding Specification, the version FIDO lists for certification. It defines the same DOM, Android intent and iOS custom-URL client bindings and the same TLS/HTTPS interoperability profile as 1.2. Compared with 1.2, it has no SYSTEM_INTERRUPTED error code, it only recommends against the FIDO_CLIENT permission on Android 5+, it has no explicit-intent rule for AIDL binding, iOS payloads use plain base64, and the client's `application/fido+uaf` Content-Type header is a MUST.

**Who needs it:** relying party app developers, UAF client developers and server developers targeting UAF 1.1

**Look here for:**
- Error codes → §4.5 `#h3_errorcode-interface`
- Android intent operations → §6.2 `#h3_org.fidoalliance.intent.fido_operation-intent`
- HTTPS profile → §8.3 `#h3_HttpsTransportInteroperabilityProfile`

## Reading guide

**Use this version when:** you build or certify a UAF 1.1 client, relying party app or server-side HTTPS endpoint; UAF 1.1 is the version FIDO certifies. The structure, section numbers and anchors are the same as 1.2, so the two editions can be read side by side.

**Differences from 1.2** (from a text comparison of the two editions):
- §4.5 ErrorCode `#h3_errorcode-interface` has no SYSTEM_INTERRUPTED (0x12); it still carries an editor's TODO note asking when AUTHENTICATOR_ACCESS_DENIED occurs and what the RP app should do. §4.3.1 `#h4_attributes-1` lacks the pointer to the protocol's rule for combining userVerification flags.
- §6.1.1 `#h4_org.fidoalliance.uaf.permissions.fido_client`: on Android 5 and later, clients SHOULD NOT (1.2: MUST NOT) declare FIDO_CLIENT. The RP-side check in §6.4 `#h3_security-considerations-for-android-implementations` is written in lowercase must/should.
- §6.4 has no rule that RP apps bind to the AIDL service with an explicit intent (added in 1.2).
- §7 iOS `#h2_ios-custom-url-api`: request and response payloads are plain base64 (1.2: base64url), there is no Swift example, and the result descriptions in §7.2 `#h3_json-values` speak of Android-style RESULT_OK/RESULT_CANCELLED alongside `errorCode`.
- §8.3.1 `#h4_obtaining-a-uaf-request-message`: when fetching a request, the client MUST set Content-Type `application/fido+uaf; charset=utf-8` (1.2 relaxes it to SHOULD), and there is no explicit server obligation to accept that media type.

**Section by section:** structure as in 1.2; see that page's reading guide. The essentials are the same: server status codes in §3.1 `#h3_uaf-status-codes`, the DOM `navigator.fido.uaf` methods in §5.2 `#h3_uaf-interface`, the single FIDO_OPERATION intent in §6.2 `#h3_org.fidoalliance.intent.fido_operation-intent`, ACT_AS_WEB_BROWSER as the only way to pass an explicit origin, JWE-encrypted iOS responses in §7.1.2 `#h4_secret-key-generation`, and the optional HTTPS profile in §8.3 `#h3_HttpsTransportInteroperabilityProfile`. The same inconsistencies apply (the "uafResult" field that ServerResponse calls `statusCode`, and iOS encryption described once as public-key).
