# FIDO UAF APDU

Version 1.2 · Proposed Standard · 2020-10-20 · [source](https://fidoalliance.org/specs/fido-uaf-v1.2-ps-20201020/fido-uaf-apdu-v1.2-ps-20201020.html)

## Summary

The UAF APDU specification maps UAF Authenticator Commands onto ISO 7816-4 APDUs so that a UAF authenticator can be built on a Secure Element (UICC, eSE, microSD and similar). It describes the Hybrid SE authenticator, in which the SE holds the keys and runs the UAF applet while host software handles user verification and display, and the message flow between the ASM and that authenticator. It then defines the applet and its commands: applet selection by AID, user verification (PIN via VERIFY), cryptographic duties, CLA byte coding, the `UAF` APDU that carries a TLV authenticator command, the mapping of authenticator status codes to status words, SELECT and VERIFY, and two ways to handle long commands and responses (ISO chaining/extended length, or a proprietary variant). A short security section closes it.

The applet AID value is registered in the UAF Registry (§6.1 there). Command semantics come from Authenticator Commands.

**Who needs it:** Secure Element and smart-card authenticator vendors, ASM developers driving SE-based authenticators

## Reading guide

**Start here:** §4.2.2.1 `#h5_mapping-between-fido-uaf-authenticator-commands-and-apdu-commands` (the whole idea: a UAF authenticator command is wrapped unchanged in one APDU), §4.2.2.2 `#h5_response-message-and-status-conditions-of-an-uaf-apdu-command` (how the host turns status words back into UAF status codes), then §4.3 `#h3_managing-long-apdu-commands-and-responses` (how responses longer than one APDU come back). Everything before §4 is non-normative background.

**Section by section:**
- §1 Notation `#h2_notation`: TLVs are little-endian (as in the Authenticator Commands spec), APDUs follow ISO 7816-4:2013, and all diagrams, examples and notes are non-normative.
- §2 Introduction `#h2_introduction` and §3 use cases `#h2_se-based-authenticator-implementation-use-cases` (informative): target form factors (UICC, eSE, µSD, NFC card, USB token). The SE can be the whole silent authenticator or the crypto part of a Hybrid SE Authenticator, where PIN or biometric capture and possibly matching happen in a TEE, sensor or host software. Implementing this spec is optional in UAF, but products that carry UAF over APDUs should follow it.
- §3.1.1 Architecture `#h4_architecture-of-the-hybrid-se-authenticator`: one firm rule. A hybrid design MUST have a dedicated software host that knows the applet; the host maps UAF commands to APDUs. §3.1.2 `#h4_communication-flow-between-the-asm-and-the-hybrid-se-authenticator`: if user verification runs in the host (e.g. a TEE), the host, not the SE, creates the UserVerificationToken.
- §4.1 UAF Applet `#h3_uaf-applet-in-the-authenticator`: the AID comes from the registry; user verification is PIN or biometric; the applet performs the Authenticator Commands crypto and SHALL use registry algorithms.
- §4.2.1 Class byte `#h4_class-byte-coding`: CLA 0x00 for SELECT and the ISO VERIFY/GET RESPONSE, CLA 0x80 for UAF, proprietary VERIFY and GET RESPONSE. Payloads over 255 bytes should use ISO command chaining.
- §4.2.2 UAF command `#h4_apdu-command-uaf`: INS SHALL be 0x36, P1 = P2 = 0x00, data = the complete Authenticator Command TLV; the applet MUST read the first 2-byte tag to identify the command.
- §4.2.2.2 status mapping: 9000 returns the data field; 61xx means the host loops GET RESPONSE and concatenates; any other status word becomes a host-built TLV response carrying the mapped TAG_STATUS_CODE (e.g. 6A88 → UAF_CMD_STATUS_USER_NOT_ENROLLED, 63C0 → USER_LOCKOUT, unmapped → ERR_UNKNOWN). Some UAF codes (USER_CANCELLED, TIMEOUT, CANNOT_RENDER_TRANSACTION_CONTENT) have no APDU equivalent.
- §4.2.3 SELECT `#h4_apdu-command-select`: the host must select the applet first (00 A4 04 0C, AID A000000647AF0001); on Android, in a logical channel, because the basic channel belongs to the baseband.
- §4.2.4 VERIFY `#h4_apdu-command-verify`: INS 0x20 (PIN) or 0x21 (biometric). If the applet supports UserVerificationToken, it SHALL return one on success, and the host needs it for Register and Sign. Support is visible in GetInfo or the SELECT response.
- §4.3.1 ISO variant `#h4_iso-variant` / §4.3.2 proprietary variant `#h4_proprietary-variant`: the proprietary variant returns tag 0x2813 holding the expected total length, and the host re-sends the UAF command with P2 = 1 until it has all the data. The host must support both and choose by looking for 0x2813.
- §5 Security considerations `#h2_security-considerations` (informative): host-to-SE integrity and confidentiality are left to the implementation; GlobalPlatform and ETSI secure channels are suggested.

**What matters most:**
- The applet never parses an APDU-specific structure: it handles the full Authenticator Command TLV. Get that spec right first (§4.2.2.1).
- Status word translation is the host's job, and the host must build a valid UAF TLV response for error words (§4.2.2.2).
- An applet without UserVerificationToken may use plain ISO VERIFY only if it binds VERIFY to the following Register/Sign, e.g. with secure messaging (note in §4.2.4.2 `#h5_response-message-and-status-conditions`).
- Long-response handling: the host must detect which variant the applet uses (§4.3.2).

**Watch out for:**
- §4.3 is worded backwards: it ties GET RESPONSE to SEs that *can* send a complete response. The note at the end of §4.3.2 (choose by the presence of tag 0x2813) is the usable rule.
- Table 3 maps 6982 to UAF_CMD_STATUS_ACCESS_DENIED, while Table 4 describes 6982 as "user verification required"; treat both as the same condition.
- §4.2.2.1 points to "part 6.2" of the Authenticator Commands spec for command structures; that number refers to the other spec's layout.
- The P2 = 1 repetition in §4.3.2 departs from the P2 = 0x00 shown in Table 2.
- Tag 0x2813 is also TAG_TRANSACTIONCONFIRMATION_TOKEN in the Authenticator Commands spec; this document does not say where in the response the host should look for it.

**Related documents:** fido-uaf-authnr-cmds (the command and response TLVs carried in the payload, status codes, UserVerificationToken); fido-uaf-reg (the UAF AID and tag values); fido-uaf-asm-api (the layer above the host); fido-uaf-protocol (what the server finally checks).
