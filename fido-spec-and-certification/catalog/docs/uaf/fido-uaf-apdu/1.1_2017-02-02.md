# FIDO UAF APDU

Version 1.1 · Proposed Standard · 2017-02-02 · [source](https://fidoalliance.org/specs/fido-uaf-v1.1-ps-20170202/fido-uaf-apdu-v1.1-ps-20170202.html)

## Summary

The 1.1 edition of the UAF APDU mapping, the version FIDO lists for certification. It covers the Hybrid SE authenticator architecture, UAF applet selection, PIN verification, the `UAF` APDU that carries TLV authenticator commands, status-word mapping and long-APDU handling. Its technical content is the same as 1.2; the later edition only renumbers tables and capitalises one requirement keyword, so implementations built to either edition behave the same.

**Who needs it:** Secure Element authenticator vendors and ASM developers targeting UAF 1.1

**Look here for:**
- Command-to-APDU mapping → §4.2.2.1 `#h5_mapping-between-fido-uaf-authenticator-commands-and-apdu-commands`
- Status word mapping → §4.2.2.2 `#h5_response-message-and-status-conditions-of-an-uaf-apdu-command`
- Long APDUs → §4.3 `#h3_managing-long-apdu-commands-and-responses`

## Reading guide

**Use this version when:** you build or certify a Secure Element based UAF authenticator, or the host/ASM in front of one, against UAF 1.1, which is the UAF version FIDO certifies. Because the 1.2 text is technically identical, the same applet and host satisfy both editions.

**Differences from 1.2:** none that change behaviour. A text comparison of the two editions shows table numbering shifted by one (1.1 starts its class-byte table at Table 2, so the status mapping is Table 4 and the long-response table numbering follows), "must" for the dedicated host in §3.1.1 `#h4_architecture-of-the-hybrid-se-authenticator` capitalised to MUST in 1.2, minor punctuation, and reference entries pointing at 1.1 rather than 1.2 documents. The INS byte, SELECT AID, VERIFY variants, status-word table and both long-response variants are the same.

**Section by section:** structure as in 1.2; see that page's reading guide. The parts to read first are the same: the command mapping §4.2.2.1 `#h5_mapping-between-fido-uaf-authenticator-commands-and-apdu-commands`, status-word handling §4.2.2.2 `#h5_response-message-and-status-conditions-of-an-uaf-apdu-command`, VERIFY and the UserVerificationToken §4.2.4 `#h4_apdu-command-verify`, and long responses §4.3 `#h3_managing-long-apdu-commands-and-responses` (ISO GET RESPONSE or the proprietary tag 0x2813 with the UAF command repeated at P2 = 1). The same wording issues apply: §4.3 reads backwards relative to the closing note of §4.3.2 `#h4_proprietary-variant`, status 6982 is labelled differently in the two status tables, and 0x2813 is also TAG_TRANSACTIONCONFIRMATION_TOKEN in Authenticator Commands 1.1. When reading the payload side, pair this edition with fido-uaf-authnr-cmds 1.1.
