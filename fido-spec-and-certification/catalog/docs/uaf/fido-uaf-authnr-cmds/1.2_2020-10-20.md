# FIDO UAF Authenticator Commands

Version 1.2 · Proposed Standard · 2020-10-20 · [source](https://fidoalliance.org/specs/fido-uaf-v1.2-ps-20201020/fido-uaf-authnr-cmds-v1.2-ps-20201020.html)

## Summary

UAF Authenticator Commands defines the normative behaviour of a UAF authenticator at its lowest interface. It classifies authenticators as first-factor or second-factor and as bound or roaming. It allocates the TLV tags and status codes. It defines the structures: RawKeyHandle; the registration and authentication assertions (TAG_UAFV1_REG_ASSERTION and TAG_UAFV1_AUTH_ASSERTION) that the FIDO Server parses; and the UserVerificationToken. The commands are GetInfo, Register, Sign, Deregister and OpenSettings, each with its structure, response, status codes and processing steps, including counters, attestation and transaction-confirmation display.

Later chapters explain how KeyIDs and key handles are stored and looked up for each authenticator type, which inputs gate access to each command (KHAccessToken, KeyHandle, KeyID), algorithm choices, how the authenticator model is indicated, and how the design relates to TEE, Secure Elements, TPM and unreliable transports. Appendix A gives security guidelines for implementers. The ASM API sits above this document; the APDU document maps these commands onto Secure Element APDUs.

**Who needs it:** authenticator vendors and firmware/TEE/SE implementers, ASM developers, FIDO Server developers (assertion formats)

**Look here for:**
- TLV tag and status code values → §4.1 `#h3_command-tags`, §4.4 `#h3_status-codes`
- Layout of the registration assertion a server must parse → §5.2.1 `#h4_tag_uafv1_reg_assertion`
- Register command processing → §6.2.4 `#h4_command-description-1`
- Sign command processing, including transaction display → §6.3.4 `#h4_command-description-2`
- Where KeyIDs and key handles live for each authenticator type → §7 `#h2_keyids-and-key-handles`
- Security guidelines for implementers → Appendix A `#h2_security-guidelines`

**Changes from previous version:** New status UAF_CMD_STATUS_SYSTEM_INTERRUPTED (0x12), with a retry hint; USER_CANCELLED is now marked as not to be retried. The Sign command may now show transaction text before user verification (the preferred option) as well as after it. The Authenticator Nonce is capped at 64 bytes, with a rationale added. Bound authenticators that use a different command interface, such as a native key store or key chain, may bind keys to the AppID by another method of equal strength instead of KHAccessToken, should declare `isKeyRestricted` in metadata, and may receive a temporary KeyID from the ASM. A KeyID may be a hash of the public key. The GetInfo PNG characteristics gain a PLTE descriptor. Attestation identifiers are renamed from `TAG_ATTESTATION_*` to `ATTESTATION_*`. The mandatory functions now cover verifying user presence as well as verifying the user. Several key-handle statements are softened from definite to typical behaviour.

## Reading guide

**Start here:** §3.1 `#h3_types-of-authenticators` (the four authenticator types drive almost every branch later), §4 `#h2_tags` (TLV rules), §5.2 `#h3_structures-to-be-parsed-by-fido-server` (the KRD and SignedData that servers verify), then the Register and Sign descriptions §6.2.4 `#h4_command-description-1` and §6.3.4 `#h4_command-description-2`. Appendix A `#h2_security-guidelines` is informative but is where counter, key-handle and matcher expectations live.

**Section by section:**
- §2–§3 `#h2_overview`, `#h2_uaf-authenticator` (informative): everything assumes UAFV1TLV; other schemes need not follow this document. Mandatory functions: verify the user or presence, do the crypto, build server-parsable structures, attest if supported; transaction display is optional. §3.1 defines 1stF/2ndF × bound/roaming; a bound authenticator acting as roaming for another device MUST follow both sets of rules; every authenticator MUST implement at least one attestation type, one algorithm and one key format.
- §4 Tags `#h2_tags`: all data MUST be TLV; 14-bit tag space; 0x1000 composite, 0x2000 critical (MUST abort if not understood); the ASM MUST send fields in the normative order, while authenticator output may be in any order. §4.1 command tags `#h3_command-tags`, §4.2 command-only tags `#h3_tags-used-only-in-authenticator-commands` (KeyHandle, UVT, AppID, KHAccessToken, AuthenticatorInfo …), §4.3 protocol tags `#h3_tags-used-in-uaf-protocol` (including ATTESTATION_BASIC_FULL/SURROGATE/ECDAA and TAG_EXTENSION 0x3E11 critical vs 0x3E12 non-critical), §4.4 status codes `#h3_status-codes`.
- §5.1 RawKeyHandle `#h3_rawkeyhandle`: layout is implementation-defined; 1stF authenticators MUST store and link the username, 2ndF MUST NOT; the RawKeyHandle MUST be wrapped before leaving the authenticator.
- §5.2.1 TAG_UAFV1_REG_ASSERTION `#h4_tag_uafv1_reg_assertion`: KRD = AAID, ASSERTION_INFO (version, auth mode, signature and public-key alg/encoding), FinalChallengeHash, KeyID, counters (sign and reg), public key; then one attestation block. Basic full signs the whole KRD TLV with the attestation key and lists the certificate chain leaf-first, ending at a metadata root; surrogate signs with the new UAuth key; ECDAA per the ECDAA spec. Signed custom data goes in TAG_EXTENSION inside the KRD, unsigned data outside it.
- §5.2.2 TAG_UAFV1_AUTH_ASSERTION `#h4_tag_uafv1_auth_assertion`: SignedData = AAID, ASSERTION_INFO (auth mode 0x01 verified / 0x02 transaction confirmed), authenticator nonce (8–64 bytes), FinalChallengeHash, transaction content hash (zero length in mode 0x01), KeyID, SignCounter; signature over the whole SignedData TLV.
- §5.3 UserVerificationToken `#h3_userverificationtoken` (concept is non-normative): single-use or time-bound binding between vendor user verification and Register/Sign.
- §6.1 GetInfo `#h3_getinfo-command`: API version, and per authenticator: index, AAID, metadata bit flags (2ndF, roaming, internal key-handle storage, built-in UI, settings, AppID expected, user enrolled, UVT support, hash-only transactions), MaxKeyHandles, UV/key/matcher protection, tcDisplay, algorithm, content type and PNG characteristics (with PLTE in 1.2), assertion scheme, attestation types, extension IDs.
- §6.2 Register `#h3_register-command`: show the AppID if a display can; mix AppID into KHAccessToken; verify (or enrol) the user, honouring a UVT; check attestation type; generate a fresh key pair (MUST be unique per call); build and wrap RawKeyHandle; KeyID = key handle for 2ndF roaming, else a generated KeyID (unique per AAID, unguessable, ≤32 bytes); attest; store (1stF roaming) or return (bound) the key handle. MUST NOT register without verifying or enrolling the user; silent authenticators MUST NOT have key handles stored on the server; unsupported counters are 0 and both reset on factory reset.
- §6.3 Sign `#h3_sign-command`: optional transaction display before (preferred) or after user verification; silent authenticators and those with tcDisplay 0 refuse transactions with ACCESS_DENIED; unwrap and filter key handles by KHAccessToken; with several matches a 1stF authenticator returns TAG_USERNAME_AND_KEYHANDLE pairs (two-stage Sign) and a 2ndF one uses the first; hash-only transactions allowed only when tcDisplay is 0x0003; increment SignCounter and sign. MUST NOT sign or reveal usernames before verifying the user; bound authenticators MUST validate KHAccessToken (or an equal-strength alternative for key-store-style interfaces).
- §6.4 Deregister `#h3_deregister-command`: only for authenticators that store key handles (others return CMD_NOT_SUPPORTED and the ASM deletes); empty KeyID deletes all keys for the AppID/KHAccessToken; SHOULD NOT reveal whether a KeyID existed and never returns KEY_DISAPPEARED_PERMANENTLY. §6.5 OpenSettings `#h3_opensettings-command`.
- §7 KeyIDs and key handles `#h2_keyids-and-key-handles` (informative): per-type tables (§7.1–7.4) showing where key handles live and why 2ndF types need server-supplied KeyIDs.
- §8 Access control `#h2_access-control-for-commands` (normative): Register always needs UserVerify; Sign needs UserVerify plus KHAccessToken and, except for 1stF roaming, the key-handle list; Deregister needs KHAccessToken and KeyID.
- §9–§10 (informative) `#h2_considerations`, `#h2_relationship-to-other-standards`: TPM-compatible algorithm choices; when an authenticator cannot put its AAID in the KRD, the ECDAA issuer key must be dedicated to one model (§9.2 `#h3_indicating-the-authenticator-model`); TEE/SE/TPM integration notes; no reliability layer for lossy transports (§10.4 `#h3_unreliable-transports`).

**What matters most:**
- Byte-exact assertion layout and signing the complete KRD/SignedData TLV including tag and length (§5.2); servers must accept any tag order inside composites.
- User verification before Register and Sign, KHAccessToken filtering for bound authenticators, and wrapped key handles (§6.2.4, §6.3.4, §8).
- Counter semantics: 0 means unsupported, reset on factory reset, per-key counters preferred and a global one advanced by a random amount (§6.2.4, Appendix A). Servers' clone detection depends on this.
- KeyID rules and the different key-handle models per authenticator type (§6.2.4, §7).
- Transaction confirmation: hash goes into SignedData with mode 0x02; metadata MUST declare the display type truthfully, including ASM-hosted displays (§6.3.4).

**Watch out for:**
- §6 is labelled "This section is non-normative" yet states that interoperable authenticators MUST implement the command interface and contains many MUST rules; the processing rules are treated as normative in practice.
- GetInfo flag 0x0100 names TAG_TRANSACTION_TEXT_HASH, which is not defined; the Sign command uses TAG_TRANSACTION_CONTENT_HASH.
- TAG_TRANSACTIONCONFIRMATION_TOKEN is 0x2813, the same value the APDU binding (fido-uaf-apdu §4.3.2) uses for its proprietary length tag.
- The attestation identifiers are listed here as ATTESTATION_*; ASM and client documents still say they come from the UAF Registry with a TAG_ATTESTATION prefix, but the 1.2 registry no longer lists them.
- Some steps say "jump to step #8" or "step 9.3" although the published lists are not numbered that way.
- Appendix A uses lowercase must/should throughout; it is informative guidance, though certification security requirements cover similar ground.

**Related documents:** fido-uaf-asm-api (the caller of these commands, KHAccessToken construction, status mapping); fido-uaf-protocol (how servers verify these structures); fido-uaf-reg (tag registry, extensions); fido-uaf-apdu (carrying these commands to a Secure Element); the shared FIDO Registry (ALG_*, KEY_PROTECTION, USER_VERIFY values), Metadata Statement and ECDAA documents.
