# FIDO UAF Authenticator Commands

Version 1.1 · Proposed Standard · 2017-02-02 · [source](https://fidoalliance.org/specs/fido-uaf-v1.1-ps-20170202/fido-uaf-authnr-cmds-v1.1-ps-20170202.html)

## Summary

The 1.1 edition of UAF Authenticator Commands, the version FIDO lists for certification. It has the same structure as 1.2: authenticator types, TLV tags and status codes, assertion structures, the GetInfo, Register, Sign, Deregister and OpenSettings commands, key-handle storage models, access control and security guidelines. Compared with 1.2, it has no SYSTEM_INTERRUPTED status, Sign shows transaction text only after user verification, there is no upper bound on the Authenticator Nonce length, and there is no allowance for key store or key chain based authenticators to replace KHAccessToken. Attestation types are named `TAG_ATTESTATION_*`.

**Who needs it:** authenticator vendors and ASM developers targeting UAF 1.1 certification

**Look here for:**
- Tags and status codes → §4.1 `#h3_command-tags`, §4.4 `#h3_status-codes`
- Register command processing → §6.2.4 `#h4_command-description-1`
- Sign command processing → §6.3.4 `#h4_command-description-2`
- Access control for commands → §8 `#h2_access-control-for-commands`

## Reading guide

**Use this version when:** you build or certify a UAF 1.1 authenticator or the ASM that drives it; UAF 1.1 is the version FIDO certifies. Section numbers and anchors match 1.2, so the two can be compared directly.

**Differences from 1.2** (from a text comparison):
- §4.3 `#h3_tags-used-in-uaf-protocol` and §5.2.1 `#h4_tag_uafv1_reg_assertion` name the attestation blocks TAG_ATTESTATION_BASIC_FULL, TAG_ATTESTATION_BASIC_SURROGATE and TAG_ATTESTATION_ECDAA (same values 0x3E07–0x3E09), matching the 1.1 registry.
- §4.4 `#h3_status-codes` has no UAF_CMD_STATUS_SYSTEM_INTERRUPTED and no "do not retry" note on USER_CANCELLED.
- §5.2.2 `#h4_tag_uafv1_auth_assertion`: the authenticator nonce must be at least 8 bytes with no maximum (1.2 caps it at 64).
- §6.3.4 `#h4_command-description-2`: transaction content is displayed only after user verification; 1.2 adds the before-verification option and prefers it. The 1.1 text also lacks the alternative-binding allowance for bound authenticators using key store/key chain interfaces, and the note on a cached key handle or cookie making a silent authenticator part of a first-factor setup.
- §6.2.4 `#h4_command-description-1`: KeyIDs are generated randomly (1.2: any generation method, including a public-key hash) and there is no ASM-supplied temporary KeyID. §6 has no `isKeyRestricted` note.
- §6.1.3 `#h4_command-response`: PNG characteristics have no PLTE descriptor.
- §8 `#h2_access-control-for-commands`: KHAccessToken must be known to the caller, without 1.2's "or an alternative of similar strength".
- §7 `#h2_keyids-and-key-handles` states key-handle placement as fixed facts (e.g. 2ndF bound authenticators never store key handles) where 1.2 says "typically" or "might".

**Section by section:** structure as in 1.2; see that page's reading guide. The core is unchanged: TLV rules in §4 `#h2_tags`, KRD and SignedData layouts in §5.2 `#h3_structures-to-be-parsed-by-fido-server`, Register and Sign processing, KHAccessToken filtering and two-stage Sign with TAG_USERNAME_AND_KEYHANDLE, Deregister that never reveals whether a KeyID existed (§6.4.4 `#h4_command-description-3`), and the security guidelines in Appendix A `#h2_security-guidelines`. The same document quirks apply: §6 is labelled non-normative while full of MUSTs, GetInfo flag 0x0100 names an undefined TAG_TRANSACTION_TEXT_HASH, and TAG_TRANSACTIONCONFIRMATION_TOKEN (0x2813) shares its value with the APDU binding's proprietary length tag.
