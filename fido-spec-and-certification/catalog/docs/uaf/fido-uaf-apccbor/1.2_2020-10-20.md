# FIDO UAF Android Protected Confirmation Assertion Format

Version 1.2 · Proposed Standard · 2020-10-20 · [source](https://fidoalliance.org/specs/fido-uaf-v1.2-ps-20201020/fido-uaf-apccbor-v1.2-ps-20201020.html)

## Summary

This UAF 1.2 document defines the APCV1CBOR assertion scheme, which uses Android Protected Confirmation (APC) to carry out UAF transaction confirmation. With APC, the Android platform shows the transaction text in a trusted UI and signs a CBOR object containing the confirmed prompt.

For registration, the assertion is the normal UAF registration assertion with two constraints: only surrogate basic attestation is allowed, and the Android Key Attestation extension must be present. The self-signature field is empty because the key cannot sign arbitrary data. For authentication, a TLV wrapper (TAG_APCV1CBOR_AUTH_ASSERTION) carries the APC-signed CBOR data together with the AAID, the KeyID and a signature that covers only the CBOR data; the other fields are unauthenticated hints. The processing rules show how the ASM puts the final challenge hash into APC's extraData and the `text/plain` transaction into its prompt text, and how the FIDO Server checks both against the cached transaction. A sample Metadata Statement shows how such an authenticator is described.

This is a new document in UAF 1.2. The tag values are allocated in the UAF Registry 1.2.

**Who needs it:** Android authenticator and ASM developers using Protected Confirmation, FIDO Server developers supporting transaction confirmation

## Reading guide

**Start here:** §3.2 `#h3_authentication-assertion` (the only new wire format), then the two server sections §4.2 `#h3_registration-response-processing-rules-for-fido-server` and §4.4 `#h3_authentication-response-processing-rules-for-fido-server`, which plug into the UAF Protocol's server rules at the point where an unknown assertion scheme would otherwise be skipped. §2 is one informative sentence.

**Section by section:**
- §3.1 Registration Assertion `#h3_registration-assertion`: an ordinary UAFV1TLV registration assertion (KRD) with two constraints. Only surrogate basic attestation is allowed and the `fido.uaf.android.key_attestation` extension MUST be present; TAG_SIGNATURE SHALL be zero-length because an APC-restricted key cannot sign its own KRD.
- §3.2 Authentication Assertion `#h3_authentication-assertion`: TAG_APCV1CBOR_AUTH_ASSERTION containing TAG_APCV1CBOR_SIGNED_DATA (the serialized APC CBOR object, tbsData), TAG_AAID, TAG_KEYID and TAG_SIGNATURE. The signature covers tbsData only; AAID and KeyID are unauthenticated hints. There are no counters, no authenticator nonce and no TAG_ASSERTION_INFO in this structure.
- §4.1 ASM registration rules `#h3_registration-response-processing-rules-for-asm`: the usual ASM steps (locate authenticator, verify or enrol the user, hash the final challenge), then generate a key marked for Android Protected Confirmation, build the KRD with an empty surrogate signature, attach the hardware key attestation extension, store CallerID/AppID/KeyHandle/KeyID for bound authenticators, and return assertionScheme "APCV1CBOR".
- §4.2 Server registration rules: replaces skipping at step 6.9 of the protocol's registration processing. Checks: preferred attestation type, KRD FinalChallengeHash equals FCHash, authenticator version not older than metadata, RegCounter must be 0, attestation type is ATTESTATION_BASIC_SURROGATE and metadata has *no* attestationRootCertificates, the key attestation extension verifies under the UAF Registry rules, and its attestation includes TRUSTED_CONFIRMATION_REQUIRED.
- §4.3 ASM authentication rules `#h3_authentication-response-generation-rules-for-asm`: verify CallerID for bound authenticators; the ASM MUST have the user verified; resolve KeyHandles from keyIDs (or let the user pick a username); build a ConfirmationPrompt with the transaction text as prompt text and the FinalChallengeHash as extraData; sign dataThatWasConfirmed with the chosen key; wrap it as in §3.2. The Metadata Statement MUST describe the transaction confirmation display truthfully (typically ANY or PRIVILEGED_SOFTWARE).
- §4.4 Server authentication rules: replaces skipping at step 6.6 of protocol §3.5.7.5. Match AAID with the stored registration, find UAuth.pub by AAID and KeyID, compute FCHash (metadata hash for FinalChallengeParams, `fcp.hashAlg` for client data), require extraData == FCHash, require promptText to be in the RP's cachedTransactions, then verify the signature over tbsData.
- §5 Example Metadata Statement `#h2_example-for-fido-metadata-statement` (informative): assertionScheme APCV1CBOR, surrogate attestation type, empty attestationRootCertificates, isKeyRestricted true, tcDisplay set, and the key attestation roots carried in `supportedExtensions`.

**What matters most:**
- Trust comes from Android key attestation, not from a UAF attestation chain: the server must reject an AAID whose metadata lists attestation roots, and must see TRUSTED_CONFIRMATION_REQUIRED (§4.2).
- The transaction binding is entirely in tbsData: extraData carries the final challenge hash and promptText the transaction, so the server must compare both (§4.4).
- Transaction content is `text/plain` only, because APC shows a text prompt (note in §4.4).
- Without counters in the authentication assertion, the protocol's sign-counter clone check cannot be applied to these assertions (§3.2).

**Watch out for:**
- Step references point into other documents without always naming them: "step 6.9" in §4.2 is in the protocol's registration-response rules, and §3.1 cites "section 5.2.1" of the Authenticator Commands spec.
- §4.4 says the assertion "starts with a valid CBOR structure", but per §3.2 it starts with a TLV tag and only tbsData is CBOR.
- §4.4 calls the WebAuthn-style variant "ClientData"; the protocol names it CollectedClientData.
- The ASM rules link to Android developer pages for the APC API; those external pages, not this spec, define ConfirmationPrompt behaviour.

**Related documents:** fido-uaf-protocol 1.2 (server processing rules this document hooks into, cachedTransactions, CollectedClientData); fido-uaf-reg 1.2 (tags 0x3E05/0x3E06 and the Android Key Attestation server checks); fido-uaf-asm-api 1.2 (RegisterIn/AuthenticateIn and status codes); fido-uaf-authnr-cmds 1.2 (KRD layout and surrogate attestation).
