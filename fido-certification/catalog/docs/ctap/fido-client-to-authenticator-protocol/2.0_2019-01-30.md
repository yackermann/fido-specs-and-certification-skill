# Client to Authenticator Protocol (CTAP)

Version 2.0 · Proposed Standard · 2019-01-30 · [source](https://fidoalliance.org/specs/fido-v2.0-ps-20190130/fido-client-to-authenticator-protocol-v2.0-ps-20190130.html)

## Summary

CTAP 2.0 is the first CTAP2 Proposed Standard: the CBOR-encoded command protocol a client platform uses to talk to a roaming authenticator, plus its USB HID, NFC and BLE bindings and rules for falling back to CTAP1/U2F devices. It defines six commands (makeCredential, getAssertion, getNextAssertion, getInfo, clientPIN, reset), a single PIN protocol built around a `pinToken`, and only one extension, `hmac-secret`. Authenticators built to it report `FIDO_2_0` (and `U2F_V2` if they also speak U2F) in getInfo `versions`. Later versions replace the PIN machinery and add management commands, so this edition matters mostly for legacy devices and for backwards compatibility.

**Who needs it:** authenticator vendors maintaining FIDO2 (CTAP 2.0) products, platform & client developers supporting older authenticators, labs testing legacy devices

**Look here for:**
- What getInfo returns and which version strings exist → §5.4 `#authenticatorGetInfo`
- How the 2.0 PIN protocol and pinToken work → §5.5 `#authenticatorClientPIN`
- CTAP2 status/error codes → §6.3 `#error-responses`
- Mapping CTAP2 requests onto U2F authenticators → §7 `#u2f-interoperability`
