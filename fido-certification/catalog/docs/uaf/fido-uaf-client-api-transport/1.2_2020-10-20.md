# FIDO UAF Application API and Transport Binding Specification

Version 1.2 · Proposed Standard · 2020-10-20 · [source](https://fidoalliance.org/specs/fido-uaf-v1.2-ps-20201020/fido-uaf-client-api-transport-v1.2-ps-20201020.html)

## Summary

The UAF Application API and Transport Binding Specification defines how a relying party's web page or native app talks to the UAF Client, and how UAF messages travel to the FIDO Server. It defines the shared types (UAFMessage, Version, Authenticator, DiscoveryData, ErrorCode). It then gives three client bindings: a DOM API for browsers (`navigator.fido.uaf` with discover, checkPolicy and processUAFOperation calls and their callbacks, plus privacy and same-origin rules); an Android intent API (FIDO_OPERATION intent types, permissions, an AIDL service alternative and caller checks); and an iOS custom-URL API using x-callback-url, with encrypted payloads.

The transport chapter sets TLS requirements and an HTTPS interoperability profile: GetUAFRequest, ReturnUAFRequest and SendUAFResponse objects, the ServerResponse and Token interfaces, and the `application/fido+uaf` media type. The message contents themselves are defined in the Protocol specification.

**Who needs it:** relying party web and app developers, UAF client and browser/platform developers, FIDO Server developers (HTTPS profile)

**Look here for:**
- Error codes returned to the calling app → §4.5 `#h3_errorcode-interface`
- Browser API methods → §5.2 `#h3_uaf-interface`
- Android intent operations → §6.2 `#h3_org.fidoalliance.intent.fido_operation-intent`
- iOS x-callback-url binding → §7.1 `#h3_ios-specific-definitions`
- TLS requirements → §8.2 `#h3_tls-security-requirements`
- HTTPS message exchange with the server → §8.3 `#h3_HttpsTransportInteroperabilityProfile`

**Changes from previous version:** New error code SYSTEM_INTERRUPTED (0x12). On Android 5 and later, UAF Clients MUST NOT (was SHOULD NOT) declare the FIDO_CLIENT permission. Relying party apps that use the AIDL service MUST bind with an explicit intent. On iOS, payloads are base64url rather than base64, a Swift example is added, and the result descriptions are rewritten around the x-callback-url `errorCode` instead of Android-style result codes. In the HTTPS profile, the client's Content-Type header is now a SHOULD, and servers MUST accept `application/fido+uaf`. Also: a pointer to how authenticator flags are combined, a leftover TODO note removed, and RFC 2119 keywords capitalised.
